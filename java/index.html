I · Foundations · Chapter 1

Why Android is shaped this way

A phone is a hostile place to run software. Every odd rule in Android follows from that.

Why it exists

A server gets steady power, plenty of memory, and software its owner chose. A phone has a battery, a few gigabytes shared by dozens of apps, and code from strangers. The user switches apps every few seconds and expects each to be where they left it.

A Java server process starts at main() and lives until you stop it. Android inverted that contract. The system owns your process. It starts your process when something needs it and kills it when memory runs short, without asking.

Mental model

Your app is a guest in someone else's house. The system invites it in for a reason (a component), and can ask it to leave at any time.

  1. No main(). You declare entry points called components. The system instantiates them.
  2. A sandbox per app. Each app runs as its own Linux user and cannot read another app's files or memory.
  3. Everything crosses a process boundary through Binder. Starting a screen, reading contacts and showing a notification are remote calls to system services.

Mechanics

Layer What it does You meet it when
Linux kernel Processes, memory, drivers, Binder IPC, per-app UIDs You hit a permission or memory limit
HAL and native libraries Camera, sensors, graphics, media You use hardware
ART (Android Runtime) Runs DEX bytecode with an interpreter, JIT, and profile-guided ahead-of-time compilation. It is not a JVM You measure startup, or reach for a JDK API that is missing
Framework and system_server Activity, window, package and notification managers Every API call
Your app One or more processes forked from Zygote Always

Zygote boots once with the framework classes preloaded. Each app is a fork() of it, so apps start fast and share memory pages.

The main thread. Each app process has one main thread running a Looper that drains a message queue. Input, lifecycle callbacks and drawing all run there in order. Block it and the app freezes. If input goes unhandled for about five seconds the system shows an Application Not Responding dialog (ANR).

End-to-end flow: tapping the Kosh icon

  1. The launcher sends an Intent through Binder to system_server.
  2. The activity manager resolves the target and sees no Kosh process exists.
  3. It asks Zygote to fork. The child becomes the Kosh process under Kosh's UID.
  4. ActivityThread.main() starts the main Looper and attaches to the system.
  5. The system creates Application, then the launch Activity. onCreate() inflates the layout.
  6. On the next vsync the Choreographer runs measure, layout and draw. SurfaceFlinger composites the frame.

Failure modes

  • Main-thread work. Disk or network on the main thread drops frames, then causes ANRs.
  • Process death. The user leaves Kosh, memory runs low, Kosh is killed. On return the screen is recreated but every in-memory object, including every static field, is gone.
  • TransactionTooLargeException. Binder transactions share a buffer of about 1 MB per process. A large list in an Intent crashes at runtime.
  • Assuming a JVM. No virtual threads, no java.lang.management, and newer JDK APIs appear only on newer OS versions or through desugaring (chapter 2).

Trade-offs and when not to go native

Option Choose it when Cost
Native Android in Java A Java team, an existing Java codebase, or libraries you must share with a Java backend Views only; newer Jetpack APIs are increasingly Kotlin-first
Native Android in Kotlin A new app with no constraint A new language for a Java team, though a small one
Flutter, React Native UI-heavy app, one team, modest platform integration Bridges for platform features, larger binaries
A web app Content and forms, no hardware needs Weak background work, offline and key storage

For a regulated wallet, hardware-backed keys, biometrics and attestation push strongly toward native. All of those APIs are plain Java.

Production and security

The sandbox is your first control. Everything you export (components, files, links) is attack surface. Later chapters keep asking one question: what did we just expose outside our UID?

Java on Android

Which Java you actually get, what is missing, and the habits that keep Java code safe on this platform.

Why it exists

Android speaks the Java language but does not run a JVM. Source compiles to .class files, then to DEX bytecode for ART. Two questions therefore have separate answers: which language features can I write, and which library APIs exist on the device? Getting these confused produces code that compiles and then crashes on older phones.

Mental model

Language features are decided by the build tools. Library APIs are decided by the phone's OS version, unless the build tools carry a copy for you.

Mechanics

Question Decided by Practical answer today
Can I write lambdas, var, records, sealed types, text blocks? The compiler and D8, which rewrite ("desugar") newer constructs Yes, with source level 17
Can I call java.time, streams, Optional? The device's API level, or core library desugaring bundled into the app Yes on every device once desugaring is enabled
Can I use virtual threads, or the newest JDK APIs? ART No 
// app/build.gradle.kts
android {
    compileOptions {
        sourceCompatibility = JavaVersion.VERSION_17
        targetCompatibility = JavaVersion.VERSION_17
        isCoreLibraryDesugaringEnabled = true        // java.time and friends on old devices
    }
}
dependencies { coreLibraryDesugaring(libs.desugar.jdk.libs) }

Modern Java, used the Android way

/** Money as integer minor units. A record gives equals, hashCode and toString. */
public record Money(long minor, String currency) implements Comparable<Money> {

    public Money plus(Money other) {
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("Currency mismatch");
        return new Money(Math.addExact(minor, other.minor), currency);     // overflow throws, never wraps
    }

    /** Returns null for anything that is not a positive amount with at most two decimals. */
    @Nullable public static Money parse(@NonNull String text, @NonNull String currency) {
        try {
            var value = new BigDecimal(text.trim().replace(",", ""));
            if (value.signum() <= 0 || value.scale() > 2) return null;
            return new Money(value.movePointRight(2).longValueExact(), currency);
        } catch (NumberFormatException | ArithmeticException e) {
            return null;
        }
    }

    @Override public int compareTo(Money o) { return Long.compare(minor, o.minor); }
}

/** A closed set of outcomes. The compiler knows every implementation. */
public sealed interface TransferResult {
    record Success(String reference) implements TransferResult {}
    record Declined(String reason) implements TransferResult {}
    record NetworkError() implements TransferResult {}
}

static String message(TransferResult r) {
    if (r instanceof TransferResult.Success s) return "Sent. Ref " + s.reference();
    if (r instanceof TransferResult.Declined d) return "Declined: " + d.reason();
    return "Check your connection";
}

Nullability by annotation

Java has no nullable types, so Android uses annotations that lint and the IDE enforce:

@NonNull String displayName(@Nullable String nickname, @NonNull String legalName) {
    return nickname != null ? nickname : legalName;
}

Annotate every public method. It is the cheapest crash prevention available in Java, and it gives exact types to any Kotlin code that calls yours later.

What you do without

No coroutines (chapter 14 uses executors and RxJava). No Jetpack Compose (Part II uses Views). No extension functions, so helpers are static utility methods. No default arguments, so builders and overloads remain. The KTX artifacts add nothing for Java callers; use the base libraries.

End-to-end flow: one line of Java, to the device

  1. javac compiles LocalDate.now() and a record to .class files at language level 17.
  2. D8 desugars the record into an ordinary final class with generated methods.
  3. Core library desugaring rewrites the java.time call to a bundled implementation, because devices below API 26 lack the package.
  4. R8 shrinks and renames. The result is DEX.
  5. ART runs it. The phone never sees Java 17 bytecode.

Failure modes

  • NoSuchMethodError on older phones. A JDK API used without desugaring. Lint's NewApi check catches most; do not suppress it.
  • Null from anywhere. Unannotated methods, and Bundle, Intent and JSON values that may be absent.
  • Leaky inner classes. A non-static inner class or anonymous listener holds its outer Activity. Hand it to a long-lived object and the activity leaks.
  • static as storage. Static fields vanish with the process and leak one user's data to the next session if not cleared.
  • Reflection-based libraries and R8. Classes reached only by reflection are renamed or removed in release builds.

Trade-offs and when not to use it

Choose Java when the team and codebase are Java and the app is View-based. Be honest about direction: new Jetpack libraries arrive Kotlin-first, and some (Compose, Navigation 3, Room 3) are Kotlin-only. Java and Kotlin interoperate file by file in one module, so the choice is never permanent. A common steady state is Java for existing code and Kotlin for new modules.

Production and security

A record's generated toString() prints every field. Override it on anything holding tokens, account numbers or card data. Never use double for money. Mark classes final and fields private final by default; immutable state is what makes the patterns in Part III safe across threads.

Project anatomy and the build

What is in an Android project, and how Java source becomes an installable, signed app.

Why it exists

An Android app is not a JAR. It is DEX bytecode, compiled resources for many screens and languages, a manifest the OS reads before running anything, and a signature that fixes the app's identity forever. Gradle with the Android Gradle Plugin (AGP) drives that pipeline.

Mental model

The build takes one source tree and produces many variants, each a signed package whose manifest tells the OS what the app is allowed to be.

Mechanics

kosh/
├── settings.gradle.kts        which modules exist
├── gradle/libs.versions.toml  one place for every version
├── app/
│   ├── build.gradle.kts
│   └── src/main/
│       ├── AndroidManifest.xml
│       ├── java/com/kosh/app/…
│       └── res/               layout/, values/, drawable/, navigation/, by qualifier
└── core/, feature/            library modules (chapter 24)

compileSdk Which API surface you compile against Latest stable

Resources and qualifiers. res/values/strings.xml and res/values-hi/strings.xml hold the same keys; the system picks by device configuration. The same mechanism selects night colours (values-night) and width-specific layouts (layout-w600dp). In a View app this mechanism does much of the work that code does in Compose.

Variants. Build types (debug, release) differ in how the app is built. Flavours (dev, prod) differ in what is built.

End-to-end flow: from ./gradlew assembleRelease to a phone

  1. Annotation processors (Hilt, Room) generate Java sources. javac compiles everything.
  2. AAPT2 compiles resources and generates R and the View Binding classes. Manifests from all modules merge.
  3. R8 shrinks, optimises, renames and converts to DEX.
  4. The output is packaged as an APK or an AAB (the upload format for Google Play).
  5. The package is signed. The certificate is the app's permanent identity.
  6. On install, the package manager verifies the signature, assigns a UID and records components and permissions.

Failure modes

  • Release-only crashes. R8 removed or renamed a class reached by reflection: JSON models, some SDKs. Add keep rules and always test the release variant.
  • Manifest merge surprises. A library adds a permission or an exported component. Read the merged manifest.
  • Dependency conflicts. Use BOMs and ./gradlew :app:dependencies.
  • Slow builds. Annotation processors that are not incremental, and one giant module.

Trade-offs and when not to use it

Flavours multiply quickly. Use one only for something that must differ at build time; put the rest behind runtime configuration. Convention plugins are worth it past about five modules.

Production and security

Anything in BuildConfig or strings.xml ships inside the APK and is readable with a zip tool. Keep signing keys in CI secrets. Enable dependency verification so a build maps to known artifacts, which SOC 2 reviewers will ask about.

Components and intents

The four entry points the system can start, and the messages that connect them.

Why it exists

Since the system starts and stops your process, it needs named entry points it can instantiate for a purpose: show a screen, do background work, react to an event, share data. Those are the four components. The Intent lets one app ask another to do something without linking against it.

Mental model

Components are doors into your app. The manifest is the list of doors. An intent is a note pushed under a door, and exported decides whether strangers may push notes.

Mechanics

Component Purpose Started by
Activity A window with UI The user, another app, a notification
Service Work with no UI that the user is aware of Your app, or a bound client
BroadcastReceiver React to an event The system or apps
ContentProvider Expose structured data to other apps A ContentResolver query

static void notifyPaymentReceived(Context context, String txId, String title, String body) {
    var manager = NotificationManagerCompat.from(context);

}

A PendingIntent is an intent wrapped with your identity for someone else to fire later. Use FLAG_IMMUTABLE unless a platform feature must fill in fields.

End-to-end flow: "Pay with Kosh" from a merchant app

  1. The merchant app fires an implicit intent with a payment URI.
  2. system_server matches it against installed apps' intent filters and finds Kosh's exported payment activity.
  3. If Kosh is not running, Zygote forks it.
  4. Kosh's activity receives the intent in onCreate() and treats every field as untrusted.
  5. The user approves. Kosh calls setResult(RESULT_OK, data) and finishes.
  6. The merchant's result callback fires.

Failure modes

  • Exported by accident. Components with an intent filter must declare android:exported (Android 12 and later). An exported activity that trusts its extras is an injection point.
  • Background starts. Apps cannot start activities from the background. A notification is the sanctioned route.
  • No handler. An implicit intent with no match throws ActivityNotFoundException. Package visibility rules may require a <queries> element.
  • Receivers without a flag. Runtime-registered receivers need RECEIVER_EXPORTED or RECEIVER_NOT_EXPORTED when targeting Android 14 or later.

Trade-offs and when not to use it

Modern apps use one activity hosting fragments (chapter 9). Extra activities are for separate entry points such as a payment handler. A Service is rarely the right tool for background work; chapter 17 uses WorkManager.

Production and security

Audit the merged manifest for every exported="true". For each, write down who may call it and what it validates. Never put secrets in extras sent to other apps.

Lifecycle, process death and state

Why screens are destroyed and rebuilt, and how to keep what the user typed.

Why it exists

The system reclaims memory by destroying things, and it rebuilds a screen on configuration change (rotation, language, dark mode, window resize) so the right resources load. Early Android said "save state yourself in a Bundle", which produced a decade of lost form data. ViewModel, LiveData and SavedStateHandle exist to make correct behaviour the easy path.

Mental model

Three lifetimes. Views are short. The ViewModel outlives rotation. Saved state outlives the process. Put each piece of state in the shortest lifetime that is still long enough.

Mechanics

Callback Meaning Typical use
onCreate Instance is being built Inflate, wire dependencies
onStart / onStop Visible / not visible Start and stop observing
onResume / onPause In focus / losing focus Camera, sensors
onDestroy Going away, perhaps to be recreated Rarely anything
Where state lives Survives rotation Survives process death Use for
A field in an Activity or Fragment No No Almost nothing
View state (text in an EditText with an id) Yes Yes Saved automatically for views that have ids
ViewModel field Yes No Screen state, in-flight work
SavedStateHandle Yes Yes IDs and user input needed to rebuild
Disk (Room, DataStore) Yes Yes Anything the user would be upset to lose 
@HiltViewModel
public class TransferViewModel extends ViewModel {
    private final SavedStateHandle saved;

    @Inject TransferViewModel(SavedStateHandle saved) { this.saved = saved; }

    /** Survives process death: small and serialisable. */
    public LiveData<String> amountText() { return saved.getLiveData("amount", ""); }

    public void onAmountChange(String text) { saved.set("amount", text); }
}

@AndroidEntryPoint
public class TransferFragment extends Fragment {
    private FragmentTransferBinding binding;
    private TransferViewModel vm;

    @Override public View onCreateView(@NonNull LayoutInflater inflater, ViewGroup parent, Bundle state) {
        binding = FragmentTransferBinding.inflate(inflater, parent, false);
        return binding.getRoot();
    }

    @Override public void onViewCreated(@NonNull View view, Bundle state) {
        vm = new ViewModelProvider(this).get(TransferViewModel.class);

        // getViewLifecycleOwner(): the observer is removed when the view is destroyed
        vm.amountText().observe(getViewLifecycleOwner(), text -> {
            if (!text.contentEquals(binding.amount.getText())) binding.amount.setText(text);
        });
        binding.amount.addTextChangedListener(new SimpleTextWatcher(s -> vm.onAmountChange(s.toString())));
    }

    @Override public void onDestroyView() { super.onDestroyView(); binding = null; }   // release the views
}

LiveData delivers only while the observer's lifecycle is at least started, and always on the main thread.

End-to-end flow: the user leaves mid-transfer

  1. The user types ₹2,500, then switches apps. Kosh gets onPause, then onStop.
  2. The system serialises saved state into a Bundle held by system_server.
  3. Memory runs low. The Kosh process is killed with no callback.
  4. The user returns. A new process forks; the activity and fragment are recreated with the saved Bundle.
  5. A new TransferViewModel reads amount from its SavedStateHandle. The field shows ₹2,500.
  6. The recent payees list was in memory only, so the ViewModel reloads it.

Failure modes

  • Never tested. Developers' phones have spare memory. Force it: background the app, run adb shell am kill com.kosh.app, return.
  • Touching the binding after onDestroyView. A callback arrives late and dereferences a null binding. Observe with the view lifecycle owner.
  • Observing with this in a fragment. Observers pile up each time the view is recreated.
  • Huge saved state. TransactionTooLargeException on the way to the background.
  • Leaking the activity. A ViewModel or singleton holding a Context, View or fragment.

Trade-offs and when not to use it

android:configChanges lets you handle rotation yourself and skip recreation. It hides bugs that process death still exposes. Android 17 also stops restarting activities for a few configuration changes that need no redraw, such as keyboard changes. Not everything belongs in saved state: restoring a half-entered one-time password after an hour is worse than clearing it.

Production and security

Saved state may be written to disk by the system. Keep card numbers and tokens out of it. Set FLAG_SECURE on sensitive windows so Recents thumbnails and screenshots are blank, and set android:saveEnabled="false" on sensitive input fields.

The View system

A tree of stateful objects, and the pipeline that turns it into frames.

Why it exists

Android's UI toolkit since 2008 is an object tree: View objects, usually described in XML, mutated by code. For a Java app it is the toolkit, and it remains fully supported. Understanding how it produces a frame is what separates a smooth app from one that stutters.

Mental model

A screen is a tree of stateful objects. You find a node and change it. Keeping the tree consistent with your data is your job, so do it in exactly one place per screen.

Mechanics

<!-- res/layout/fragment_balance.xml -->

How a frame is produced

  1. Measure. Parents pass constraints down; children report sizes up.
  2. Layout. Parents position children.
  3. Draw. Each view records drawing commands into a display list.
  4. The RenderThread replays display lists on the GPU. SurfaceFlinger composites.

All of it must fit in one frame: 16.6 ms at 60 Hz, 8.3 ms at 120 Hz. requestLayout() reruns steps 1 to 3 for part of the tree. invalidate() reruns only draw.

One render function per screen

The discipline that prevents most View bugs: a single method that takes the whole screen state and sets every widget.

public class BudgetRingView extends View {
    private final Paint track = new Paint(Paint.ANTI_ALIAS_FLAG);
    private final Paint arc = new Paint(Paint.ANTI_ALIAS_FLAG);
    private final RectF bounds = new RectF();
    private float fraction;

    public BudgetRingView(Context context, @Nullable AttributeSet attrs) {
        super(context, attrs);
        float stroke = 10 * getResources().getDisplayMetrics().density;
        for (Paint p : new Paint[]{track, arc}) { p.setStyle(Paint.Style.STROKE); p.setStrokeWidth(stroke); }
        arc.setStrokeCap(Paint.Cap.ROUND);
        track.setColor(MaterialColors.getColor(this, com.google.android.material.R.attr.colorSurfaceVariant));
        arc.setColor(MaterialColors.getColor(this, androidx.appcompat.R.attr.colorPrimary));
    }

    public void setFraction(float value) {
        fraction = Math.max(0f, Math.min(1f, value));
        invalidate();                                   // draw only: size did not change
    }

    @Override protected void onSizeChanged(int w, int h, int oldW, int oldH) {
        float inset = arc.getStrokeWidth() / 2f;
        bounds.set(inset, inset, w - inset, h - inset);
    }

    @Override protected void onDraw(@NonNull Canvas canvas) {     // no allocation here: it runs every frame
        canvas.drawArc(bounds, 0, 360, false, track);
        canvas.drawArc(bounds, -90, 360 * fraction, false, arc);
    }
}

End-to-end flow: a tap on Refresh

  1. The touch arrives on the main thread and is dispatched down the tree to the Button.
  2. The click listener calls viewModel.refresh().
  3. The ViewModel posts a new state. The observer calls render(state).
  4. setText makes the TextView call requestLayout().
  5. On the next vsync the Choreographer runs measure, layout and draw for the dirty subtree.

Failure modes

  • State in two places. One code path updates the balance and forgets the timestamp. A single render method removes this class of bug.
  • Wrong thread. Touching a view off the main thread throws CalledFromWrongThreadException.
  • Deep or weighted hierarchies. Nested LinearLayout weights measure children twice per level.
  • Allocation in onDraw. Creating Paint or RectF per frame causes garbage collection pauses.
  • Leaks. A long-lived object holding a View holds its Activity.

Trade-offs and when not to use it

Views are verbose: a list needs an adapter, a holder and a diff callback. They are also stable, well documented, fast when used properly, and the only option in Java. If a screen would be dramatically simpler in Compose, the interoperability route is to write that one screen in Kotlin and host it in a ComposeView; the rest of the app can stay Java.

Production and security

WebView is a View and deserves caution: disable JavaScript unless needed, never attach a JavaScript bridge to untrusted content, and never use it for login (chapter 21).

Lists with RecyclerView

Ten thousand rows from a dozen views, and why the diff matters more than the adapter.

Why it exists

Creating one view per row for a long list exhausts memory and takes seconds. RecyclerView creates only as many row views as fit on screen, plus a few, and rebinds them with new data as the user scrolls.

Mental model

The adapter converts positions into bound views. The pool recycles views that scroll away. The diff tells the list what changed, so it can animate instead of redrawing everything.

Mechanics

public class TransactionAdapter extends ListAdapter<TransactionUi, TransactionAdapter.Holder> {

    public interface OnClick { void open(String id); }
    private final OnClick onClick;

    public TransactionAdapter(OnClick onClick) { super(DIFF); this.onClick = onClick; }

    static class Holder extends RecyclerView.ViewHolder {
        final RowTransactionBinding binding;
        Holder(RowTransactionBinding binding) { super(binding.getRoot()); this.binding = binding; }
    }

    @NonNull @Override public Holder onCreateViewHolder(@NonNull ViewGroup parent, int viewType) {
        var holder = new Holder(RowTransactionBinding.inflate(LayoutInflater.from(parent.getContext()), parent, false));
        holder.itemView.setOnClickListener(v -> {                       // set once, not on every bind
            int position = holder.getBindingAdapterPosition();
            if (position != RecyclerView.NO_POSITION) onClick.open(getItem(position).id());
        });
        return holder;
    }

    @Override public void onBindViewHolder(@NonNull Holder holder, int position) {
        TransactionUi tx = getItem(position);
        holder.binding.counterparty.setText(tx.counterparty());
        holder.binding.when.setText(tx.whenLabel());
        holder.binding.amount.setText(tx.amountLabel());
    }

    private static final DiffUtil.ItemCallback<TransactionUi> DIFF = new DiffUtil.ItemCallback<>() {
        @Override public boolean areItemsTheSame(@NonNull TransactionUi a, @NonNull TransactionUi b) {
            return a.id().equals(b.id());                               // identity
        }
        @Override public boolean areContentsTheSame(@NonNull TransactionUi a, @NonNull TransactionUi b) {
            return a.equals(b);                                         // records compare by value
        }
    };
}

Very large lists. The Paging library loads pages from Room or the network and exposes PagingData through LiveData or RxJava; PagingDataAdapter replaces ListAdapter.

End-to-end flow: a new transaction arrives

  1. The ViewModel posts a new list with one extra item at the top.
  2. submitList hands the old and new lists to DiffUtil on a background thread.
  3. The diff reports "one insert at position 0".
  4. Back on the main thread the adapter dispatches notifyItemInserted(0).
  5. The list animates existing rows down and binds one holder for the new row.

Failure modes

  • notifyDataSetChanged(). Rebinds everything, loses animations and scroll position. Use ListAdapter.
  • Mutating the submitted list. submitList with the same list instance does nothing. Always submit a new immutable list.
  • Work in onBindViewHolder. Formatting dates or loading images synchronously while scrolling. Format in the ViewModel; load images with a library such as Glide or Coil.
  • Stale positions in listeners. Capturing position from bind time. Ask the holder for its current position, as above.
  • Nested scrolling. A RecyclerView inside a ScrollView measures every row and defeats recycling. Use one list with multiple view types.

Trade-offs and when not to use it

For five static rows, a LinearLayout with inflated children is simpler. For everything dynamic, use RecyclerView. ListView is legacy.

Production and security

Rows are reused: a row that showed one user's data is rebound for another item. Always set every field in bind, including clearing images and visibility, or data bleeds between rows.

Fragments and navigation

One activity, many screens, and a graph that describes how they connect.

Why it exists

One activity per screen made sharing data and animating between screens awkward. Fragments are screens that live inside one activity. The Navigation component adds a declared graph of destinations, a back stack, typed arguments and deep links, so you stop writing fragment transactions by hand.

Mental model

The activity is a frame. Fragments are the pictures in it. The navigation graph is the map of which picture can follow which.

A fragment has two lifecycles: its own, and its view's. On the back stack the fragment object survives while its view is destroyed. Almost every fragment bug comes from mixing these up.

End-to-end flow: open a transaction, rotate, go back

  2. NavController pushes detail on the back stack. HomeFragment's view is destroyed; the fragment object stays.
  3. DetailFragment is created. Its ViewModel reads txId and loads.

  • Fragments talking to each other directly. Use shared ViewModels or fragment results.

Trade-offs and when not to use it

The Navigation component is the right default for a fragment-based app. Hand-written fragment transactions suit very small apps. Navigation 3, the newer library, is built for Compose and is unavailable to Java UI code. Fragments themselves have a deserved reputation for lifecycle complexity; the rules above contain it.

Production and security

Deep links land users on inner screens with a synthetic back stack. Every destination must check authentication itself. Validate arguments like any external input.

MVC on Android

The first pattern everyone reaches for, how to do it properly, and exactly where it gives way.

Why it exists

Model-View-Controller comes from Smalltalk in the 1970s. Its purpose is one idea: the code that knows the business rules should not know how it is displayed. Every later pattern refines that. Learn MVC first because the later patterns are answers to its specific failures on Android.

Mental model

The Model holds data and rules. The View draws and reports input. The Controller receives input, asks the Model to act, and tells the View what to show.

On Android the natural mapping is XML layout as View, plain Java classes as Model, and the Activity as Controller. The trouble is in that last mapping.

Mechanics

The feature for this whole part is Kosh's Send money screen: an amount, a payee, a Send button, a result.

/** Model: no Android imports. */
public class TransferModel {
    public interface Callback { void onResult(TransferResult result); }
    private final PaymentsApi api;

    public TransferModel(PaymentsApi api) { this.api = api; }

        return null;

    }

End-to-end flow: tapping Send

  1. The click listener in the activity runs.
  2. It reads the amount from the view and asks the model to validate.
  3. It mutates views to show progress and calls model.send.
  4. The network replies. The callback mutates views again.

Four steps, one file, easy to follow. That simplicity is real, and it is why MVC survives for small screens.

Failure modes

  • The massive activity. Lifecycle, permissions, navigation, view wiring and controller logic in one class of thousands of lines.
  • Rotation during step 3. The activity is destroyed and recreated. The callback holds the old instance: it leaks, and it updates views nobody sees. The new instance shows an idle form while a payment is in flight. The user taps Send again.
  • Process death. All progress and result state lived in view objects and is gone.
  • Untestable logic when the controller is the activity.
  • State scattered across widgets. "Is a transfer in progress?" is answered by progress.getVisibility().

The second and fifth items are what the next patterns remove.

Trade-offs and when not to use it

Use MVC when Move on when
A settings toggle, an about page, a prototype The screen starts asynchronous work

A small change in a legacy app You need unit tests on screen logic

MVC is not wrong. Its Model separation is permanent. What changes next is who stands between the model and the screen, and how long that object lives.

Production and security

Validation in the model is a usability feature, never a control. The server must validate amount, balance and limits again.

From MVP to MVVM to MVI

The same screen three more ways. Each step removes one failure of the step before.

Why it exists

Chapter 11 left two problems: logic bound to a short-lived activity, and state scattered across widgets. MVP solves testability. MVVM solves lifetime. MVI solves scattered state.

Mental model

MVP: the presenter commands the view. MVVM: the view observes state. MVI: the view observes one state and sends one kind of message.

Mechanics

MVP

@HiltViewModel

        state.setValue(current().asSending());

                .observeOn(AndroidSchedulers.mainThread())
                .subscribe(this::onResult,
                           error -> state.setValue(current().withError("Something went wrong"))));
    }

    private void onResult(TransferResult result) {
        if (!(result instanceof TransferResult.NetworkError)) pendingKey = null;   // an unknown outcome is retried with the same key
        state.setValue(current().withResult(result));
    }

    private TransferUiState current() { return Objects.requireNonNull(state.getValue()); }

    @Override protected void onCleared() { work.clear(); }           // cancel when the screen is gone for good
}

MVI

All input is one sealed type. All state changes go through one pure function.

public sealed interface TransferEvent {
    record AmountChanged(String text) implements TransferEvent {}
    record SendClicked() implements TransferEvent {}
    record Completed(TransferResult result) implements TransferEvent {}
}

public final class TransferReducer {
    public static TransferUiState reduce(TransferUiState s, TransferEvent e) {
        if (e instanceof TransferEvent.AmountChanged a) return s.withAmount(a.text());
        if (e instanceof TransferEvent.SendClicked) return s.sending() ? s : s.asSending();
        if (e instanceof TransferEvent.Completed c) return s.withResult(c.result());
        return s;
    }
}

public void onEvent(TransferEvent event) {                           // in the ViewModel
    TransferUiState before = current();
    state.setValue(TransferReducer.reduce(before, event));
    if (event instanceof TransferEvent.SendClicked && !before.sending()) {
        work.add(sendMoney.execute(payeeId, before.amount(), UUID.randomUUID().toString())
                .observeOn(AndroidSchedulers.mainThread())
                .subscribe(r -> onEvent(new TransferEvent.Completed(r)),
                           t -> onEvent(new TransferEvent.Completed(new TransferResult.NetworkError()))));
    }
}

End-to-end flow: tapping Send under MVVM, with a rotation

  1. The fragment calls onSend. The ViewModel sets sending = true and subscribes to the use case.
  2. LiveData notifies the observer. render disables the button and shows progress.
  3. The user rotates. Activity, fragment and views are destroyed. The ViewModel and its subscription are not.
  4. The new fragment observes state() and at once renders sending = true.
  5. The use case completes. State becomes a result. The receipt appears.

Failure modes

  • Many small LiveData fields. Eight separate observables can show loading and error together. Prefer one state object.
  • Events replayed. A navigation value in plain LiveData fires again after rotation. Use the Event wrapper.
  • setValue from a background thread. It throws. Use postValue, or switch to the main thread first as above.
  • Android types in the ViewModel. A Context, View or fragment leaks and blocks JVM tests.
  • Fat ViewModels. Business rules migrate in because it is convenient. Chapter 13 gives them a home.
  • Mutable state objects. A state class with setters lets two threads change it mid-render. Records are immutable.

Trade-offs and when not to use it

The default in this book is MVVM with one immutable state object. Use full MVI where the screen is a real state machine and illegal states cost money: payment flows, onboarding with branching. Java's lack of copy() makes the withX methods tedious; accept that, or generate them with a library such as AutoValue or Immutables. MVP remains reasonable in existing codebases and is not worth choosing for new screens.

Production and security

A reducer gives an audit trail: log event names and state transitions, never amounts, account numbers or tokens. Double-submit protection belongs in the state machine and again on the server through idempotency keys (chapter 16).

Why it exists

Mental model

Threads, executors and RxJava

Asynchronous work in Java: keeping the main thread free, cancelling with the screen, and composing calls.

Why it exists

The main thread must never block, and almost everything useful blocks. Java on Android has no coroutines and no virtual threads. The tools are: executors for running work elsewhere, LiveData for delivering state to the UI, and RxJava for composing, transforming and cancelling asynchronous streams. Room, Retrofit, DataStore and WorkManager all offer RxJava bindings, which is why this book uses it for the data layer.

Mental model

Three questions for every asynchronous call: which thread does the work, which thread gets the result, and who cancels it when the screen goes away.

Mechanics

Level 1: executors and a handler

public final class AppExecutors {
    public final Executor io = Executors.newFixedThreadPool(4);
    public final Executor main = new Handler(Looper.getMainLooper())::post;
}

executors.io.execute(() -> {
    List<Payee> payees = dao.loadPayeesBlocking();
    executors.main.execute(() -> render(payees));           // crashes if the view is gone: nothing cancels this
});

Enough for one fire-and-forget call. It has no cancellation, no error channel and no composition.

Level 2: RxJava 3

Type Emits Use for
Single<T> One value or an error A network call, one query
Completable Success or an error A write
Maybe<T> Zero or one value A lookup that may find nothing
Flowable<T> Many values over time, with backpressure A Room query that updates, a socket 
public class DefaultPaymentsRepository implements PaymentsRepository {
    private final PaymentsApi api;
    private final TransactionDao dao;

    @Inject DefaultPaymentsRepository(PaymentsApi api, TransactionDao dao) { this.api = api; this.dao = dao; }

    @Override public Single<TransferResult> transfer(String payeeId, Money amount, String idempotencyKey) {
        return api.transfer(idempotencyKey, new TransferRequest(payeeId, amount.minor()))    // the caller owns the key
                .flatMap(dto -> dao.upsert(List.of(TransactionMappers.fromTransfer(dto, payeeId, amount)))   // then save
                        .toSingleDefault((TransferResult) new TransferResult.Success(dto.reference)))
                .onErrorReturn(e -> e instanceof IOException
                        ? new TransferResult.NetworkError() : new TransferResult.Declined("Try again"))
                .subscribeOn(Schedulers.io());              // main-safe: callers need not think about threads
    }
}
  • subscribeOn chooses where the work runs. observeOn chooses where results are delivered from that point on.
  • Nothing happens until subscribe. It returns a Disposable; disposing it cancels the work.
  • A ViewModel collects its disposables in a CompositeDisposable and clears it in onCleared().

End-to-end flow: a transfer, with the user leaving

  1. onSend subscribes. subscribeOn(Schedulers.io()) moves the HTTP call to an I/O thread.
  2. The main thread stays free to draw.
  3. The response arrives; flatMap writes it to Room on the same background thread.
  4. observeOn(mainThread()) hops back. state.setValue runs on the main thread.
  5. If the ViewModel had been cleared, work.clear() would dispose the chain at step 2 and abort the HTTP call.

Step 5 is right for loading a list and wrong for a payment. Chapter 17 moves the transfer to WorkManager so it outlives the screen.

Failure modes

  • Forgetting to dispose. The chain holds its lambdas, which hold the ViewModel or fragment. Leaks, and callbacks into dead screens.
  • No error handler. subscribe(onSuccess) with no onError crashes the app with OnErrorNotImplementedException.
  • Undeliverable errors. An error arriving after disposal goes to the global handler, which crashes by default. Install RxJavaPlugins.setErrorHandler and log expected I/O errors there.
  • subscribeOn in the wrong place, twice. Only the first subscribeOn counts. Apply it once, in the repository.
  • Blocking calls. blockingGet() on the main thread is an ANR.
  • Operator soup. Ten chained operators nobody can read. Keep chains short and name intermediate methods.

Trade-offs and when not to use it

RxJava is powerful and has a steep learning curve; it is in maintenance rather than active growth, and new Android APIs appear as coroutines first. For a small app, executors plus LiveData and Retrofit's Call.enqueue are enough. ListenableFuture (Guava) is what some Jetpack APIs return in Java; it composes poorly, so convert at the edge. If the asynchronous code is where the team suffers most, that is the strongest single argument for moving the data layer to Kotlin.

Production and security

Decide per boundary which failures are data and which are crashes: repositories convert expected failures into result types; unexpected ones reach the crash reporter. Never log exception messages from payment calls without checking what they contain.

Local persistence with Room and DataStore

A database and a settings store that the rest of the app can observe.

Why it exists

Memory is temporary and the network is unreliable. The disk is the only place state reliably survives. Raw SQLite means hand-written SQL strings and cursors with no compile-time checks. SharedPreferences did disk I/O on the main thread. Room and DataStore replace them.

Mental model

The database is the app's single source of truth. Screens observe queries. Whoever changes a row, every observer of a query that reads it is told.

Mechanics

Which Room

Room 2.x generates Java, runs as a Java annotation processor, and is what this chapter uses. It is in maintenance mode. Room 3.0 generates only Kotlin and requires KSP and the Kotlin compiler even when your own code is Java, and its DAO methods are coroutine-based or reactive. For a Java app that means one of two paths: stay on Room 2.x, or isolate the database in a single module that applies the Kotlin plugin and exposes Java-friendly reactive types. Chapter 24 shows that module boundary.

End-to-end flow: a new transaction appears on screen

  1. A sync calls dao.upsert(...).
  2. Room's invalidation tracker sees the transactions table changed.
  3. The observeRecent Flowable reruns its query on a background thread and emits.
  4. The repository maps entities to domain models; the ViewModel maps to UI models and posts LiveData.
  5. ListAdapter diffs and inserts one row.

No code anywhere says "refresh the list".

Failure modes

  • Destructive migration in production. fallbackToDestructiveMigration() wipes user data when a migration is missing.
  • Untested migrations. Users skip versions. Export schemas and test with MigrationTestHelper.
  • Unbounded growth. A cache nobody prunes.
  • N+1 queries. One query per row. Use a join or @Relation.
  • Two DataStore instances for one file. Throws at runtime.
  • Timestamps in local time. Store UTC instants; format in the UI.

Trade-offs and when not to use it

Room is the default for relational data. Use DataStore for a handful of settings, plain files for documents, and no persistence at all for data you must not keep, such as a full card number. Weigh the Room 2 versus Room 3 decision now, since it shapes your module structure.

Production and security

App-private storage is protected by the sandbox and file-based encryption. For a higher bar, encrypt sensitive columns with a Keystore-held key (chapter 21) or use SQLCipher. Exclude databases holding personal data from cloud backup with dataExtractionRules. PCI DSS scope grows the moment a card number touches this database, so do not store it.

Why it exists

A phone calls from a train entering a tunnel, behind a captive portal, switching from Wi-Fi to mobile data. Mental model

Every call has three outcomes, not two: success, a response that says no, and no response at all. The third is the one that matters for money.

Errors as types

public sealed interface ApiResult<T> {
    record Ok<T>(T value) implements ApiResult<T> {}
    record Rejected<T>(int code, @Nullable String reason) implements ApiResult<T> {    // the server said no
        /** Only a definitive 4xx is a verdict. 401, 408, 429 and every 5xx may succeed later with the same key. */
        public boolean isFinal() { return code >= 400 && code < 500 && code != 401 && code != 408 && code != 429; }
    }
    record Unreachable<T>() implements ApiResult<T> {}                                 // never got an answer
    record Unknown<T>() implements ApiResult<T> {}                                     // sent, outcome not known

    static <T> Single<ApiResult<T>> from(Single<T> call) {
        return call.<ApiResult<T>>map(Ok::new).onErrorReturn(e -> {
            if (e instanceof HttpException h) return new Rejected<>(h.code(), h.message());
            if (e instanceof UnknownHostException || e instanceof ConnectException) return new Unreachable<>();   // nothing was sent
            if (e instanceof IOException) return new Unknown<>();    // timeouts, resets, a cut-off response: it may have arrived
            throw Exceptions.propagate(e);                  // a bug: let it crash
        });
    }
}

Interceptors

public class BearerInterceptor implements Interceptor {
    private final SessionStore session;
    @Inject BearerInterceptor(SessionStore session) { this.session = session; }

    @NonNull @Override public Response intercept(@NonNull Chain chain) throws IOException {
        Request request = chain.request();
        String token = session.cachedAccessToken();
        if (token == null || !request.url().host().equals("api.kosh.example")) return chain.proceed(request);
        return chain.proceed(request.newBuilder().header("Authorization", "Bearer " + token).build());
    }
}

Idempotency

A timeout on POST /transfers does not tell you whether the money moved. The client generates a unique key per user intent, stores it before sending, and sends the same key on every retry. The server returns the original result for a repeated key. Without this, a retry is a second payment.

End-to-end flow: one GET

  1. The repository subscribes. Retrofit builds an OkHttp Request.
  2. Application interceptors add the Authorization header, a request id and the app version.
  3. OkHttp reuses a pooled HTTP/2 connection, or does DNS, TCP and TLS.
  4. The response returns through the interceptors. A 401 triggers the authenticator (chapter 18).
  5. Moshi decodes JSON into DTOs on a background thread.
  6. The Single emits. The repository writes to Room; the UI updates from the database.

Failure modes

  • Treating a timeout as a failure. The user is told "payment failed" and pays again. Unknown needs its own screen.
  • Automatic retry of a POST. Safe only with an idempotency key.
  • R8 and reflection-based JSON. DTO fields are renamed in release builds and parse as null. Add keep rules or use Moshi's code generation.
  • Cleartext HTTP. Blocked by default since Android 9.
  • Captive portals. Every call returns an HTML login page; a JSON parse error is the symptom.
  • Logging interceptors in release. Bodies, tokens and account numbers end up in logs.

Trade-offs and when not to use it

Retrofit with OkHttp is the conservative choice with the best tooling. Without RxJava, use Call<T>.enqueue with callbacks. GraphQL suits screens that aggregate many resources. gRPC suits internal streaming APIs (chapter 19).

Production and security

Send app version, platform, a request id and a W3C traceparent on every call. Redact logs at the interceptor. For PCI DSS, let the payment provider's SDK collect and tokenise card numbers so they never appear in your own API calls.

  • Lab. Build a release variant and confirm your DTOs still parse.
  • Challenge. Write user-facing copy for Rejected, Unreachable and Unknown on a payment. Three different messages.

Offline-first and background sync

Read from the database, write through an outbox, and let the system choose when to talk to the server.

Why it exists

Mobile connectivity is intermittent and the process can die at any moment. An app that reads straight from the network shows spinners in lifts and loses writes when the user leaves. Offline-first design decouples the UI from the network.

Mental model

Reads come from the database. Writes go into the database first, as intentions. A worker moves intentions to the server and brings truth back.

Mechanics

WorkManager

@HiltWorker
public class OutboxWorker extends Worker {
    private final OutboxDao outbox; private final PaymentsApi api;

    @AssistedInject OutboxWorker(@Assisted @NonNull Context context, @Assisted @NonNull WorkerParameters params,
                                 OutboxDao outbox, PaymentsApi api) {
        super(context, params); this.outbox = outbox; this.api = api;
    }

    @NonNull @Override public Result doWork() {                  // already on a background thread
        for (OutboxEntity item : outbox.queuedBlocking()) {
            ApiResult<TransferDto> r = ApiResult.from(api.transfer(item.idempotencyKey,
                    new TransferRequest(item.payeeId, item.amountMinor))).blockingGet();

            if (r instanceof ApiResult.Ok<TransferDto> ok) outbox.markConfirmedBlocking(item.idempotencyKey, ok.value().reference);
            else if (r instanceof ApiResult.Rejected<TransferDto> no && no.isFinal())    // the server refused this transfer
                outbox.markFailedBlocking(item.idempotencyKey, no.reason());
            else return Result.retry();                          // 401, 408, 429, 5xx, unreachable or unknown: same key, later
        }
        return Result.success();
    }

    /** Expedited work runs as a foreground service before Android 12, so it must supply a notification. */
    @NonNull @Override public ForegroundInfo getForegroundInfo() { return syncForegroundInfo(getApplicationContext()); }
}

    Notification n = new NotificationCompat.Builder(context, "sync")           // the channel is created at app start
            .setSmallIcon(R.drawable.ic_stat_kosh).setContentTitle("Finishing your transfer").setOngoing(true).build();

}

    PeriodicWorkRequest request = new PeriodicWorkRequest.Builder(SyncWorker.class, 6, TimeUnit.HOURS)

}

A blocking Worker is the simplest form in Java, and blockingGet() is correct here because WorkManager already runs it on a background thread. RxWorker is the alternative when the work is naturally a chain.

End-to-end flow: sending money in a lift

  1. The user confirms. One transaction writes the outbox row and a pending transaction.
  2. The home query emits; the payment appears as "Sending".
  3. enqueueOutbox schedules the worker. No network, so it waits.
  4. The user closes the app. The process dies.
  5. Connectivity returns. The system starts the Kosh process and runs OutboxWorker.
  6. The call succeeds. The outbox row is confirmed and the posted transaction is upserted.
  7. A notification tells the user. If the app is open, the row changes through the same database flow.

Failure modes

  • Duplicate submission. The worker runs twice or a response is lost. The idempotency key makes it harmless.
  • Optimistic lies. Showing the balance reduced before the server agrees. Show the pending item and the last confirmed balance with its time.
  • Sync storms. A million devices syncing on the hour. Add jitter; let push trigger sync.
  • Conflicts. Choose a rule per data type: server wins for money, last write wins for labels.
  • Stale forever. Show "Updated 2 hours ago" whenever data may be old.
  • Expecting exact timing. Periodic work has a 15-minute minimum and the system defers it.

Trade-offs and when not to use it

Offline-first roughly doubles the data layer. It is worth it for content the user revisits and writes they must not lose. It is wrong for data that must be live to mean anything: an FX quote, an OTP, a card authorisation. Call the network directly for those and cache nothing.

Production and security

Queued payment intentions are sensitive. Expire outbox rows after a short window, require fresh authentication for anything queued beyond it, and make the server reject stale keys. Monitor outbox age and worker failure rate.

Tokens: refresh once, not five times

public class TokenAuthenticator implements Authenticator {
    private final SessionStore session;
    @Inject TokenAuthenticator(SessionStore session) { this.session = session; }

    @Nullable @Override
    public Request authenticate(@Nullable Route route, @NonNull Response response) {
        if (response.request().header("X-Retry-Auth") != null) return null;        // already retried: give up
        String header = response.request().header("Authorization");
        String failed = header == null ? null : header.replace("Bearer ", "");

        String fresh;
        synchronized (this) {                                   // OkHttp calls this on a background thread
            String current = session.cachedAccessToken();
            fresh = (current != null && !current.equals(failed))
                    ? current                                   // another call already refreshed
                    : session.refreshBlocking();                // null means logged out
        }
        if (fresh == null) return null;
        return response.request().newBuilder()
                .header("Authorization", "Bearer " + fresh).header("X-Retry-Auth", "1").build();
    }
}

When an access token expires, five parallel calls get 401 together. The lock lets the first refresh and the other four reuse its result.

Retry with backoff and jitter

static <T> SingleTransformer<T, T> retryOnIo(int attempts, long baseMs) {
    return upstream -> upstream.retryWhen(errors -> errors.zipWith(Flowable.range(1, attempts), (error, attempt) -> {
        if (!(error instanceof IOException) || attempt == attempts) throw Exceptions.propagate(error);
        return attempt;
    }).flatMap(attempt -> {
        long ceiling = Math.min(baseMs << attempt, 5_000);
        return Flowable.timer(ThreadLocalRandom.current().nextLong(ceiling / 2, ceiling + 1), TimeUnit.MILLISECONDS);
    }));
}

End-to-end flow: opening the dashboard with an expired token

  1. Four requests leave in parallel with the old access token.
  2. Banking returns 401 to two of them. The authenticator runs for the first and takes the lock.
  3. It calls the identity provider's token endpoint and stores the new pair.
  4. The second call acquires the lock, sees a newer token and reuses it.
  5. Both requests are retried once and succeed.
  6. Market data times out at two seconds. The rates card shows "Rates unavailable"; the balance is already on screen.

Failure modes

  • Refresh stampede. No lock, five refresh calls, and a provider that rotates refresh tokens invalidates four. Users are logged out at random.
  • Credentials sent to the wrong host. One global interceptor adds the bearer token to the image CDN and the analytics vendor. Scope interceptors per client and check the host.
  • All-or-nothing screens. One optional call fails and the dashboard shows an error.
  • Chatty startup. Twelve sequential calls before first paint on 3G.
  • Version skew. The app released eighteen months ago is still calling.

Trade-offs and when not to use it

A BFF is right when screens aggregate several services and you control the backend. A circuit breaker inside a phone sees one user's traffic; keep it simple or leave it to the gateway.

Production and security

Never ship a third-party secret in the app. Give each downstream an audience-restricted token. Propagate a trace id from the device so an incident can be followed from tap to ledger entry.

Realtime and push

Polling, streams and push notifications: which one keeps a balance current, and at what battery cost.

Why it exists

Users expect an incoming payment to appear without pulling to refresh. A phone cannot hold a socket open in the background: the OS freezes idle apps and the radio is a major battery drain. Android has two regimes. While the app is on screen, you may stream. When it is not, one shared system connection (Firebase Cloud Messaging on Google devices) wakes you.

Mental model

Foreground: hold a stream. Background: wait for a push. Either way the message is a hint to sync, and the database stays the source of truth.

Mechanics

Mechanism Direction Good for Cost
Polling Client pulls Simple, tolerant backends Wasted requests, delay
Server-sent events Server to client Feeds, status updates One-way only
WebSocket Both ways Chat, live prices Reconnect logic, stateful servers
gRPC streaming Both ways, typed Internal APIs with protobuf Tooling weight, proxy support
Push (FCM) Server to device Anything while the app is not running No delivery or ordering guarantee

A WebSocket as a Flowable

static Flowable<String> socket(OkHttpClient client, String url) {
    return Flowable.create(emitter -> {
        WebSocket ws = client.newWebSocket(new Request.Builder().url(url).build(), new WebSocketListener() {
            @Override public void onMessage(@NonNull WebSocket s, @NonNull String text) { emitter.onNext(text); }
            @Override public void onFailure(@NonNull WebSocket s, @NonNull Throwable t, Response r) { emitter.tryOnError(t); }
            @Override public void onClosed(@NonNull WebSocket s, int code, @NonNull String reason) { emitter.onComplete(); }
        });
        emitter.setCancellable(() -> ws.close(1000, null));        // subscriber gone: close the socket
    }, BackpressureStrategy.LATEST);                               // the UI only needs the newest tick
}

End-to-end flow: Asha pays you ₹500 while Kosh is closed

  1. The ledger posts the credit and publishes an event.
  2. A notification service sends an FCM data message {type: ACCOUNT_CHANGED, accountId}.
  3. Google Play services delivers it and starts the Kosh process.
  4. onMessageReceived enqueues an expedited sync and returns.
  5. The worker calls the banking API with the user's token and upserts into Room.
  6. The worker posts a notification built from fetched data: "₹500 received from Asha".
  7. If the app is open, the home query emits and the balance updates.

The push carried no amount and no name. Forging or replaying it reveals nothing.

Failure modes

  • Push as truth. Rendering the amount from the payload shows wrong data when messages arrive late, twice or out of order.
  • Gaps after reconnect. Resume from the last sequence number, or run a normal sync on every reconnect.
  • Sockets in the background. A foreground service kept alive only to hold a connection drains the battery and conflicts with platform policy.
  • Thundering herd. The server restarts and a million clients reconnect at once. Jitter the backoff.
  • Stale tokens. Not removing the token on logout sends one user's alerts to another person's phone.
  • Assuming delivery. Always sync on app open as well.

Trade-offs and when not to use it

Most apps need no socket. Push plus sync-on-open covers balances and transactions. Add a stream only for data that changes many times a minute while the user watches.

Production and security

Lock screens show notifications; offer a setting to hide amounts. Authenticate streams with a short-lived token. Rate-limit what one message can trigger.

  • Missing or wrong service type. A crash at startForeground() on Android 14 and later.

  • Oversized Binder payloads. Return an id or a file descriptor.

Most background work belongs in WorkManager. A foreground service is right only for work the user started and is watching. Cross-process AIDL is rare in application code.

Production and security

Identity and security

Who the user is, where secrets live on the device, and what a wallet must assume about the phone it runs on.

Why it exists

Every connection in this part carries a credential. On a phone the attacker may hold the device, the binary is public, and the user may have installed malware. Android provides hardware-backed keys, biometric gating, verified links and attestation so an app can still make trustworthy claims. These are all plain Java APIs.

Mental model

The app is a public client on a device you do not control. It can hold short-lived proof that a user authenticated. It can never hold a secret that belongs to you.

Mechanics

Threat Main defences
Lost or stolen unlocked phone Biometric or PIN before sensitive actions, short sessions
Malicious app on the device Sandbox, non-exported components, verified links
Network attacker TLS everywhere, optional certificate pinning
Reverse engineering No secrets in the binary, server-side enforcement
Rooted device, modified app Play Integrity attestation, server-side risk decisions

Sign-in. OAuth 2.0 authorization code flow with PKCE in a Custom Tab, through a library such as AppAuth (a Java library). No client secret in the app. Never an embedded WebView.

A token vault on Android Keystore

/** AES-256-GCM with a key that never leaves secure hardware. Layout: 12-byte IV, then ciphertext. */
public class TokenVault {
    private static final String ALIAS = "kosh_token_key";

    private SecretKey key() throws GeneralSecurityException, IOException {
        KeyStore store = KeyStore.getInstance("AndroidKeyStore");
        store.load(null);
        if (store.getKey(ALIAS, null) instanceof SecretKey existing) return existing;

        KeyGenerator generator = KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore");
        generator.init(new KeyGenParameterSpec.Builder(ALIAS,
                KeyProperties.PURPOSE_ENCRYPT | KeyProperties.PURPOSE_DECRYPT)
                .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
                .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
                .setKeySize(256).build());
        return generator.generateKey();
    }

    public byte[] seal(byte[] plain) throws GeneralSecurityException, IOException {
        Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
        cipher.init(Cipher.ENCRYPT_MODE, key());                    // the Keystore picks a fresh IV
        byte[] iv = cipher.getIV(), body = cipher.doFinal(plain);
        return ByteBuffer.allocate(iv.length + body.length).put(iv).put(body).array();
    }

    public byte[] open(byte[] sealed) throws GeneralSecurityException, IOException {
        Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
        cipher.init(Cipher.DECRYPT_MODE, key(), new GCMParameterSpec(128, sealed, 0, 12));
        return cipher.doFinal(sealed, 12, sealed.length - 12);      // throws if the data was altered
    }
}

Store the sealed refresh token in DataStore. The older EncryptedSharedPreferences library is deprecated.

End-to-end flow: a transfer above the step-up limit

  1. The user confirms ₹50,000. The server replies that step-up is required, with a challenge.
  2. The app builds the bytes to sign: challenge, payee, amount, idempotency key.
  3. BiometricPrompt appears. The user presents a fingerprint.
  4. Secure hardware releases the key for one operation and signs.
  5. The app sends the transfer with the signature and a Play Integrity token.
  6. The server verifies the signature and the verdict, then posts the transfer.

Failure modes

  • Pinning without an exit. The certificate rotates and every installed copy stops working. Ship a backup pin, an expiry and a tested rotation plan, or do not pin.
  • Secrets in BuildConfig. Extracted in minutes.
  • Tokens in logs, crash reports or backups.
  • Biometric as a UI gate only. Bind it to a key.
  • Keys lost on restore. Keystore keys do not migrate to a new phone. Design re-enrolment as a normal path.
  • Root detection as a guarantee. Client checks are bypassable; treat them as signals.
  • Overlay attacks. Set filterTouchesWhenObscured on sensitive controls and FLAG_SECURE on sensitive windows.

Trade-offs and when not to use it

Pinning protects against a compromised certificate authority and creates an outage risk you own; many teams pin only the most sensitive hosts. R8 obfuscation is not a control. Blocking rooted devices outright excludes legitimate users; a graded response is usually better.

Production and security

For PCI DSS, let a certified provider's SDK capture card data so the number never reaches your code. For SOC 2, show how signing keys are held, who can release, and how a vulnerable version is retired. Review against the OWASP MASVS before each major release.

Glass UI with Views

Translucent, blurred surfaces in the View system: how they are drawn, what they cost, and how to keep text readable.

Why it exists

Glass surfaces (frosted panels that let colour through from behind) give depth without heavy borders. They suit a navigation bar floating over a scrolling list, or a balance card over a gradient. They are also easy to get wrong: blur is one of the more expensive things a GPU does per frame, and text over an unpredictable background fails contrast checks. This chapter treats glass as an engineering feature with a budget.

Mental model

Glass is four layers: something colourful behind, a blur of it, a translucent tint, and a thin bright edge. Remove the first and you have a grey box.

Level 1: backdrop blur

A view that draws a blurred copy of whatever a sibling view shows beneath it:

/** Safe to inflate on every API level: RenderNode (API 29) and RenderEffect (API 31) are touched only inside the guard. */
public class BackdropBlurView extends View {
    @Nullable private RenderNode node;                 // created on first blur, never on old devices
    private final int[] mine = new int[2], theirs = new int[2];
    @Nullable private View source;
    private float radiusPx = 60f;
    @ColorInt private int tint = 0x8CFFFFFF;

    public BackdropBlurView(Context context, @Nullable AttributeSet attrs) { super(context, attrs); }

    /** The view to see through. It must be a sibling, never an ancestor, or drawing would recurse. */
    public void setSource(View source) { this.source = source; invalidate(); }
    public void setTint(@ColorInt int tint) { this.tint = tint; invalidate(); }

    @Override protected void onDraw(@NonNull Canvas canvas) {
        if (source != null && Build.VERSION.SDK_INT >= 31 && canvas.isHardwareAccelerated()) {
            if (node == null) node = new RenderNode("backdrop");
            node.setPosition(0, 0, getWidth(), getHeight());
            node.setRenderEffect(RenderEffect.createBlurEffect(radiusPx, radiusPx, Shader.TileMode.CLAMP));

            getLocationInWindow(mine); source.getLocationInWindow(theirs);
            RecordingCanvas recording = node.beginRecording();
            recording.translate(theirs[0] - mine[0], theirs[1] - mine[1]);     // line the copy up with the original
            source.draw(recording);
            node.endRecording();

            canvas.drawRenderNode(node);
        }
        canvas.drawColor(tint);                                                // tint always; blur when possible
    }
}

@RequiresApi(33)
static void addGrain(View view) {
    RuntimeShader grain = new RuntimeShader("""
            uniform shader content; uniform float amount;
            half4 main(float2 p) {
                half4 c = content.eval(p);
                float n = fract(sin(dot(p, float2(12.9898, 78.233))) * 43758.5453);
                return half4(c.rgb + (n - 0.5) * amount, c.a);

    view.setRenderEffect(RenderEffect.createRuntimeShaderEffect(grain, "content"));
}

A little noise hides gradient banding. Each shader runs per pixel per frame; keep them small.

Choosing a level at runtime

public enum GlassLevel { TINT, BLUR;
    public static GlassLevel current(Context context) {
        PowerManager power = context.getSystemService(PowerManager.class);
        boolean saving = power != null && power.isPowerSaveMode();
        return Build.VERSION.SDK_INT >= 31 && !saving ? BLUR : TINT;

End-to-end flow: one frame of a list scrolling under a glass bar

  1. The scroll offset changes. The list redraws, and the scroll listener invalidates the bar.
  2. The bar re-records the list into its RenderNode, because what is behind it changed.
  3. The GPU downsamples that region and applies a two-pass Gaussian blur.
  4. The tint is composited over the blurred pixels, then the border, then the bar's icons and labels.
  5. All of it must finish inside the frame budget from chapter 6, at 120 Hz on many phones.

Steps 2 and 3 repeat on every frame of the scroll. Cost grows with the blurred area and the radius.

Failure modes

  • Blurring the content instead of the backdrop. Unreadable text.
  • Unreadable text on busy backgrounds. The tint must guarantee contrast whatever scrolls underneath. Measure the worst case.
  • Jank on mid-range devices. A full-screen blur, several stacked glass layers, or an animated radius. Blur small regions and animate alpha instead.
  • Flat grey. Blur over a plain background looks like a dull rectangle. Glass needs colour behind it.
  • No fallback. Below Android 12 there is no RenderEffect. A design that depends on blur shows raw content under text.
  • Software canvases. Screenshots and some test renderers are not hardware accelerated; drawRenderNode then throws or draws nothing. Guard it, as above.

Trade-offs and when not to use it

Navigation bars and toolbars over scrolling content Tables, statements and dense numeric screens
A hero card over a controlled gradient Forms and error messages
Sheets and dialogs, through window blur Low-end devices you cannot test

In a wallet, the amount is the most important pixel on the screen. Put amounts on a strong tint or on solid colour. Decoration yields to legibility every time.

Production and security

Animation that explains what changed, at a cost you have measured.

Why it exists

A screen that jumps from one state to another makes the user work out what happened. Motion carries that information: this row became that detail screen, this payment went from sending to sent. Translucent layers that appear abruptly also look like rendering faults, so glass depends on it.

Mental model

Animate properties the GPU can change without layout (alpha, translation, scale, rotation). Describe layout changes as "before" and "after" and let the framework animate between them.

Modularisation

Splitting a large app so that teams, builds and boundaries scale together, with a place for Kotlin if you ever need one.

Why it exists

A single app module works until three things hurt at once: a one-line change rebuilds everything, any class can reach any other so layers erode, and teams collide in the same files. Gradle modules give compile-time walls.

Mental model

Modules are the architecture diagram, enforced by the compiler. If the diagram says UI must not touch the network client, make it impossible.

:feature:transfer

:core:domain              models, use cases, repository interfaces (pure Java library)
:core:data                repository implementations
:core:database            Room
:core:network             Retrofit clients
:core:security            Keystore, biometrics, integrity
:core:testing             fakes and test rules

Some libraries now need the Kotlin compiler even when your code is Java: Room 3, AppFunctions, a Compose screen, a Macrobenchmark module. Modules make that cheap. Put the library behind one module that applies the Kotlin plugin and exposes a Java-friendly interface:

End-to-end flow: changing one line in the transfer screen

  1. Gradle sees only :feature:transfer sources changed.
  2. It recompiles that module. Its public API did not change, so dependants are not recompiled.
  3. :app repackages.
  4. Other modules come from the build cache.

Failure modes

  • The common module. Everything depends on it and any change rebuilds the world.
  • Too many modules too early. Sixty modules for six screens.
  • Feature-to-feature shortcuts. One import now, a dependency cycle a year later.
  • Resource name clashes. Two modules define R.string.title. Use resourcePrefix per module.
  • Leaky api dependencies. A module exposes Retrofit types and the UI starts using them.

Trade-offs and when not to use it

Below roughly twenty screens and one team, packages inside one module plus discipline are cheaper. Introduce modules along existing seams: core layers first, then features.

Production and security

Module boundaries are review boundaries. Put Keystore, signing and integrity code in :core:security with restricted code owners.

public class RxSchedulersRule implements TestRule {
    @Override public Statement apply(Statement base, Description description) {
        return new Statement() {
            @Override public void evaluate() throws Throwable {
                RxJavaPlugins.setIoSchedulerHandler(s -> Schedulers.trampoline());
                RxAndroidPlugins.setMainThreadSchedulerHandler(s -> Schedulers.trampoline());
                try { base.evaluate(); } finally { RxJavaPlugins.reset(); RxAndroidPlugins.reset(); }
            }
        };
    }
}

Performance

Startup, smooth frames, memory and battery: what to measure and what actually moves the numbers.

Why it exists

Users judge an app in its first second and by whether scrolling stutters. Google Play measures too: apps with poor stability or responsiveness are shown less. Performance is mostly three budgets (time to first frame, time per frame, memory) on devices far slower than the one on your desk.

Mental model

Measure release builds on a mid-range device. Everything else is a guess.

Mechanics

Start What happens Target
Cold Process fork, Application.onCreate, first activity, first frame Under about a second on mid-range hardware
Warm Process alive, activity recreated Faster
Hot Activity brought to front Near instant
  • Baseline Profiles ship a list of hot classes and methods so ART compiles them ahead of time at install.
  • Do less in Application.onCreate. Every eager SDK adds to every start, including starts for a push message.
  • R8 shrinks and optimises; smaller DEX loads faster.

End-to-end flow: finding a slow start

  1. Android vitals shows slow cold starts on low-memory devices.
  2. Macrobenchmark on a comparable device reproduces it with numbers.
  3. A Perfetto trace shows 400 ms in Application.onCreate: three SDK initialisers and a synchronous preferences read.
  4. Two SDKs move to lazy initialisation and the read becomes asynchronous with a default.
  5. The Baseline Profile is regenerated. CI fails if the benchmark regresses.

Failure modes

  • Benchmarking debug builds. No R8, no profile, extra checks.
  • Optimising by intuition. Measure first.
  • Stale Baseline Profiles. Generated once, never updated.
  • Main-thread disk reads at start. Preferences, flags, a database open.
  • Testing only on flagships. The median Android device is much slower.

Trade-offs and when not to use it

Fix startup and the main list first, set budgets in CI, and stop. Visual richness, including blur, is a cost you choose; make it visible in the benchmark and decide with numbers.

Production and security

Traces and performance SDKs can capture URLs and screen names; make sure they capture no personal or financial data. Prepare slow security steps (key generation, attestation) before the user reaches the confirm button.

Release and operations

Shipping a binary you cannot roll back to devices you do not control.

Why it exists

A server deploy replaces every instance in minutes and can be reverted. A mobile release is reviewed by a store, adopted over weeks, and never reaches some users. Versions from two years ago still call your APIs.

Mental model

You do not deploy an app. You publish a version and persuade devices to adopt it. Control lives on the server: flags, configuration and compatibility.

Mechanics

Signing. With Play App Signing, Google holds the app signing key and you sign uploads with a separate upload key that can be reset if lost.

Tracks and rollout. Internal, closed, open, production. Production goes out in stages (1%, 5%, 20%, 50%, 100%) while you watch vitals. A staged rollout can be halted. It cannot be reversed.

/** The server answers 426 when this build must not continue. */
public class UpgradeGateInterceptor implements Interceptor {
    private final UpgradeGate gate;
    @Inject UpgradeGateInterceptor(UpgradeGate gate) { this.gate = gate; }

    @NonNull @Override public Response intercept(@NonNull Chain chain) throws IOException {
        Response response = chain.proceed(chain.request());
        if (response.code() == 426) gate.require(response.header("X-Min-Version"));
        return response;
    }
}

End-to-end flow: a bad release

  1. Version 1.9.0 reaches 5% of users. Transfer success for that version drops.
  2. An alert on "success rate by app version" fires within the hour.
  3. The rollout is halted. The new flow's flag is turned off for 1.9.0; users fall back to the old flow already in the binary.
  4. The fix ships as 1.9.1 through the same stages.
  5. A review adds the missing test.

Failure modes

  • Breaking API changes. Removing a field the two-year-old app needs.
  • No forced-upgrade path when a security flaw is found.
  • Flag debt. Give every flag an owner and an expiry.
  • Missing mapping files. Crash reports full of a.b.c().
  • Lost keys without Play App Signing.
  • SDK surprises. An update starts collecting data your privacy declaration does not mention.

Trade-offs and when not to use it

Use flags for risk control, not as a permanent configuration system. Weekly release trains give predictability; continuous delivery to production is rarely practical with store review and staged adoption.

Production and security

For SOC 2: every release traces to a reviewed commit, built by CI, signed by a controlled key, promoted with an approval. Keep a software bill of materials per release. Rehearse the forced-upgrade and key-compromise runbooks. Remove debug menus and test endpoints from release with build-type source sets.

public class HomeViewModel extends ViewModel {

}

End-to-end flows

1. Cold start with a returning user

  1. Icon tap, Zygote fork, Application.onCreate with only Hilt and crash reporting eager.
  2. MainActivity inflates the nav host. The start destination checks session state from DataStore.
  3. A session exists. HomeFragment shows cached balance and transactions from Room at once, marked "Updated 09:14".
  4. In parallel the dashboard refreshes through the BFF. The token is expired; one refresh happens under the authenticator's lock.
  5. Room is updated; the Flowable emits; the label changes.

2. Sending ₹50,000

  1. The transfer reducer handles AmountChanged and SendClicked; validation runs in the domain layer.
  2. The server replies that step-up is required. State becomes "awaiting step-up" with a challenge.
  3. BiometricPrompt unlocks the hardware key, which signs challenge, payee, amount and idempotency key.
  4. One Room transaction writes the outbox row and a PENDING transaction. The UI transitions to "Sending".
  5. An expedited worker posts the transfer with signature, key and integrity token.
  6. Success: the transaction becomes POSTED and the receipt appears with a haptic. Timeout: the state stays pending with honest copy, and the worker retries with the same key.

  1. The ledger posts a credit. A data push with only an account id reaches the device.

Introducing Kotlin, if and when

Staying all-Java is viable today for a View-based app. The pressure will come from libraries, not from the language. A low-risk sequence:

  1. Tests and the benchmark module. No production risk, and the team learns the syntax.
  2. :core:database when you want Room 3. It hides behind the Java interface from chapter 24.
  3. New leaf features. A new screen in a new module, possibly in Compose, hosted by a fragment.
  4. The data layer, replacing RxJava chains with coroutines behind the same repository interfaces.
  5. Leave stable Java modules alone. Mixed codebases run for years without trouble.

Annotate your Java with @NonNull and @Nullable now. It costs little and makes every later step safer.
