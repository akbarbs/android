I · The language core · Chapter 1

Why Kotlin, and how it runs

What Kotlin is, why Android adopted it, and what happens to a line of it before a phone executes it.

Why it exists

For years Android's Java was held at old language levels. Listeners were anonymous inner classes, background work was threads and callbacks, and NullPointerException was the most common crash on the platform. JetBrains designed Kotlin to run on the same virtual machine and call Java in both directions, so a team could adopt it one file at a time. Version 1.0 shipped in 2016, Google supported it officially in 2017 and declared Android Kotlin-first in 2019.

Two things now exist only in Kotlin: Jetpack Compose, which is a Kotlin compiler plugin, and coroutines, which most Jetpack libraries use for asynchronous work. In Kosh, every layer of the map above is written in it.

Mental model

Kotlin is a different front end to the same machine. It compiles to the class files Java compiles to, and Android turns those into what the phone runs.

Mechanics

A program

fun main() {
    val app = "Kosh"
    println("Hello from $app")
}

There are no semicolons and no wrapping class. val declares a value, and $app inside a string inserts it.

Top-level declarations

Functions and constants can sit directly in a file. The compiler puts them in a class named after the file:

// Money.kt
import kotlin.math.abs

const val MINOR_PER_RUPEE = 100                      // a compile-time constant

fun rupees(minor: Long): String {                    // a top-level function: no class needed
    val whole = abs(minor) / MINOR_PER_RUPEE
    val paise = (abs(minor) % MINOR_PER_RUPEE).toString().padStart(2, '0')
    return (if (minor < 0) "−" else "") + "₹$whole.$paise"
}

fun main() = println(rupees(1_248_050))              // ₹12480.50

$ kotlinc Money.kt -d out
$ javap -p out/MoneyKt.class
public final class MoneyKt {
  public static final int MINOR_PER_RUPEE;
  public static final java.lang.String rupees(long);
  public static final void main();
  public static void main(java.lang.String[]);
}

That output is the whole trick. A top-level function is a static method, Long became a primitive long, and Java code can call MoneyKt.rupees(…) without knowing Kotlin was involved.

The toolchain

kotlinc is the compiler; the K2 compiler has been the default since Kotlin 2.0. A small runtime library, kotlin-stdlib, ships inside your app and holds the collection functions, coroutine support and the rest of the standard library. In an Android project you never call kotlinc yourself: Gradle and the Android Gradle Plugin do, as the build chapter of the Android book describes.

End-to-end flow: one line, from source to a running instruction

  1. The compiler parses and type-checks the file. Null safety, exhaustive when and type inference all happen here and cost nothing at run time.
  2. It emits JVM bytecode in .class files, the same format javac produces.
  3. R8 (or D8 in debug builds) converts the class files to DEX, Android's bytecode, and in release builds removes what is unused.
  4. The DEX files are packaged into the app bundle and signed.
  5. On the device, ART compiles DEX to machine code: ahead of time for code listed in a baseline profile, just in time for the rest.

The phone never sees Kotlin. Anything you learn about JVM bytecode, DEX or ART applies equally to Java and Kotlin code.

Failure modes

  • Mixed Kotlin versions. A library built with a newer Kotlin than your compiler fails with "Module was compiled with an incompatible version of Kotlin". Upgrade Kotlin; do not suppress the check.
  • Compiler plugins out of step. KSP and other compiler plugins are built for a specific Kotlin version. The Compose compiler has shipped with Kotlin itself since 2.0, so that one cannot drift.
  • Advice from 2017. Synthetic view imports from kotlin-android-extensions are gone, and GlobalScope is discouraged. Check the date on anything you copy.
  • Slow builds. Kotlin compiles more slowly than Java, and annotation processing through KAPT is slower again. Prefer KSP and split the project into modules.

Trade-offs and when not to use it

Kotlin gives you several ways to write the same thing, so a team needs a style guide and a linter sooner than a Java team does. Some costs are hidden: a lambda can allocate an object, and Int? is a boxed Integer. Coroutines take real time to learn well.

Leave a stable Java module in Java if nobody is changing it. Mixed projects work, and converting code only for the sake of converting it buys nothing.

Production and security

Pin the Kotlin version in the version catalog and upgrade it deliberately, together with the compiler plugins that depend on it. Avoid kotlin-reflect in apps: it is large, and R8 cannot shrink code that is reached by reflection.

Kotlin compiles to ordinary bytecode, so it is exactly as easy to decompile as Java. A const val is copied into every class that uses it. Neither is a place for a secret.

  • Challenge. Your team owns 200,000 lines of Java. Write the one-page policy that says which code moves to Kotlin, and when.

Values, types and control flow

Immutable by default, expressions instead of statements, and one set of number types.

Why it exists

Java separates statements from expressions, primitives from their boxed twins, and makes every variable mutable unless you add final. Each of those defaults produces bugs: a variable reassigned by mistake, a branch that forgets to set a result, an Integer compared with ==.

Kotlin reverses the defaults. In Kosh this is the vocabulary of the domain layer: amounts, statuses and labels.

Mental model

Almost everything produces a value, and almost nothing changes after it is assigned.

Mechanics

Values and basic types

fun main() {
    val limit = 50_000                 // Int, inferred. val: assigned once
    var attempts = 0                   // var: may be reassigned
    attempts += 1

    val balance: Long = 1_248_050      // minor units. Long, because money overflows Int
    val rate = 7.25                    // Double
    val enough = balance > limit       // Boolean
    val label = "₹${balance / 100}.${balance % 100} after $attempts attempt(s), enough=$enough, rate=$rate"
    println(label)

    val total: Long = balance + limit  // Long + Int is defined and gives a Long
    // val bad: Long = limit           // does not compile: an Int is never silently a Long
    val widened: Long = limit.toLong() // conversions are explicit
    println(total + widened)

    val note = """
        To: Asha
        Ref: KX-88213
    """.trimIndent()                   // a raw string: no escapes, line breaks kept
    println(note.lines().size)
}
TypeWhat it is
Int, Long32-bit and 64-bit integers. Literals may use _ as a separator.
Double, FloatFloating point. Never for money.
Boolean, Char, StringAs in Java. Strings are immutable.
AnyThe root of every non-null type, like Object.
UnitWhat a function returns when it has nothing to return. Unlike void, it is a real value.
NothingThe type of an expression that never finishes, such as throw.

There is one Int in the source. The compiler uses a primitive int where it can and a boxed Integer where it must: for Int? and inside generic types such as List<Int>.

if and when are expressions

enum class Status { PENDING, POSTED, FAILED }

fun badge(status: Status, amountMinor: Long): String {
    val sign = if (amountMinor < 0) "−" else "+"          // if is an expression: it has a value
    val tone = when (status) {                            // so is when. Every enum case must be covered
        Status.PENDING -> "grey"
        Status.POSTED -> if (amountMinor < 0) "ink" else "green"
        Status.FAILED -> "red"
    }
    return "$sign $tone"
}

fun bucket(amountMinor: Long): String = when {            // when with no subject: the first true branch wins
    amountMinor < 0 -> "debit"
    amountMinor == 0L -> "zero"
    amountMinor in 1..99_999 -> "small credit"            // a range check
    else -> "large credit"
}

fun main() {
    println(badge(Status.POSTED, 50_000))                 // + green
    println(bucket(250_000))                              // large credit
}

There is no ternary operator because if already returns a value. when replaces switch and has no fall-through.

Loops, ranges and equality

fun main() {
    for (i in 1..3) print("$i ")                 // 1 2 3
    for (i in 0..<3) print("$i ")                // 0 1 2
    for (i in 10 downTo 0 step 5) print("$i ")   // 10 5 0
    println()

    val names = listOf("Asha", "Ravi", "Meera")
    for ((index, name) in names.withIndex()) println("$index: $name")

    var retries = 3
    while (retries > 0) retries--

    val a = "KX-88213"
    val b = StringBuilder("KX-").append(88213).toString()   // equal text, built separately
    println(a == b)                              // true: == calls equals()
    println(a === b)                             // false: === asks "is it the same object?"
}

End-to-end flow: one transaction badge

Follow badge(Status.POSTED, 50_000) through the function above:

  1. The if evaluates to "+" and is assigned to sign.
  2. The when matches POSTED. Its branch is another if, which evaluates to "green".
  3. The string template joins the two into "+ green".

No variable was reassigned and no branch could forget to produce a value. Now add REVERSED to the enum: the when stops compiling until you say what its colour is. The change is found at build time, at the exact line.

Failure modes

  • Integer overflow. Int.MAX_VALUE + 1 wraps silently, as in Java. Keep money in Long and use Math.addExact where a wrong sum would matter.
  • Integer division. 7 / 2 is 3. Dividing minor units by 100 drops the paise unless you also take the remainder.
  • Floating-point money. 0.1 + 0.2 == 0.3 is false.
  • An else that hides a new case. A when over an enum with an else branch keeps compiling when a constant is added. Leave the else out.
  • var by habit. Start with val. Change it only when the compiler tells you that you reassign.

Trade-offs and when not to use it

Type inference keeps code short and hides types in long chains; write the type on anything public. Expression style can be pushed too far: an if inside a when inside a template is legal and unreadable. Name the intermediate values. Explicit conversions such as toLong() are noise on some days and the reason a truncation bug did not ship on others.

Production and security

Store money as integer minor units in a Long. Convert at the boundary and nowhere else. toInt() on a large Long truncates without complaint; use Math.toIntExact when the value came from outside.

String templates make it very easy to write "token=$token". Do not build log lines from secrets or account numbers.

Null safety

How Kotlin turns "this might be missing" into something the compiler checks.

Why it exists

In Java, any reference can be null and the type does not say which ones are. Annotations such as @Nullable help tools and bind nobody. The result was a crash that could happen on any line.

Kotlin splits every type in two. In Kosh the nullable half appears at the edges: a server field that may be absent, a form the user has not filled in, an extra that another app did not send.

Mental model

String? is a different type from String. The compiler will not accept the first where the second is needed until you have said what happens when it is null.

Mechanics

The operators

data class Payee(val name: String, val nickname: String?, val upiId: String?)

fun displayName(p: Payee): String = p.nickname ?: p.name             // Elvis: the right side when the left is null

fun handleLength(p: Payee): Int = p.upiId?.length ?: 0               // safe call: null if upiId is null

fun requireUpi(p: Payee): String =
    p.upiId ?: throw IllegalStateException("${p.name} has no UPI id")   // throw is an expression too

fun notify(p: Payee) {
    p.upiId?.let { id -> println("Collect request sent to $id") }       // the block runs only for a non-null value
}

fun describe(p: Payee): String {
    val id = p.upiId
    if (id == null) return "No UPI id"
    return id.uppercase()            // smart cast: past the check, id is a String
}

fun main() {
    val asha = Payee("Asha Rao", nickname = null, upiId = "asha@okbank")
    val ravi = Payee("Ravi Kumar", nickname = "Ravi", upiId = null)
    println("${displayName(asha)} / ${displayName(ravi)}")           // Asha Rao / Ravi
    println("${handleLength(asha)} / ${handleLength(ravi)}")         // 11 / 0
    notify(asha); notify(ravi)                                       // one line printed
    println(describe(ravi))
}
SyntaxMeaning
a?.bb if a is not null, otherwise null
a ?: ba if it is not null, otherwise b
a!!a as a non-null type; throws NullPointerException if you were wrong
a as? Ta as a T, or null if it is not one
a?.let { … }run the block with the non-null value

!! is an assertion. Each one is a claim that you can explain, to a reviewer, why the value cannot be null there.

Late initialisation, Java values and casts

class Session {
    lateinit var token: String                   // a non-null type that is assigned later

    val isSignedIn: Boolean get() = ::token.isInitialized
}

fun main() {
    val s = Session()
    println(s.isSignedIn)                        // false
    try { println(s.token) }                     // reading it too early throws
    catch (e: UninitializedPropertyAccessException) { println(e.message) }
    s.token = "abc"
    println(s.isSignedIn)                        // true

    val env: String? = System.getenv("KOSH_ENV") // Java cannot say whether this is null, so you decide
    println(env ?: "dev")

    val extra: Any = "250"
    val amount: Int? = (extra as? String)?.toIntOrNull()   // safe cast, then safe parse
    println(amount)                              // 250
}

A value that comes from Java has a platform type: the compiler does not know whether it can be null and lets you treat it either way. Declare the type yourself, as env does above.

End-to-end flow: a missing nickname, from JSON to the screen

  1. The server omits nickname for a payee.
  2. The DTO declares val nickname: String? = null, so parsing succeeds and the property is null.
  3. The mapper copies it into the domain Payee, whose type also says String?.
  4. The row calls displayName(payee). The Elvis operator returns the legal name.

Nothing checked for null "just in case". The decision was made once, at the place where absence has a meaning, and the compiler would have rejected payee.nickname.length anywhere along the way.

Failure modes

  • !! to make the error go away. The crash has moved, not gone.
  • Platform types trusted as non-null. A Java method returns null, you assigned it to a String, and the app throws on that line.
  • lateinit read too early or too late. In a fragment, a lateinit binding read after onDestroyView is the classic case.
  • Smart casts on mutable properties. "Smart cast is impossible, because it is a mutable property that could have been changed by this time." Copy it into a local val, or use ?.let.
  • Reflection-based JSON. Gson builds objects without calling the constructor and can put null into a non-null property. The crash then appears far from the cause. Use kotlinx.serialization or Moshi with generated adapters.
  • List<String?> versus List<String>?. A list of maybe-strings is not a maybe-list of strings.

Trade-offs and when not to use it

Nullable types everywhere give you Java back, with more punctuation. Push null to the edges: convert it to a default, a non-null type or a sealed result as soon as the value enters your code.

Null says "absent" and nothing else. When the reason matters (not loaded yet, not permitted, not found) null is the wrong tool; use a sealed type from chapter 6. Between lateinit, a nullable property and by lazy, prefer lazy when you can compute the value and a nullable property when absence is a real state.

Production and security

Everything that arrives from outside is nullable until you have validated it: JSON, deep links, intent extras. An exported activity that does intent.getStringExtra("id")!! can be crashed by any app on the device.

When a NullPointerException appears in crash reports for Kotlin code, search for three things: !!, a platform type and lateinit. It is almost always one of them.

Functions and lambdas

Default and named arguments, functions as values, and what inline changes.

Why it exists

Java APIs grow overloads to simulate default values, builders to simulate named options and anonymous classes to pass behaviour. Kotlin makes all three direct. That matters on Android more than anywhere: a Compose screen is a function that takes lambdas, a click handler is a lambda, and every collection operation takes one.

In Kosh, functions as values carry events from the UI up to the state holder.

Mental model

A function is a value. You can store it, pass it and return it, and braces are how you write one in place.

Mechanics

Declaring and calling

fun fee(amountMinor: Long, percent: Double = 1.0, capMinor: Long = 2_500): Long {
    val raw = (amountMinor * percent / 100).toLong()
    return minOf(raw, capMinor)
}

fun double(x: Int) = x * 2                                  // single expression; the return type is inferred

fun main() {
    println(fee(100_000))                                   // 1000: defaults fill in the rest
    println(fee(100_000, capMinor = 500))                   // 500: a named argument skips percent
    println(fee(amountMinor = 1_000_000, percent = 0.5))    // 2500: capped
    println(double(21))
}

Function types and lambdas

data class Tx(val id: String, val amountMinor: Long)

fun sumWhere(items: List<Tx>, keep: (Tx) -> Boolean): Long {     // a function type as a parameter
    var total = 0L
    for (tx in items) if (keep(tx)) total += tx.amountMinor
    return total
}

fun retry(times: Int, block: () -> Unit) { repeat(times) { block() } }

fun main() {
    val txs = listOf(Tx("t1", 50_000), Tx("t2", -12_000), Tx("t3", 8_000))

    val credits = sumWhere(txs) { it.amountMinor > 0 }           // trailing lambda; `it` is its one parameter
    val debits = sumWhere(txs, fun(tx: Tx): Boolean { return tx.amountMinor < 0 })   // the same thing, long form
    println("$credits $debits")                                  // 58000 -12000

    val isLarge: (Tx) -> Boolean = { tx -> tx.amountMinor >= 50_000 }   // a lambda held in a value
    println(txs.filter(isLarge).map(Tx::id))                     // [t1]; Tx::id is a reference to the property

    var calls = 0
    retry(3) { calls++ }                                         // a lambda can read and change local variables
    println(calls)                                               // 3
}

(Tx) -> Boolean is a type like any other. When a lambda is the last argument it moves outside the parentheses, which is why Column { Text("Hi") } in Compose is an ordinary function call.

inline and return

inline fun <T> timed(label: String, block: () -> T): T {       // inline: the lambda body is copied to the call site
    val start = System.nanoTime()
    try { return block() }
    finally { println("$label took ${(System.nanoTime() - start) / 1_000} µs") }
}

fun firstLarge(amounts: List<Long>): Long? {
    amounts.forEach { if (it > 100_000) return it }             // returns from firstLarge, because forEach is inline
    return null
}

fun countLarge(amounts: List<Long>): Int {
    var n = 0
    amounts.forEach {
        if (it <= 100_000) return@forEach                       // skips this element only
        n++
    }
    return n
}

fun main() {
    val amounts = listOf(5_000L, 250_000L, 900_000L)
    println(timed("scan") { firstLarge(amounts) })              // 250000
    println(countLarge(amounts))                                // 2
}

Most standard-library functions that take lambdas (forEach, map, let) are inline, so a plain return inside them leaves the enclosing function.

End-to-end flow: a tap on Send

  1. The transfer screen is declared as a function with a parameter onSend: () -> Unit.
  2. It passes that value to Button(onClick = onSend), which stores it.
  3. The user taps. The framework invokes the stored function.
  4. The lambda that was passed in from the caller runs: { viewModel.send() }.

The button never learned what "send" means. State goes down as parameters and events come up as function values, which is the pattern the state hoisting chapter of the Android book builds on.

Failure modes

  • Capturing too much. A lambda that mentions an activity or a view holds a reference to it. Stored in something long-lived, that is a leak.
  • Nested it. Two lambdas deep, it refers to the inner parameter. Name your parameters as soon as lambdas nest.
  • Surprising return. In an inline lambda it leaves the outer function; use return@forEach to skip one element.
  • Unnamed booleans. fee(1000, true, false) tells the reader nothing. Name the arguments.
  • Renaming a parameter. Callers that name an argument break. Parameter names are part of your API.
  • Allocation in hot paths. A non-inline lambda that captures a variable is a new object on each call. In code that runs every frame, that is garbage.

Trade-offs and when not to use it

Higher-order functions remove duplication and can also hide control flow: a stack trace through five lambdas is harder to read than one through five named functions. Mark a function inline when it is small and takes a lambda; inlining a large one copies its body into every caller. When a callback needs a name and documentation, a fun interface (chapter 13) says more than a bare function type.

Production and security

The production question for every stored lambda is ownership: who holds it, and for how long. A callback registered with a singleton must be unregistered. Default arguments are evaluated on each call, so createdAt: Long = System.currentTimeMillis() does what you hope. There is little here that is specific to security.

II · Modelling · Chapter 5

Classes, properties and objects

Constructors, properties, interfaces, singletons and what "final by default" asks of you.

Why it exists

A Java class that holds three values needs fields, a constructor, getters, setters and usually a builder. Most of that text says nothing. Kotlin folds the constructor into the class header and replaces field-plus-accessors with a property, so what remains on the page is the part that is specific to your class.

In Kosh these are the domain models, the repository interfaces and the few true singletons.

Mental model

The class header is the constructor. A property is a field with a getter and a setter, and you write only the parts that differ from the default.

Mechanics

A class with an invariant

class Account(val id: String, openingMinor: Long = 0) {         // primary constructor; `val` makes id a property
    var balanceMinor: Long = openingMinor
        private set                                             // readable everywhere, writable only in here

    val isOverdrawn: Boolean get() = balanceMinor < 0           // computed on each read; stores nothing

    init { require(id.isNotBlank()) { "Account id is blank" } } // runs during construction

    fun deposit(minor: Long) {
        require(minor > 0) { "Deposit must be positive" }
        balanceMinor = Math.addExact(balanceMinor, minor)
    }
}

fun main() {
    val a = Account("SB-1001", openingMinor = 5_000)            // no `new`
    a.deposit(2_500)
    println("${a.id} ${a.balanceMinor} ${a.isOverdrawn}")       // SB-1001 7500 false
    // a.balanceMinor = 0                                       // does not compile: the setter is private
}

balanceMinor can be read by anyone and changed only through deposit, which checks its argument. isOverdrawn has a getter and no storage.

Interfaces, inheritance, objects and companions

interface LimitsPolicy {
    fun check(amountMinor: Long): String?                       // null means "allowed"
    val dailyCapMinor: Long get() = 10_000_000                  // an interface can carry a default
}

open class DefaultLimits : LimitsPolicy {                       // classes are final unless marked open
    override fun check(amountMinor: Long): String? =
        if (amountMinor > dailyCapMinor) "Above the daily limit" else null
}

class MinorAccountLimits : DefaultLimits() {
    override val dailyCapMinor: Long get() = 500_000
}

object NoLimits : LimitsPolicy {                                // a singleton, created on first use
    override fun check(amountMinor: Long): String? = null
}

class Transfer private constructor(val payeeId: String, val amountMinor: Long) {
    companion object {                                          // where Java would use static members
        const val MAX_NOTE_LENGTH = 80
        fun of(payeeId: String, amountMinor: Long): Transfer? =
            if (payeeId.isNotBlank() && amountMinor > 0) Transfer(payeeId, amountMinor) else null
    }
}

fun main() {
    println(MinorAccountLimits().check(600_000))    // Above the daily limit
    println(NoLimits.check(600_000))                // null
    println(Transfer.of("", 100))                   // null
}

End-to-end flow: constructing an account

What happens for Account("SB-1001", openingMinor = 5_000):

  1. The arguments are evaluated and id is stored as a property.
  2. Property initialisers and init blocks run from top to bottom, in the order they are written: balanceMinor is assigned, then the require checks the id.
  3. If the check fails the constructor throws, and no half-built object escapes.
  4. Later, deposit validates its amount, adds with an overflow check and writes through the private setter.

Every rule about an account lives in the class. No caller can put it into a state the class did not agree to.

Failure modes

  • Initialisation order. An init block that reads a property declared below it sees zero or null. Declare before use.
  • Calling an open function from a constructor. The subclass override runs before the subclass has been initialised.
  • An object that holds a Context or a view. It lives as long as the process, and so does everything it references.
  • Global mutable state. An object with var properties is a global variable. Tests that touch it interfere with each other.
  • An expensive computed property. val total get() = entries.sumOf { … } looks like a field and runs on every read.

Trade-offs and when not to use it

Classes are final unless you write open. That pushes you toward interfaces and composition, and makes inheritance a decision. Use it when there is a real "is a" relationship and you control both classes.

An object is the easiest singleton to write and the hardest dependency to replace in a test. In an app with dependency injection, let the container own lifetimes. Use a property when the value is cheap, has no side effects and returns the same answer when asked twice; otherwise write a function.

Production and security

internal and private organise code. They are not security boundaries: internal members are public in the bytecode under a mangled name, and reflection reaches private ones. A secret that must not be read does not belong in a class in the app at all.

Data, enum, sealed and value classes

Four kinds of class that exist to make wrong states impossible to write.

Why it exists

Most classes in an app carry data. Most bugs in how they are used are one of two kinds: two things of the same primitive type swapped by accident, or a "status" with a combination of fields that should never occur together. Java's tools for this were integer constants, strings and hope.

In Kosh these four class kinds model money, identifiers, the outcome of a transfer and the state of every screen.

Mental model

Make a state that cannot happen impossible to write. data for a value, enum for a fixed set of names, sealed for a fixed set of shapes, value for a primitive that deserves its own type.

Mechanics

Data classes

data class Money(val minor: Long, val currency: String = "INR")

fun main() {
    val a = Money(25_000)
    val b = Money(25_000)
    println(a == b)                       // true: equals compares the constructor properties
    println(a)                            // Money(minor=25000, currency=INR)
    val c = a.copy(minor = 30_000)        // a changed copy; a itself is untouched
    val (minor, currency) = c             // destructuring, by position
    println("$minor $currency")           // 30000 INR
    println(setOf(a, b).size)             // 1: hashCode agrees with equals
}

Only properties in the primary constructor take part in equals, hashCode, toString and copy. copy is shallow: a list inside the copy is the same list.

Enum, value and sealed

enum class Channel(val label: String) { UPI("UPI"), IMPS("IMPS"), NEFT("NEFT") }

@JvmInline value class AccountId(val raw: String)              // a distinct type that compiles down to a String
@JvmInline value class PayeeId(val raw: String)

sealed interface TransferResult {
    data class Success(val reference: String) : TransferResult
    data class Declined(val reason: String) : TransferResult
    data object Pending : TransferResult                       // sent; the outcome is not known yet
}

fun message(r: TransferResult): String = when (r) {            // no else: add a case and this stops compiling
    is TransferResult.Success -> "Sent. Ref ${r.reference}"    // smart cast to Success
    is TransferResult.Declined -> "Declined: ${r.reason}"
    TransferResult.Pending -> "We are confirming this payment"
}

fun send(from: AccountId, to: PayeeId, channel: Channel): TransferResult =
    if (channel == Channel.NEFT) TransferResult.Pending else TransferResult.Success("KX-1")

fun main() {
    val from = AccountId("SB-1001")
    val to = PayeeId("P-77")
    println(message(send(from, to, Channel.UPI)))              // Sent. Ref KX-1
    // send(to, from, Channel.UPI)                             // does not compile: the two ids cannot be swapped
    println(Channel.entries.joinToString { it.label })         // UPI, IMPS, NEFT
}

End-to-end flow: adding a new outcome

Product decides that large transfers need a biometric step. You add one line: data class NeedsStepUp(val challenge: String) : TransferResult.

  1. The build fails at every when over TransferResult that has no else: the message function, the screen's reducer, the analytics mapper.
  2. At each one you decide what the new case means there.
  3. When the build is green, every place that inspects a transfer result handles the new one.

Had the result been a String status, the same change would have compiled immediately and failed in production, in whichever branch was forgotten.

Failure modes

  • Mutable data in a hash-based collection. A data class with a var property changes its hash code when the property changes. Put one in a set, mutate it, and the set can no longer find it.
  • Arrays in data classes. Arrays compare by reference, so two equal-looking instances are not equal. Use a List.
  • An else branch over a sealed type. It switches the exhaustiveness check off.
  • Persisting ordinal. Reordering the enum corrupts stored data. Store the name or an explicit code.
  • Unknown values from a newer server. enumValueOf throws for a name it does not know. Map anything unrecognised to an explicit Unknown case.
  • Value classes that box. Used as a nullable type, a generic argument or through an interface, a value class is wrapped in an object after all.

Trade-offs and when not to use it

A sealed type is closed, which is its strength inside one app and its weakness across a network: an app released last year cannot know a case added this year. Keep sealed types on your side of the boundary and translate at the edge.

Do not make an entity a data class. An Account whose balance changes has an identity; two accounts with equal fields are still two accounts. In a published library, adding a property to a data class changes copy and the componentN functions and breaks compiled callers.

Production and security

The generated toString prints every property. A data class that holds a card number or a token will put it in a log line the first time someone writes "$request". Override toString on sensitive types, or do not make them data classes.

Collections and sequences

Read-only and mutable collections, the operators you will use daily, and when laziness pays.

Why it exists

A loop with an accumulator says how to compute something and leaves the reader to work out what. Kotlin's standard library names the common shapes (filter, group, sum) and separates collections you can read from collections you can change.

In Kosh almost every screen starts from a list of transactions and derives something from it.

Mental model

An operation takes a collection and returns a new one. A chain reads from top to bottom as a sentence: keep the debits, group them by payee, add each group up.

Mechanics

The everyday operators

data class Tx(val id: String, val payee: String, val amountMinor: Long, val day: String)

val txs = listOf(
    Tx("t1", "Asha", -25_000, "Mon"), Tx("t2", "Salary", 8_500_000, "Mon"),
    Tx("t3", "Asha", -5_000, "Tue"), Tx("t4", "Ravi", -120_000, "Tue"),
)

fun main() {
    val debits = txs.filter { it.amountMinor < 0 }                     // a new list; txs is unchanged
    val spent = debits.sumOf { -it.amountMinor }                       // 150000
    val byPayee: Map<String, Long> = debits.groupBy { it.payee }
        .mapValues { (_, list) -> list.sumOf { -it.amountMinor } }     // {Asha=30000, Ravi=120000}
    val biggest = debits.minByOrNull { it.amountMinor }?.payee         // Ravi; null for an empty list
    val (small, large) = debits.partition { -it.amountMinor < 100_000 }
    val perDay = txs.groupingBy { it.day }.eachCount()                 // {Mon=2, Tue=2}
    val byId = txs.associateBy { it.id }                               // id -> Tx, for lookups
    println("$spent $byPayee $biggest ${small.size}/${large.size} $perDay ${byId["t3"]?.payee}")

    val readOnly: List<Tx> = txs                  // this type has no add()
    val mutable = txs.toMutableList()             // a separate, mutable copy
    mutable += Tx("t5", "Meera", -900, "Wed")
    println("${readOnly.size} ${mutable.size}")   // 4 5
}

Sequences

fun main() {
    val amounts = (1..1_000_000).map { it * 10L }

    // Eager: builds a million-element list, then a second one, then keeps three
    val eager = amounts.map { it + 1 }.filter { it % 7 == 0L }.take(3)

    // Lazy: each element goes through the whole chain, and the chain stops after three results
    var touched = 0
    val lazy = amounts.asSequence().onEach { touched++ }
        .map { it + 1 }.filter { it % 7 == 0L }.take(3).toList()

    println("$eager $lazy touched=$touched")      // [21, 91, 161] twice; touched=16
}

The eager chain processed two million elements to produce three. The sequence touched sixteen.

End-to-end flow: spend by payee

Trace byPayee in the first sample with its four transactions:

  1. filter returns a new list of the three debits: t1, t3, t4.
  2. groupBy returns a map: Asha → [t1, t3], Ravi → [t4].
  3. mapValues returns another map with each list replaced by its sum: Asha → 30000, Ravi → 120000.

Three steps, three new collections, and the original list untouched. That is the cost model: clarity paid for with allocation.

Failure modes

Read-only does not mean immutable:

fun main() {
    val backing = mutableListOf("t1", "t2")
    val view: List<String> = backing           // a read-only view of the same list
    backing += "t3"
    println(view)                              // [t1, t2, t3]: read-only does not mean immutable
    val snapshot = backing.toList()            // a copy that later changes cannot reach
    backing.clear()
    println("$view $snapshot")                 // [] [t1, t2, t3]
}
  • Throwing accessors. first() throws on an empty list and list[5] throws when out of range. map[key] returns null; map.getValue(key) throws. Prefer the OrNull forms.
  • Long chains on long lists in UI code. Every step allocates. Run them once in the state holder, never in the body of a composable.
  • Changing a list while iterating over it. ConcurrentModificationException.
  • associateBy with duplicate keys. The last one wins, silently.
  • sumOf on Int. The sum is an Int and wraps on overflow.
  • Reusing a sequence. Each terminal operation runs the whole chain again.

Trade-offs and when not to use it

A plain for loop is still right in a hot path. Use a sequence when the collection is large and the chain has several steps or stops early; for a list of twenty it is slower than the eager version. When you need a collection that truly cannot change, use kotlinx.collections.immutable.

If the data is in a database, let the database filter and aggregate. Loading ten thousand rows to sum them in memory is the wrong layer doing the work.

Production and security

Expose List and keep the MutableList private. Copy at boundaries with toList(). A StateFlow<List<T>> must be given a new list, because it compares the new value with the old and a list mutated in place equals itself: the screen will not update.

Cap the size of any list that comes from outside before you process it.

Extensions, scope functions and receivers

Adding functions to types you do not own, the five scope functions, and how builders work.

Why it exists

You cannot add a method to String or to Android's Context. Java's answer is a utility class and a call that reads inside out: MoneyUtils.format(amount). Kotlin lets you write the function so the call reads amount.format(), and extends the same idea to lambdas, which is how the Gradle Kotlin DSL and Compose's scopes are built.

In Kosh, extensions keep formatting in the UI layer and mapping in the data layer, away from the domain types they operate on.

Mental model

An extension is a static function whose first argument is written before the dot. It cannot see private members, and it does not change the class.

Mechanics

Extension functions and properties

import kotlin.math.abs

fun Long.asRupees(): String {                          // inside, `this` is the Long it was called on
    val paise = (abs(this) % 100).toString().padStart(2, '0')
    return (if (this < 0) "−" else "") + "₹${abs(this) / 100}.$paise"
}

val String.isUpiId: Boolean                            // an extension property: computed, never stored
    get() = Regex("^[a-z0-9._-]{2,}@[a-z]{2,}$").matches(this)

fun String?.orDash(): String = this ?: "—"             // an extension on a nullable type

fun main() {
    println(1_248_050L.asRupees())                     // ₹12480.50
    println((-250L).asRupees())                        // −₹2.50
    println("asha@okbank".isUpiId)                     // true
    val note: String? = null
    println(note.orDash())                             // —  (no safe call needed)
}

Scope functions

class Request { var url = ""; var timeoutMs = 0; val headers = mutableMapOf<String, String>() }

fun main() {
    val token: String? = "abc"

    val request = Request().apply {                   // apply: configure the object, get the object back
        url = "https://api.kosh.example/v1/transfers"
        timeoutMs = 20_000
    }
    token?.let { request.headers["Authorization"] = "Bearer $it" }    // let: use a non-null value once
    val sent = request.also { println("Sending to ${it.url}") }       // also: a side effect; same object back
    val summary = with(sent) { "$timeoutMs ms, ${headers.size} header(s)" }   // with: several reads of one object
    val host = sent.url.run { removePrefix("https://").substringBefore('/') } // run: compute something from it
    println("$summary, $host")
}

Lambdas with receivers

class ReceiptBuilder {
    private val lines = mutableListOf<String>()
    fun line(label: String, value: String) { lines += label.padEnd(10) + value }
    fun rule() { lines += "-".repeat(22) }
    fun build(): String = lines.joinToString("\n")
}

    ReceiptBuilder().apply(block).build()

fun main() {
    val text = receipt {              // inside the braces, `this` is a ReceiptBuilder
        line("To", "Asha")
        line("Amount", "₹250.00")

        line("Ref", "KX-88213")
    }
    println(text)
}

ReceiptBuilder.() -> Unit is a lambda in which this is a ReceiptBuilder. Compose's Column { } works the same way: inside the braces you are in a ColumnScope.

End-to-end flow: what an extension call compiles to

For 1_248_050L.asRupees():

  1. The compiler looks for a member of Long named asRupees. There is none.
  2. It looks for an extension in scope: declared in this file or imported.
  3. It emits a static call, in effect MoneyFormatKt.asRupees(1248050L).
  4. Inside the function, this is that parameter.

The function was chosen at compile time from the declared type of the expression. Nothing is looked up at run time.

Failure modes

  • A member always wins. If a library later adds a member with the same name and parameters, your extension stops being called and nothing warns you.
  • Static dispatch. With extensions on both a base type and a subtype, the one called depends on the variable's declared type, not the object's actual class.
  • Nested scope functions. Inside an apply inside an apply, name = name assigns a property to itself.
  • ?.let { } ?: run { } used as if/else. If the let block itself returns null, the run block executes too.
  • Extensions on very general types. A public extension on String or Any appears in autocomplete everywhere and collides with someone else's.

Trade-offs and when not to use it

Write a member when the function needs private state or is part of what the type means, and you own the type. Write an extension when it is one layer's view of the type: display formatting belongs to the UI, so the domain class stays free of it. Builders are pleasant to read and tedious to write and debug; build one when the same structure appears dozens of times, not twice.

Production and security

An extension cannot reach anything the caller could not already reach, so it exposes nothing new. Keep extensions private or internal unless other modules need them. In review, treat scope functions nested more than one level deep as a readability defect; a linter such as detekt can enforce it.

Generics and delegation

Writing one type for many, variance without wildcards, and handing work to another object with by.

Why it exists

A result of a network call has the same shape whether it carries a balance or a list of payees. Java's generics express that, with wildcards (? extends T) at every use and no type information at run time. Separately, some patterns are pure repetition: compute once on first use, notify on change, forward every call to a wrapped object.

In Kosh, generics describe API results and repositories, and by appears wherever Android hands you a delegate: by viewModels(), by preferencesDataStore(…), by remember { mutableStateOf(…) }.

Mental model

out T means the type only hands T back, so a result of Int can stand in for a result of Any. by means another object does this for me.

Mechanics

Generics, variance and reified types

sealed interface ApiResult<out T> {                                  // out: this type only hands T back
    data class Ok<T>(val value: T) : ApiResult<T>
    data class Failed(val reason: String) : ApiResult<Nothing>       // Nothing fits every T
}

fun <T, R> ApiResult<T>.map(transform: (T) -> R): ApiResult<R> = when (this) {
    is ApiResult.Ok -> ApiResult.Ok(transform(value))
    is ApiResult.Failed -> this
}

fun <T : Comparable<T>> largest(items: List<T>): T? = items.maxOrNull()      // T must be comparable

inline fun <reified T> List<Any>.firstOf(): T? = firstOrNull { it is T } as T?   // reified: T exists at run time

fun main() {
    val r: ApiResult<Int> = ApiResult.Ok(25_000)
    val wider: ApiResult<Any> = r                          // allowed because of `out`
    println(r.map { it / 100 })                            // Ok(value=250)
    println(wider is ApiResult.Ok)                         // true
    println(largest(listOf("Ravi", "Asha")))               // Ravi
    println(listOf<Any>(1, "KX-1", 2.5).firstOf<String>()) // KX-1
}

Variance is declared once, on the type. out marks a producer; in marks a consumer, such as Comparator<in T>. Nothing is a subtype of everything, which is why one Failed fits every ApiResult<T>.

Delegation

import kotlin.properties.Delegates

interface Logger { fun log(message: String) }
class ConsoleLogger : Logger { override fun log(message: String) = println("[kosh] $message") }

class TransferService(logger: Logger) : Logger by logger {          // every Logger call is forwarded to `logger`
    val limits: Map<String, Long> by lazy {                         // computed once, on first read; thread-safe
        log("loading limits")
        mapOf("UPI" to 10_000_000L, "IMPS" to 50_000_000L)
    }

    var status: String by Delegates.observable("idle") { _, old, new -> log("$old -> $new") }
}

class Config(values: Map<String, Any?>) {
    val apiBase: String by values                                   // reads values["apiBase"]
    val timeoutMs: Int by values
}

fun main() {
    val service = TransferService(ConsoleLogger())
    service.status = "sending"                                      // [kosh] idle -> sending
    println(service.limits["UPI"])                                  // [kosh] loading limits, then 10000000
    println(service.limits["IMPS"])                                 // 50000000; not loaded again
    println(Config(mapOf("apiBase" to "https://api.kosh.example", "timeoutMs" to 20_000)).timeoutMs)
}

End-to-end flow: the first read of a lazy property

  1. The compiler turns val limits by lazy { … } into a hidden Lazy object and a getter that asks it for its value.
  2. On the first read the Lazy takes a lock, runs the block, logs "loading limits" and stores the map.
  3. On the second read it returns the stored map. The block does not run again.
  4. Had the block thrown, nothing would have been stored and the next read would try again.

Failure modes

  • Type erasure. x is List<String> does not compile, and x as List<String> succeeds for any list, then fails later where an element is used.
  • Variance errors. "Type parameter T is declared as 'out' but occurs in 'in' position" means a producer is trying to accept a T.
  • lazy that captures a view. In a fragment, a lazy property computed from the view keeps pointing at the old view after the view is recreated.
  • Class delegation is not inheritance. Methods of the wrapped object that call each other do not go through your overrides.
  • Map-backed properties. A missing key throws when the property is read, and a wrong type throws a ClassCastException.
  • reified from Java. Inline functions with reified type parameters cannot be called from Java.

Trade-offs and when not to use it

Make something generic when two concrete versions already exist and are the same. A BaseRepository<T, ID> written before the second repository usually fits neither. Prefer by over inheritance for wrappers and decorators. Custom property delegates can hide disk or network access behind what looks like a field read; keep delegates for cheap operations.

Production and security

An unchecked cast on data from outside (a deserialised object, a Bundle extra) is a crash another app can trigger. Check the type with as? and handle the null.

Serialisers that read generic types by reflection need the generic signatures to survive R8. Generated serialisers avoid the problem.

Errors and results

Exceptions without checked exceptions, and returning outcomes the caller must handle.

Why it exists

Java's checked exceptions were meant to make failure visible in signatures. In practice they produced empty catch blocks and throws Exception. Kotlin has no checked exceptions at all, which removes the noise and raises a question: how does a caller know what can go wrong?

The answer used throughout Kosh is a convention. A declined transfer is not an exception; it is one of the things a transfer can do.

Mental model

If the caller is expected to handle it, return it. If nobody can sensibly handle it, throw it.

Mechanics

Throwing and catching

import java.io.File

class InsufficientFunds(val shortByMinor: Long) : Exception("Short by $shortByMinor")

fun withdraw(balanceMinor: Long, amountMinor: Long): Long {
    require(amountMinor > 0) { "Amount must be positive" }        // IllegalArgumentException: the caller is wrong
    check(balanceMinor >= 0) { "Balance is already negative" }    // IllegalStateException: we are wrong
    if (amountMinor > balanceMinor) throw InsufficientFunds(amountMinor - balanceMinor)
    return balanceMinor - amountMinor
}

fun parseAmount(text: String): Long? = try {                      // try is an expression
    text.trim().toBigDecimal().movePointRight(2).longValueExact()
} catch (e: NumberFormatException) {
    null
} catch (e: ArithmeticException) {
    null
}

fun firstLine(path: String): String? =
    File(path).bufferedReader().use { it.readLine() }             // use: closed on success and on failure

fun main() {
    println(parseAmount("250.50"))                                // 25050
    println(parseAmount("2.505"))                                 // null: more than two decimals
    val outcome = runCatching { withdraw(10_000, 25_000) }        // a Result<Long>
    println(outcome.exceptionOrNull()?.message)                   // Short by 15000
    println(outcome.getOrElse { 0 })                              // 0
}

require is for arguments, check is for state. try has a value, so there is no need for a variable assigned in two branches. runCatching wraps a block in a Result.

Outcomes as types

sealed interface WithdrawResult {
    data class Done(val newBalanceMinor: Long) : WithdrawResult
    data class Short(val byMinor: Long) : WithdrawResult
    data object InvalidAmount : WithdrawResult
}

fun withdraw(balanceMinor: Long, amountMinor: Long): WithdrawResult = when {
    amountMinor <= 0 -> WithdrawResult.InvalidAmount
    amountMinor > balanceMinor -> WithdrawResult.Short(amountMinor - balanceMinor)
    else -> WithdrawResult.Done(balanceMinor - amountMinor)
}

fun render(r: WithdrawResult): String = when (r) {       // every caller must handle every outcome
    is WithdrawResult.Done -> "New balance ${r.newBalanceMinor}"
    is WithdrawResult.Short -> "Short by ${r.byMinor}"
    WithdrawResult.InvalidAmount -> "Enter an amount"
}

fun main() = println(render(withdraw(10_000, 25_000)))   // Short by 15000

The second withdraw cannot surprise its caller: every outcome is in the return type.

End-to-end flow: "not enough balance", from the domain to the screen

  1. withdraw returns Short(15000).
  2. The use case passes it on unchanged.
  3. The state holder maps it to screen state with a when that the compiler checks.
  4. The screen shows "Short by ₹150.00".

There is no try anywhere on that path. Now pull the network cable: the HTTP client throws an IOException, the data layer catches it once, at the boundary, and converts it into a result such as Unreachable. Exceptions are translated at the edge and do not travel through the app. The networking chapter of the Android book builds that boundary.

Failure modes

  • Catching Exception in suspending code. It also catches CancellationException, so a cancelled coroutine carries on. Catch the specific type, or rethrow cancellation. runCatching has the same problem.
  • Catch-all blocks. A NullPointerException becomes "Something went wrong" and the bug is never seen.
  • Exceptions for expected cases. They are invisible in the signature, so the next caller forgets them.
  • Losing the cause. When wrapping, pass the original as cause.
  • An uncaught exception in launch. On Android it reaches the default handler and the app closes.

Trade-offs and when not to use it

Sealed results cost a mapping at every layer. Pay that for outcomes a user will see: declined, insufficient, pending. Do not pay it for programmer errors; an illegal argument should throw and be fixed. Result and runCatching are convenient for wrapping one throwing call at a boundary, and they reduce every failure to a bare Throwable.

Production and security

Exception messages are written for developers. Shown to a user or copied into a log, they can carry SQL, file paths or a URL with a token in it. Map failures to user-facing text deliberately, and redact what you log.

Fail closed. runCatching { verify(signature) }.getOrDefault(true) approves everything whenever verification itself breaks.

Coroutines

Suspending functions, scopes, dispatchers and cancellation.

Why it exists

An Android app has one main thread, and it must finish its work for each frame in a few milliseconds. Network and disk calls take hundreds. The older answers were a thread plus a callback, which nests badly and has no way to stop work for a screen that has gone, and RxJava, which is powerful and a language of its own.

Coroutines let you write the slow call as an ordinary line of code that waits without occupying a thread. In Kosh every repository function is one.

Mental model

A suspending function can pause without holding a thread and continue later. A scope owns the coroutines started in it: cancel the scope and all of them stop.

Mechanics

suspend, async and structured concurrency

import kotlinx.coroutines.*

suspend fun fetchBalance(): Long { delay(300); return 1_248_050 }         // waits without holding a thread
suspend fun fetchRecent(): List<String> { delay(200); return listOf("t1", "t2") }

suspend fun loadHome(): String = coroutineScope {                         // returns when all its children are done
    val balance = async { fetchBalance() }                                // starts now
    val recent = async { fetchRecent() }                                  // runs at the same time
    "${balance.await()} ${recent.await()}"                                // if either fails, the other is cancelled
}

fun main() = runBlocking {                                                // lets a plain main() call suspend code
    val start = System.currentTimeMillis()
    println(loadHome())
    println("about ${(System.currentTimeMillis() - start) / 100 * 100} ms")   // about 300, not 500
}

A suspend function may only be called from another one, or from a coroutine. launch starts a coroutine that returns nothing; async starts one that returns a value through await. runBlocking exists for main functions and tests. Do not call it from app code.

Cancellation is cooperative

import kotlinx.coroutines.*

fun main() = runBlocking {
    val job = launch {
        try {
            repeat(10) { i -> println("poll $i"); delay(100) }           // delay is a cancellation point
        } finally {
            println("cleaning up")                                        // runs on cancellation as well
        }
    }
    delay(250)
    job.cancelAndJoin()                                                   // ask it to stop, then wait until it has
    println("cancelled: ${job.isCancelled}")

    val rates = withTimeoutOrNull(200) { delay(1_000); "rates" }          // null when the time budget runs out
    println(rates)
}

Dispatchers decide the thread

import kotlinx.coroutines.*
import java.io.File

class StatementStore(private val io: CoroutineDispatcher = Dispatchers.IO) {
    /** Main-safe: call it from any thread. The blocking read runs on the IO pool. */
    suspend fun read(path: String): String = withContext(io) { File(path).readText() }
}

suspend fun checksum(bytes: ByteArray): Int = withContext(Dispatchers.Default) {   // CPU work: the Default pool
    var sum = 0
    for (b in bytes) {
        ensureActive()                       // a loop with no suspension must check for cancellation itself
        sum = sum * 31 + b
    }
    sum
}

fun main() = runBlocking { println(checksum("KX-88213".toByteArray())) }

Dispatchers.Main is the UI thread, IO is a pool for blocking calls and Default is a pool sized to the CPU. A function is main-safe when it moves itself to the right dispatcher, so callers never have to think about threads. Passing the dispatcher in, as StatementStore does, lets a test replace it.

When one child may fail

import kotlinx.coroutines.*
import java.io.IOException

suspend fun balance(): String { delay(50); return "₹12,480.50" }
suspend fun offers(): String { delay(50); throw IOException("offers are down") }

suspend fun dashboard(): String = supervisorScope {       // a failing child does not cancel its siblings
    val essential = async { balance() }
    val optional = async { offers() }
    val offersText = try { optional.await() } catch (e: IOException) { "no offers today" }
    "${essential.await()} · $offersText"
}

fun main() = runBlocking { println(dashboard()) }         // ₹12,480.50 · no offers today

            }

End-to-end flow: a tap on Refresh

  1. The click calls refresh() on the main thread.
  2. viewModelScope.launch starts a coroutine on the main dispatcher.
  3. accounts.balance() suspends. Inside the repository, withContext(Dispatchers.IO) runs the network call on an IO thread. The main thread is free to draw.
  4. The response arrives. The coroutine continues on the main thread and assigns the new state.
  5. If the user had left and the view model was cleared during step 3, the scope would be cancelled, the suspended call would throw CancellationException, and nothing would be assigned.

Failure modes

  • Blocking the main thread inside a coroutine. The suspend keyword does not make code non-blocking. Thread.sleep or a blocking read on the main dispatcher freezes the app.
  • Coroutines nobody owns. GlobalScope.launch, or a CoroutineScope that is never cancelled, keeps running after the screen is gone.
  • Swallowing CancellationException. A broad catch turns a cancelled coroutine into a running one.
  • A loop that never suspends. It cannot be cancelled unless it calls ensureActive() or yield().
  • runBlocking on the main thread. A freeze, and sometimes a deadlock.
  • Shared mutable state. Two coroutines on Dispatchers.Default run on different threads. Use a Mutex, confine the state to one dispatcher, or use MutableStateFlow.update.

Trade-offs and when not to use it

Coroutines are cheaper than threads and easier to read than callbacks. The rules for cancellation and exceptions are subtle, and getting them wrong produces bugs that appear only under load or on slow networks. Suspending functions are awkward to call from Java. And they are not a way to make CPU work faster: Dispatchers.Default has as many threads as the device has cores.

Work that must finish after the user leaves the app does not belong in a coroutine scope. Hand it to WorkManager.

Production and security

Inject dispatchers so tests can run on virtual time. Put a timeout on every network call. Cancellation can stop a multi-step operation halfway, so make the steps idempotent, and wrap clean-up that must complete in withContext(NonCancellable). The coroutines chapter of the Android book applies all of this to repositories and view models.

Flow

Values over time: cold flows, StateFlow, and collecting safely.

Why it exists

A suspending function returns once. A screen needs more than that: the balance changes, search results arrive as the user types, the connection comes and goes. Before Flow the tools were listeners, LiveData and RxJava.

In Kosh, the database emits a new list whenever a row changes, the state holder turns it into screen state, and the UI collects it.

Mental model

A flow is a suspending function that can return many times. A cold flow does nothing until someone collects it. A StateFlow is hot: it always holds the latest value.

Mechanics

A cold flow and its operators

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun prices(): Flow<Int> = flow {                 // cold: the block runs once per collector, when collected
    var price = 100
    while (true) { emit(price); delay(100); price += 5 }
}

fun main() = runBlocking {
    prices()
        .map { it * 100 }                        // operators describe a new flow; nothing has run yet
        .filter { it % 1_000 == 0 }
        .take(3)                                 // cancels the loop upstream after three values
        .collect { println(it) }                 // collecting starts everything: 10000, 11000, 12000
}

State from a stream

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import java.io.IOException

data class UiState(val query: String = "", val results: List<String> = emptyList())

class SearchModel(scope: CoroutineScope, private val search: suspend (String) -> List<String>) {
    private val query = MutableStateFlow("")                    // hot: it always holds a current value
    fun onQueryChange(text: String) { query.value = text }

    @OptIn(FlowPreview::class, ExperimentalCoroutinesApi::class)
    val state: StateFlow<UiState> = query
        .debounce(300)                                          // wait until typing pauses
        .distinctUntilChanged()
        .mapLatest { q ->                                       // a newer query cancels the older search
            val found = if (q.length < 2) emptyList()
                        else try { search(q) } catch (e: IOException) { emptyList() }   // one failure must not end the flow
            UiState(q, found)
        }
        .stateIn(scope, SharingStarted.WhileSubscribed(5_000), UiState())
}

fun main() = runBlocking {
    val payees = listOf("Asha", "Ashok", "Ravi")
    val modelScope = CoroutineScope(Dispatchers.Default)
    val model = SearchModel(modelScope) { q -> delay(50); payees.filter { it.startsWith(q, ignoreCase = true) } }

    val screen = launch { model.state.collect { println(it) } }
    model.onQueryChange("a"); model.onQueryChange("as"); model.onQueryChange("ash")
    delay(700)                                                  // one search runs, for "ash"
    screen.cancel(); modelScope.cancel()
}

stateIn turns a cold chain into a StateFlow. WhileSubscribed(5_000) keeps the chain alive for five seconds after the last collector leaves, long enough to survive a rotation and short enough to stop work for a screen that has really gone.

End-to-end flow: typing "ash" into payee search

Run the SearchModel sample and it prints two lines: the initial empty state and the result for "ash". Here is why there are not four:

  1. Three calls set query.value to "a", "as" and "ash" within a millisecond.
  2. debounce(300) holds each value until 300 ms pass with no newer one. Only "ash" gets through.
  3. mapLatest starts the search. Had another query arrived, this search would have been cancelled.
  4. The result becomes a UiState. stateIn stores it and hands it to the collector.

Failure modes

  • Collecting without the lifecycle. A plain lifecycleScope.launch { flow.collect { } } keeps collecting while the screen is in the background.
  • catch downstream of the work. A flow that throws is finished. A catch after mapLatest emits a fallback once and then the stream is over. Handle the failure inside the block, as the sample does.
  • Mutating instead of replacing. StateFlow ignores a value equal to the current one. Add to a list in place and nothing is emitted.
  • Events in a SharedFlow with no replay. An event emitted while nothing is collecting is lost. Model it as state the screen acknowledges.
  • A new chain on every call. fun state() = repo.observe().stateIn(…) builds another pipeline each time. Make it a property.
  • Emitting from another context. Calling emit inside withContext in a flow { } block throws. Use flowOn.

Trade-offs and when not to use it

If there is one answer, use a suspending function; a flow with a single emission is harder to call and to test. Flow has fewer operators than RxJava and that is mostly a benefit. Hot flows need care in tests, where a helper library such as Turbine earns its place. LiveData remains fine in an existing View-based app.

Production and security

Expose StateFlow and keep the MutableStateFlow private, so only the owner can write. Collect with the lifecycle. Remember that a hot flow holds its last value in memory for as long as its scope lives: a view model that kept card details in state still has them after the screen closes. Clear sensitive state on sign-out.

Kotlin with Java and the Android SDK

Calling Java from Kotlin, being called from Java, and what the SDK's types look like from here.

Why it exists

The Android SDK is a Java API. So are most libraries, and so, perhaps, is the app you are joining. Kotlin was adopted on Android because it could be added one file at a time, with each language calling the other. That interoperability is very good and not quite free.

In Kosh the boundary runs along the platform layer and through every Java library in the data layer.

Mental model

Calling Java from Kotlin costs almost nothing, except that Java types arrive with unknown nullability. Calling Kotlin from Java works, and reads well once you add a few @Jvm annotations.

Mechanics

Kotlin calling Java

End-to-end flow: a click listener

  1. setOnClickListener is a Java method that takes View.OnClickListener, an interface with one method.
  2. The compiler accepts the lambda and generates an object that implements the interface.
  3. On a tap the framework calls onClick(view) on that object, which runs the lambda body.

Failure modes

  • Unannotated Java. A library without nullability annotations gives you platform types. Assign one to a non-null type and a null from Java throws on that line.
  • Null from Java into Kotlin. Kotlin checks non-null parameters of public functions on entry. A Java caller that passes null gets a NullPointerException naming the parameter.
  • Exceptions Java cannot catch. Without @Throws, javac rejects a catch (IOException e) around a Kotlin call.
  • Read-only lists in Java hands. A Kotlin List passed to Java is a java.util.List, and Java may call add on it.
  • Kotlin keywords as Java names. A Java method called when or in needs backticks: Mockito.`when`(…).
  • Converted code that was never reviewed. The automatic Java-to-Kotlin converter produces Java-shaped Kotlin full of !!.

Trade-offs and when not to use it

Write new code in Kotlin, and convert a Java file when you are already changing it and it has tests. Converting a stable file for its own sake risks regressions for no user-visible gain. Keep the surface that Java calls small, because every annotation on it is a compromise made for the other language. If the team and the codebase are staying in Java, the Java edition of the Android book describes that path and what it gives up.

Production and security

Treat every platform type and every value from another app as nullable until checked. internal declarations are public in the bytecode, so Java code in another module can call them; do not rely on internal to hide anything from Java.

For a library with Java consumers, the generated names are part of your binary interface. Renaming a file renames its class.

Capstone: a ledger in pure Kotlin

Every part of the language in one small, tested piece of Kosh.

Why it exists

Mental model

Model the domain with types first. When the types are right, most functions are short and most wrong calls do not compile.

Mechanics

The ledger

import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow

@JvmInline value class AccountId(val raw: String)

data class Money(val minor: Long, val currency: String = "INR") : Comparable<Money> {
    operator fun plus(other: Money) = copy(minor = Math.addExact(minor, same(other).minor))        // overflow throws
    operator fun minus(other: Money) = copy(minor = Math.subtractExact(minor, same(other).minor))
    override fun compareTo(other: Money) = minor.compareTo(same(other).minor)
    private fun same(other: Money) = other.also { require(it.currency == currency) { "$currency vs ${it.currency}" } }

    companion object {
        val ZERO = Money(0)

        /** Null for anything that is not a positive amount with at most two decimals. */
        fun parse(text: String): Money? =
            text.trim().replace(",", "").toBigDecimalOrNull()
                ?.takeIf { it.signum() > 0 && it.scale() in 0..2 }       // 0..2 also rejects "1e2"
                ?.let { runCatching { it.movePointRight(2).longValueExact() }.getOrNull() }
                ?.let { Money(it) }
    }
}

fun Money.format(): String =
    (if (minor < 0) "−" else "") + "₹${abs(minor) / 100}.${(abs(minor) % 100).toString().padStart(2, '0')}"

sealed interface Entry {
    val id: String
    data class Credit(override val id: String, val from: String, val amount: Money) : Entry
    data class Debit(override val id: String, val to: String, val amount: Money) : Entry
}

sealed interface PostResult {
    data class Posted(val balance: Money) : PostResult
    data class Refused(val reason: String) : PostResult
    data object Duplicate : PostResult
}

fun interface LimitsPolicy { fun check(amount: Money): String? }      // null means "allowed"

class Ledger(val account: AccountId, private val limits: LimitsPolicy = LimitsPolicy { null }) {
    private val _entries = MutableStateFlow<List<Entry>>(emptyList())
    val entries: StateFlow<List<Entry>> = _entries.asStateFlow()      // observers see every change

    val balance: Money
        get() = _entries.value.fold(Money.ZERO) { sum, e ->
            when (e) {
                is Entry.Credit -> sum + e.amount
                is Entry.Debit -> sum - e.amount
            }
        }

    fun post(entry: Entry): PostResult {
        if (_entries.value.any { it.id == entry.id }) return PostResult.Duplicate   // the id is an idempotency key
        if (entry is Entry.Debit) {
            limits.check(entry.amount)?.let { return PostResult.Refused(it) }
            if (entry.amount > balance) return PostResult.Refused("Not enough balance")
        }
        _entries.update { it + entry }                                // a new list; the old one is never changed
        return PostResult.Posted(balance)
    }
}

fun main() {
    val ledger = Ledger(AccountId("SB-1001")) { if (it > Money(10_000_000)) "Above the daily limit" else null }
    val amount = Money.parse("2,500.00") ?: return

    println(ledger.post(Entry.Debit("e2", "Asha", amount)))

    println(ledger.post(Entry.Debit("e3", "Ravi", Money(90_000_000)))) // Refused(reason=Above the daily limit)
    println(ledger.balance.format())                                   // ₹82500.00
}

End-to-end flow: posting the same debit twice

  1. post(Debit("e2", …)) checks for an existing entry with that id. There is none.
  2. The limits policy returns null, meaning allowed.
  3. entry.amount > balance calls compareTo, which first checks that the currencies match.
  4. update swaps in a new list with the entry appended, and the StateFlow notifies its collectors.
  5. The function returns Posted with a balance folded from the entries. The balance is never stored separately, so it cannot disagree with them.
  6. The second post with id "e2" finds the entry at step 1 and returns Duplicate. Nothing changes.

Failure modes

This design has limits, and you should know them:

  • post is not thread-safe. It checks and then acts. Two threads posting the same id at once can both pass the duplicate check. update makes only the list swap atomic. Confine the ledger to one dispatcher or guard post with a Mutex.
  • balance walks every entry on each read. Fine for hundreds of entries, wrong for a hundred thousand.
  • It lives in memory. Process death empties it. Persistence is the subject of the Room chapter of the Android book.
  • The duplicate check trusts the caller. It only works if a retry reuses the id of the original attempt.

Trade-offs and when not to use it

Types-first design costs time before the first feature works. It can also be overdone: not every String needs its own class. Wrap identifiers and money, the values you could swap by accident and regret. Leave a display label as a String.

Production and security

A ledger on a phone is a cache and a queue of intentions. The server decides balances and enforces limits; the checks here exist so the user gets an answer quickly, and anyone with the APK can remove them. Never treat a client-side check as a control.

Practice

  • Lab. Make post safe to call from several coroutines, and write a test that fails without your change.
  • Investigate. Replace scale() in 0..2 with scale() <= 2 and run the tests. Explain the failure.
  • Challenge. Add reversals: an entry that cancels an earlier one. Decide what the types must forbid.
