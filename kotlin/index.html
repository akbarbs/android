I · Foundations · Chapter 1

Why Android is shaped this way

A phone is a hostile place to run software. Every odd rule in Android follows from that.

Why it exists

A server gets steady power, plenty of memory, and software its owner chose. A phone has a battery, a few gigabytes shared by dozens of apps, and code from strangers. The user also switches apps every few seconds and expects each to be exactly where they left it.

Desktop operating systems answered this badly for mobile: a process started by main() lived until the user quit it. Android inverted the contract. The system owns your process. It starts your process when something needs it and kills it when memory runs short, without asking.

Mental model

Your app is a guest in someone else's house. The system invites it in for a reason (a component), and can ask it to leave at any time.

Three consequences shape everything else in this book:

  1. No main(). You declare entry points called components. The system instantiates them.
  2. A sandbox per app. Each app runs as its own Linux user. Apps cannot read each other's files or memory.
  3. Everything crosses a process boundary through Binder. Starting a screen, reading contacts and showing a notification are all remote calls to system services.

Mechanics

The stack, bottom to top:

Layer What it does You meet it when
Linux kernel Processes, memory, drivers, Binder IPC, per-app UIDs You hit a permission or memory limit
HAL and native libraries Camera, sensors, graphics, media You use hardware
ART (Android Runtime) Runs DEX bytecode. Combines an interpreter, JIT, and profile-guided ahead-of-time compilation You measure startup
Framework and system_server Activity, window, package and notification managers Every API call
Your app One or more processes forked from Zygote Always

Zygote is a process that boots once with the framework classes preloaded. Each new app is a fork() of Zygote, so apps start fast and share memory pages for common code.

The main thread. Each app process has one main thread running a Looper that drains a message queue. Input events, lifecycle callbacks and drawing all run there, in order. Block it and the app freezes. If input goes unhandled for about five seconds the system shows an Application Not Responding dialog (ANR).

The map used in this book

Layer Responsibility in Kosh Typical classes
Platform Process, components, lifecycle, permissions Activity, Service, manifest
UI Draw state, emit user events Composables, Views
State holder Hold screen state, survive rotation, call the domain ViewModel
Domain Business rules that are not about Android Use cases, plain Kotlin
Data Decide where data comes from; one source of truth Repositories, Room, DataStore

Dependencies point right to left in the strip: UI knows the state holder, the state holder knows the domain, and so on. Data never knows about UI.

End-to-end flow: tapping the Kosh icon

  1. The launcher (itself an app) sends an Intent through Binder to system_server.
  2. The activity manager resolves which activity matches and sees that no Kosh process exists.
  3. It asks Zygote to fork. The child becomes the Kosh process under Kosh's UID.
  4. ActivityThread.main() starts the main Looper and attaches to the system.
  5. The system tells the process to create Application, then the launch Activity. onCreate() runs and sets the UI content.
  6. On the next vsync, the Choreographer runs measure, layout and draw. The frame goes to SurfaceFlinger, which composites it to the display.

Steps 3 to 6 are a cold start. Chapter 26 shows how to measure and shorten it.

Failure modes

  • Main-thread work. Disk or network on the main thread causes dropped frames, then ANRs.
  • Process death. The user leaves Kosh for a camera app, memory runs low, Kosh is killed. When they return, the system recreates the screen but every in-memory object is gone. Chapter 5 is about surviving this.
  • TransactionTooLargeException. Binder transactions share a buffer of about 1 MB per process. Passing a large list through an Intent crashes at runtime, often only on some devices.
  • Assuming you are running. Timers, sockets and threads stop when the process is frozen or killed.

Trade-offs and when not to go native

Option Choose it when Cost
Native Android (Kotlin, Compose) You need platform depth: security hardware, background work, performance, newest APIs A second codebase for iOS
Kotlin Multiplatform You want shared business logic and native capability on both platforms Build complexity, iOS tooling friction
Flutter, React Native A UI-heavy app, one team, modest platform integration Bridges for platform features, larger binaries, lag behind new OS APIs
A web app Content and forms, no hardware, instant updates matter more than polish Weak background work and offline, no hardware-backed key storage API as on native

For a regulated wallet, hardware-backed keys, biometrics and attestation push strongly toward native or KMP.

Production and security

The sandbox is your first control. Data in your app's private directory is unreadable to other apps on an unrooted device. Everything you export (components, files, links) is attack surface. Later chapters keep returning to one question: what did we just expose outside our UID?

  • Investigate. Run adb shell dumpsys activity processes and find the oom_adj ordering. Which processes die first?

Kotlin for people who know Java

The parts of Kotlin that Android leans on, and the Java habits to drop.

Why it exists

Android's Java was stuck for years on old language levels, and NullPointerException was the most common crash on the platform. Kotlin runs on the same bytecode, calls Java freely, and puts nullability in the type system. Google made Android Kotlin-first in 2019. Jetpack Compose is a Kotlin compiler plugin and cannot be written in Java at all.

Mental model

Kotlin is Java with the ceremony removed and three additions that matter: nullable types, functions as values, and suspending functions.

Mechanics

Nullability is a type

val name: String = "Kosh"      // can never be null
val nick: String? = null       // may be null

val len = nick?.length ?: 0    // safe call, then default
val sure = nick!!.length       // "trust me"; throws if wrong

val is a final reference, var is mutable. Prefer val.

Data, sealed and value classes

data class Money(val minor: Long, val currency: String)   // equals, hashCode, copy for free

sealed interface TransferResult {
    data class Success(val reference: String) : TransferResult
    data class Declined(val reason: String) : TransferResult
    data object NetworkError : TransferResult
}

fun message(r: TransferResult): String = when (r) {       // compiler checks every case is handled
    is TransferResult.Success -> "Sent. Ref ${r.reference}"
    is TransferResult.Declined -> "Declined: ${r.reason}"
    TransferResult.NetworkError -> "Check your connection"
}

@JvmInline value class AccountId(val raw: String)         // a type-safe wrapper with no allocation

Sealed types plus an exhaustive when are how this book models screen state and results. Add a case and the compiler lists every place to update.

Functions as values and trailing lambdas

fun retry(times: Int, block: () -> Unit) { repeat(times) { block() } }

retry(3) { println("try") }          // last lambda parameter moves outside the parentheses

That syntax is why Compose UI code looks like a nested document: Column { Text("Hi") } is a function call whose last argument is a lambda.

Extension functions and lambdas with receivers

fun Long.asRupees(): String = "₹%,.2f".format(this / 100.0)
12_500L.asRupees()                   // "₹125.00"

fun buildNote(block: StringBuilder.() -> Unit): String = StringBuilder().apply(block).toString()

StringBuilder.() -> Unit is a lambda where this is a StringBuilder. Gradle's Kotlin DSL and Compose scopes such as RowScope are built from it.

Scope functions, briefly

let transforms a non-null value (token?.let { send(it) }). apply configures an object and returns it. also runs a side effect. run and with exist; you can live without them.

Other things you will meet

Default and named arguments replace builder classes. object declares a singleton. companion object holds what Java would make static. Properties replace getters and setters. by lazy { } computes on first use.

Worked code: a money type

One small file that uses most of the chapter: a data class, a companion factory, operator overloading with a guard, null-returning parsing and an extension property.

data class Money(val minor: Long, val currency: String = "INR") : Comparable<Money> {

    operator fun plus(other: Money): Money {
        require(currency == other.currency) { "Cannot add $currency to ${other.currency}" }
        return copy(minor = Math.addExact(minor, other.minor))        // overflow throws, never wraps
    }

    operator fun minus(other: Money): Money = this + other.copy(minor = -other.minor)

    override fun compareTo(other: Money): Int {
        require(currency == other.currency)
        return minor.compareTo(other.minor)
    }

    companion object {
        /** Returns null for anything that is not a positive amount with at most two decimals. */
        fun parse(text: String, currency: String = "INR"): Money? =
            text.trim().replace(",", "").toBigDecimalOrNull()
                ?.takeIf { it.signum() > 0 && it.scale() <= 2 }
                ?.movePointRight(2)?.longValueExact()
                ?.let { Money(it, currency) }
    }
}

val Money.isLarge: Boolean get() = minor >= 5_000_000        // ₹50,000 and above needs step-up

fun demo() {
    val balance = Money.parse("12,480.50") ?: return
    val fee = Money(250)
    val after = balance - fee
    println(if (after > Money(0)) "ok: ${after.minor.asRupees()}" else "insufficient")
}

End-to-end flow: a Java type, rewritten

A Java Transfer class with a builder, null checks and a status enum with a payload map becomes: one data class with default arguments, non-null types, and a sealed TransferResult. About 120 lines become 15, and the null checks become compile errors at the call site instead of crashes in the field.

Failure modes

  • !! everywhere. It converts a compile-time guarantee back into a runtime crash. Treat each one as a code review comment.
  • Platform types. A Java method without nullability annotations returns String!, which Kotlin will not check. Annotate Java code or assign to an explicit String?.
  • lateinit abuse. Reading before assignment throws. Prefer constructor injection.
  • Mutable data class as a map key. Changing a var changes hashCode().
  • Scope function soup. Three nested let/run/apply blocks hide which it and this you mean.

Trade-offs and when not to use it

Kotlin compiles more slowly than Java, though the K2 compiler narrowed the gap. Clever DSLs and operator overloading are easy to write and hard to read. Keep Java for existing stable modules; mixed projects work well and file-by-file migration is routine. There is no good reason to start a new Android module in Java.

Production and security

Money is never Double. Use Long minor units or BigDecimal, and a distinct type so rupees cannot be added to dollars. Mark secrets-bearing data classes carefully: a data class generates toString() that prints every field into your logs. Override it for anything holding tokens or card data.

Practice

  • Lab. Model a card payment's states as a sealed interface. Add a RequiresStepUp case and let the compiler find the when blocks.
  • Lab. Write inline fun <T> measure(label: String, block: () -> T): T and use it with a trailing lambda.
  • Investigate. Use Tools → Kotlin → Show Kotlin Bytecode → Decompile on a data class. Count the generated methods.

Project anatomy and the build

What is in an Android project, and how source becomes an installable, signed app.

Why it exists

An Android app is not a JAR. It is compiled code in a different bytecode format, compiled resources for many screen sizes and languages, a manifest the OS reads before running anything, and a signature that fixes the app's identity forever. Gradle with the Android Gradle Plugin (AGP) drives that pipeline.

Mental model

The build takes one source tree and produces many variants (debug, release, per-flavour), each a signed package whose manifest tells the OS what the app is allowed to be.

Mechanics

kosh/
├── settings.gradle.kts        which modules exist, where plugins come from
├── gradle/libs.versions.toml  one place for every version
├── app/
│   ├── build.gradle.kts
│   └── src/main/
│       ├── AndroidManifest.xml
│       ├── kotlin/…           code
│       └── res/…              layouts, strings, drawables, by qualifier
└── core/, feature/            library modules (chapter 24)

# gradle/libs.versions.toml
[versions]
agp = "9.2.1"            # check current releases before pinning
kotlin = "2.4.20"

[plugins]
android-application = { id = "com.android.application", version.ref = "agp" }
kotlin-compose = { id = "org.jetbrains.kotlin.plugin.compose", version.ref = "kotlin" }

// app/build.gradle.kts
plugins {
    alias(libs.plugins.android.application)
    alias(libs.plugins.kotlin.compose)      // Compose compiler plugin
}

android {
    namespace = "com.kosh.app"
    compileSdk = 37

    defaultConfig {
        applicationId = "com.kosh.app"
        minSdk = 26
        targetSdk = 37
        versionCode = 42          // integer the Play Store compares
        versionName = "1.8.0"     // what users see
    }
    buildTypes {
        release {
            isMinifyEnabled = true
            isShrinkResources = true
            proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")
        }
    }
    buildFeatures { compose = true }
}

AGP 9 compiles Kotlin itself ("built-in Kotlin"), so the old org.jetbrains.kotlin.android plugin is no longer applied in new projects.

Three SDK numbers

Setting Meaning Rule of thumb
compileSdk Which API surface you compile against Latest stable
targetSdk Which OS behaviour changes you have opted into Raise once a year after testing. Google Play requires a recent target
minSdk Oldest OS that can install the app Decide from your users' devices, not habit

Raising targetSdk is where platform changes actually bite: edge-to-edge drawing, background limits, and from API 37 mandatory resizability on large screens.

Resources and qualifiers

res/values/strings.xml and res/values-hi/strings.xml hold the same keys. The system picks by device configuration. The same mechanism selects night colours (values-night), density-specific images and width-specific layouts.

Build types, flavours, variants

Build types (debug, release) differ in how the app is built. Product flavours (dev, prod) differ in what is built: endpoints, app id suffix. A variant is one of each: devDebug, prodRelease.

Worked code: settings, flavours and signing

End-to-end flow: from ./gradlew assembleRelease to a phone

  1. Kotlin and Java compile to .class files. KSP runs annotation processors such as Room and Hilt first.
  2. AAPT2 compiles resources and generates the R class. Manifests from every module and library merge into one.
  3. R8 shrinks, optimises and renames the code, then converts it to DEX.
  4. Everything is packaged as an APK (installable) or an AAB (the upload format; Google Play generates per-device APKs from it).
  5. The package is signed. The signing certificate is the app's identity: updates must carry the same one.
  6. On install, the package manager verifies the signature, assigns a UID, and records the manifest's components and permissions.

Failure modes

  • Release-only crashes. R8 removed or renamed a class reached by reflection (JSON models, some SDKs). Fix with keep rules or by using code-generating libraries. Always test the release variant.
  • Manifest merge surprises. A library silently adds a permission or an exported component. Read the merged manifest in Android Studio.
  • Dependency conflicts. Two libraries want different versions of a third. Use a BOM (Compose, Firebase, OkHttp publish them) and ./gradlew :app:dependencies.
  • Slow builds. Usually KAPT, non-cacheable tasks, or one giant module. Prefer KSP, enable the configuration cache, modularise.

Trade-offs and when not to use it

Flavours multiply: two dimensions of three flavours with two build types is 18 variants to build and test. Use a flavour only for something that must differ at build time, and put the rest behind runtime configuration. Convention plugins that share build logic are worth it past roughly five modules and overhead before that.

Production and security

Never commit signing keys or API secrets. Anything in BuildConfig or strings.xml ships inside the APK and can be read by anyone with a zip tool. Enable Gradle dependency verification and lock versions for an auditable supply chain; SOC 2 reviewers ask how a build maps to a commit and who can sign it.

Practice

  • Investigate. Add any analytics SDK and diff the merged manifest. What did it add?
  • Challenge. Kosh needs dev, uat and prod backends. Decide which differences are flavours and which are remote configuration, and justify each.

Components and intents

The four entry points the system can start, and the messages that connect them.

Why it exists

Since the system starts and stops your process, it needs named entry points it can instantiate for a purpose: show a screen, do background work, react to an event, share data. Those are the four components. It also needs a way for one app to ask another to do something without linking against it. That is the Intent.

Mental model

Components are doors into your app. The manifest is the list of doors. An intent is a note pushed under a door, and exported decides whether strangers may push notes.

Mechanics

Component Purpose Started by
Activity A window with UI The user, another app, a notification
Service Work with no UI that the user is aware of (playback, an active call) Your app, or a bound client
BroadcastReceiver React to an event (boot completed, SMS received) The system or apps
ContentProvider Expose structured data to other apps A ContentResolver query

    <uses-permission android:name="android.permission.POST_NOTIFICATIONS" />

Explicit and implicit intents

// Explicit: I name the class. Used inside your own app.
startActivity(Intent(this, MainActivity::class.java))

// Implicit: I describe the job. The system finds an app that can do it.
val share = Intent(Intent.ACTION_SEND).apply {
    type = "text/plain"
    putExtra(Intent.EXTRA_TEXT, "Paid ₹125.00 to Asha. Ref KX-88213")
}
startActivity(Intent.createChooser(share, "Share receipt"))

A PendingIntent is an intent wrapped with your identity, handed to someone else (the notification system, an alarm) to fire later as you. Create them with FLAG_IMMUTABLE unless a platform feature needs to fill in fields.

Getting results and permissions

val askNotifications = rememberLauncherForActivityResult(
    ActivityResultContracts.RequestPermission()
) { granted -> viewModel.onNotificationPermission(granted) }

Button(onClick = { askNotifications.launch(Manifest.permission.POST_NOTIFICATIONS) }) {
    Text("Turn on payment alerts")
}

Dangerous permissions (camera, location, notifications since Android 13) are granted at runtime by the user, can be denied, and can be revoked later. Design every feature for the denied state.

Worked code: the single activity and a notification

@AndroidEntryPoint
class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        enableEdgeToEdge()
        setContent { KoshTheme { KoshApp() } }
    }

    override fun onNewIntent(intent: Intent) {         // a link arrived while the activity was already open
        super.onNewIntent(intent)
        setIntent(intent)
    }
}

fun notifyPaymentReceived(context: Context, txId: String, title: String, body: String) {
    val manager = NotificationManagerCompat.from(context)
    manager.createNotificationChannel(
        NotificationChannelCompat.Builder("payments", NotificationManagerCompat.IMPORTANCE_HIGH)
            .setName("Payments").build()
    )

    val open = PendingIntent.getActivity(
        context, txId.hashCode(),
        Intent(Intent.ACTION_VIEW, "https://kosh.example/tx/$txId".toUri(), context, MainActivity::class.java),
        PendingIntent.FLAG_IMMUTABLE or PendingIntent.FLAG_UPDATE_CURRENT,
    )

    val notification = NotificationCompat.Builder(context, "payments")
        .setSmallIcon(R.drawable.ic_stat_kosh)
        .setContentTitle(title).setContentText(body)
        .setVisibility(NotificationCompat.VISIBILITY_PRIVATE)      // hidden on a locked screen
        .setContentIntent(open).setAutoCancel(true)
        .build()

    val allowed = ContextCompat.checkSelfPermission(context, Manifest.permission.POST_NOTIFICATIONS) ==
        PackageManager.PERMISSION_GRANTED
    if (allowed) manager.notify(txId.hashCode(), notification)
}

End-to-end flow: "Pay with Kosh" from a merchant app

  1. The merchant app fires an implicit intent with a payment URI.
  2. system_server matches the intent against every installed app's intent filters and finds Kosh's exported payment activity.
  3. If the Kosh process is not running, Zygote forks it (chapter 1).
  4. Kosh's activity receives the intent in onCreate(). It must treat every field as untrusted input.
  5. The user approves. Kosh calls setResult(RESULT_OK, data) and finishes.
  6. The merchant's result callback fires with the outcome.

Failure modes

  • Exported by accident. Any component with an intent filter must declare android:exported explicitly (Android 12 and later). An exported activity that trusts its extras is an injection point.
  • Background starts. Apps cannot start activities from the background, and starting foreground services from the background is restricted. A notification is the sanctioned route to the user's attention.
  • No handler. An implicit intent with no matching app throws ActivityNotFoundException. On Android 11 and later, package visibility rules also mean you may need a <queries> element to see other apps.
  • Receivers without a flag. Runtime-registered receivers must say RECEIVER_EXPORTED or RECEIVER_NOT_EXPORTED when targeting Android 14 or later.

Trade-offs and when not to use it

Modern apps use one activity and navigate between composable screens inside it (chapter 9). Extra activities are for genuinely separate entry points: a payment intent handler, a share target. A Service is rarely the right tool for background work; chapter 17 uses WorkManager and chapter 20 explains when a service is correct. A ContentProvider is needed only to share data with other apps.

Production and security

Audit the merged manifest for every exported="true". For each, write down who may call it and what it validates. Protect cross-app entry points with signature-level permissions when both apps are yours. Never put secrets in intent extras sent to other apps.

Practice

  • Lab. Add a share target to an app so it appears in the system share sheet for text/plain.

  • Challenge. Design the intent contract for "Pay with Kosh". Which fields come from the caller, and which must Kosh fetch from its own server before showing an amount?

Lifecycle, process death and state

Why screens are destroyed and rebuilt, and how to keep what the user typed.

Why it exists

The system reclaims memory by destroying things. It also rebuilds a screen when configuration changes (rotation, language, dark mode, window resize) so that the right resources load. Android's early answer was "save state yourself in a Bundle". The result was a decade of lost form data and crashes on rotation. ViewModel and saved-state APIs exist to make the correct behaviour the easy one.

Mental model

There are three lifetimes. The composition is short. The ViewModel outlives rotation. Saved state outlives the process. Put each piece of state in the shortest lifetime that is still long enough.

Mechanics

The activity lifecycle, reduced to what matters:

Callback Meaning Typical use
onCreate Instance is being built Set content, wire dependencies
onStart / onStop Visible / no longer visible Start and stop observing data
onResume / onPause In focus / losing focus Camera, sensors
onDestroy Going away, perhaps to be recreated Rarely anything
Where state lives Survives rotation Survives process death Use for
remember { } in a composable No No Animation, scroll helpers

End-to-end flow: the user leaves mid-transfer

  1. The user types ₹2,500, then switches to their banking app for an account number. Kosh gets onPause, then onStop.
  2. The system serialises saved state (SavedStateHandle, rememberSaveable) into a Bundle held by system_server.
  3. Memory runs low. The Kosh process is killed. No callback runs.
  4. The user returns from Recents. A new process forks. The activity is recreated with the saved Bundle.
  5. A new TransferViewModel reads amount from its SavedStateHandle. The field shows ₹2,500 again.
  6. The list of recent payees was in memory only, so the ViewModel reloads it from the repository.

Failure modes

  • "It works on my phone." Developers' phones have spare memory, so process death never happens in testing. Force it: put the app in the background, run adb shell am kill com.kosh.app, return.
  • Assuming a singleton is initialised. After process death the user lands on a deep screen. The "login screen always runs first" assumption is false.
  • Work tied to the wrong lifetime. A coroutine launched in a composable dies on rotation. A network call for a payment must outlive both the screen and the ViewModel (chapter 17).
  • Huge saved state. Leads to TransactionTooLargeException on the way to the background.
  • Leaking the activity. A ViewModel or singleton holding an Activity or View keeps a destroyed screen in memory.

Trade-offs and when not to use it

You can declare android:configChanges to handle rotation yourself and skip recreation. It hides bugs that process death will still expose, so treat it as an optimisation for special cases such as video players. Android 17 also stops restarting activities by default for a few configuration changes that need no redraw, such as keyboard and touchscreen changes. Not everything belongs in saved state: restoring a half-entered one-time password after an hour is worse than clearing it.

Production and security

Saved state is held by the system and may be written to disk. Do not put card numbers, CVVs or tokens in SavedStateHandle or rememberSaveable. For sensitive screens set FLAG_SECURE so the Recents thumbnail and screenshots are blank.

The View system

The original toolkit. You will read it for years, and its rendering pipeline still sits under Compose.

Why it exists

Android launched in 2008 with an object-oriented UI toolkit: a tree of View objects, usually described in XML, mutated by imperative code. It is in every app older than about 2021 and in most SDKs you will integrate. Google's guidance is now Compose-first, but a working Android engineer reads View code weekly, and the frame pipeline below is shared by both toolkits.

Mental model

A screen is a tree of stateful objects. You find a node and change it. Keeping the tree consistent with your data is your job.

How a frame is produced

  1. Measure. Parents ask children how big they want to be, passing constraints down and sizes up.
  2. Layout. Parents position children.
  3. Draw. Each view records drawing commands into a display list.
  4. The RenderThread replays display lists on the GPU. SurfaceFlinger composites the result.

All of this must fit in one frame: 16.6 ms at 60 Hz, 8.3 ms at 120 Hz. requestLayout() reruns steps 1 to 3 for part of the tree; invalidate() reruns only draw.

End-to-end flow: a tap on Refresh

Failure modes

  • State in two places. The data says ₹12,480 and the TextView says ₹12,100 because one code path forgot to update it. This class of bug is the reason declarative UI exists.
  • Wrong thread. Touching a view off the main thread throws CalledFromWrongThreadException.
  • Deep or weighted hierarchies. Nested LinearLayout weights measure children twice per level. Use ConstraintLayout for flat trees.
  • Leaks. A long-lived object holding a View holds its Activity and everything it references.
  • Fragments. Two overlapping lifecycles (fragment and its view) cause crashes from touching views after onDestroyView.

Production and security

II · UI framework · Chapter 7

The Compose mental model

UI as a function of state, and the runtime that makes rerunning that function cheap.

Why it exists

The View system makes you keep a mutable tree in step with your data by hand. Every bug where the screen disagrees with the data comes from that. React, SwiftUI, Flutter and Compose all make the same move: describe the UI for a given state, and let a runtime work out what changed.

Mental model

UI = f(state). You never update the screen. You change state, and the function runs again.

A composable function does not return a view. It emits nodes into a tree while it runs. The runtime remembers what was emitted and what each call read.

Mechanics

@Composable
fun BalanceCard(balance: Money, onRefresh: () -> Unit, modifier: Modifier = Modifier) {
    Column(modifier.padding(24.dp)) {
        Text(balance.minor.asRupees(), style = MaterialTheme.typography.displaySmall)
        Button(onClick = onRefresh) { Text("Refresh") }
    }
}

State and recomposition

@Composable
fun Counter() {
    var count by remember { mutableIntStateOf(0) }   // observable, remembered across recompositions
    Button(onClick = { count++ }) { Text("Tapped $count times") }
}
  • mutableStateOf creates a value the runtime can observe. Reading it inside a composable subscribes that scope.
  • remember stores a value in the composition so it survives the function being called again.
  • When count changes, the runtime reruns only the scopes that read it. That rerun is recomposition.

Three phases per frame

Phase Question Triggered by reading state in
Composition What to show A composable body
Layout Where to place it A layout or offset { } lambda
Drawing How to draw it A drawBehind { } or graphicsLayer { } lambda

State read only in a later phase skips the earlier ones. A scroll offset read in Modifier.offset { } moves a node without recomposing anything.

Skipping and stability

If a composable's parameters are equal to last time, the runtime skips it. With the Kotlin 2 compose compiler, strong skipping is the default: unstable parameters are compared by instance, and lambdas are remembered automatically. You still help the runtime by passing immutable data and by giving list items stable keys.

Rules for composable functions

They can run in any order, many times, and be abandoned midway. So: no side effects in the body, no reliance on execution order, and nothing slow.

End-to-end flow: a tap on the counter

  1. The click lambda sets count. The snapshot system records that a state object changed.
  2. The runtime marks every scope that read count as invalid and schedules a frame.
  3. On the next frame, composition reruns the lambda that contains Text("Tapped $count times"). Counter's caller is not rerun.
  4. The tree diff shows one text node changed. Layout remeasures it; drawing redraws it.

Failure modes

  • Side effects in composition. Calling viewModel.load() in a composable body runs it on every recomposition. Use effect APIs (chapter 9).
  • Forgetting remember. val state = mutableStateOf(0) without remember creates a fresh state on each run. The UI never appears to change.
  • Reading state too high. Reading a scroll position at the top of a screen recomposes the whole screen per pixel. Read it as low and as late as possible.
  • Mutating a plain collection. Adding to a MutableList held in state notifies no one. Use mutableStateListOf or replace an immutable list.
  • Backwards writes. Writing to state after reading it in the same composition loops.

Trade-offs and when not to use it

Compose's cost is conceptual: recomposition bugs are invisible until you measure, and debugging "why did this rerun" needs tooling. Lists with very heavy items and text editing have needed tuning in some releases. None of this argues for XML in new code. It argues for learning the model properly, which is what this chapter is for.

Production and security

Turn on Compose compiler reports in a debug build and use Layout Inspector's recomposition counts to find hot spots before users do. Ship release builds with R8; Compose in debug mode is much slower and misleads benchmarks.

The vocabulary for building real screens: arrangement, decoration, scrolling, and one visual system.

Why it exists

Every toolkit needs to answer four things: how children are arranged, how one element is sized and decorated, how to show ten thousand rows, and how to keep the whole app visually consistent. Compose answers with layout composables, modifiers, lazy lists and a theme.

Mental model

Layouts arrange children. Modifiers wrap one element, outside in, like layers of an onion. A theme is ambient data that any composable can read.

Mechanics

@Composable
fun TransactionRow(tx: TransactionUi, onClick: () -> Unit, modifier: Modifier = Modifier) {
    Row(
        modifier
            .fillMaxWidth()
            .clickable(onClick = onClick)     // the ripple covers the full width

Modifier order is behaviour

Modifier.clickable { }.padding(16.dp) makes the padding clickable. Modifier.padding(16.dp).clickable { } does not. Each modifier wraps everything after it. Read chains top to bottom as outside to inside.

Layout rules

Row, Column and Box cover most needs. Compose measures each child once per layout pass, which is why deep nesting is cheap here and was not in Views. For anything unusual, write a Layout { measurables, constraints -> … }; it is about fifteen lines.

Why it exists

Mental model

@Composable
fun TransferScreen(state: TransferUiState, onEvent: (TransferEvent) -> Unit, onDone: () -> Unit) {
    val snackbar = remember { SnackbarHostState() }
    val latestOnDone by rememberUpdatedState(onDone)           // the effect below always sees the newest lambda

    LaunchedEffect(state.result) {
        when (val r = state.result) {
            is TransferResult.Success -> latestOnDone()
            is TransferResult.Declined -> snackbar.showSnackbar(r.reason)
            TransferResult.NetworkError -> snackbar.showSnackbar("We are confirming this payment")
            null -> Unit
        }
    }

    Scaffold(snackbarHost = { SnackbarHost(snackbar) }) { inner ->
        Column(Modifier.padding(inner).padding(24.dp).imePadding(),
               verticalArrangement = Arrangement.spacedBy(16.dp)) {
            AmountField(state.amount, onValueChange = { onEvent(TransferEvent.AmountChanged(it)) },
                        error = state.amountError)
            Button(onClick = { onEvent(TransferEvent.SendClicked) },
                   enabled = !state.sending && state.amount.isNotBlank(),
                   modifier = Modifier.fillMaxWidth()) {
                if (state.sending) CircularProgressIndicator(Modifier.size(18.dp), strokeWidth = 2.dp)
                else Text("Send")
            }

fun TransferRoute(onDone: () -> Unit, vm: TransferViewModel = hiltViewModel()) {
    val state by vm.state.collectAsStateWithLifecycle()

}

End-to-end flow: open a transaction, rotate, go back

  1. A row click calls onOpen(id). The home route adds TransactionDetail(id) to the back stack.
  2. NavDisplay sees the list changed and composes the detail entry with a transition.
  3. The detail route's ViewModel is scoped to that entry. It loads by id.
  4. Rotation recreates the activity. The back stack was saved and is restored; the same ViewModel instance is reattached.
  5. The system back gesture calls onBack. The key is removed, the entry leaves composition, its ViewModel is cleared.

Failure modes

  • Passing objects between screens. Pass the id and load from the repository. Objects in navigation arguments go stale and bloat saved state.
  • Navigation inside composition. Calling backStack.add() in a composable body, instead of in a callback or effect, pushes on every recomposition.
  • LaunchedEffect(Unit) capturing stale lambdas. The effect never restarts, so it keeps the first onDone. Use rememberUpdatedState.
  • One-off events lost or replayed. A "navigate now" emitted while the screen is in the background disappears, or fires twice after rotation. Model it as state that the UI consumes and acknowledges, as the snackbar example does.
  • ViewModels passed down the tree. Children become untestable and unpreviewable. Pass state and lambdas.

Trade-offs and when not to use it

Navigation 3 gives control and makes adaptive layouts simpler; it also asks you to own more. On an app already built on NavHost, migrate when you need what it offers, not before. Hoisting has a limit too: lifting every toggle into a ViewModel creates large state classes that change on every keystroke.

Production and security

Deep links land users on inner screens with a synthetic back stack. Every destination must check authentication itself; never rely on "the user must have passed through login". Validate deep link arguments like any external input.

MVC on Android

The first pattern everyone reaches for, how to do it properly, and exactly where it gives way.

Why it exists

Model-View-Controller comes from Smalltalk in the 1970s. Its purpose is one idea: the code that knows the business rules should not know how it is displayed. Everything later in this part is a refinement of that. Learn MVC first because the later patterns are answers to its specific failures on Android.

Mental model

The Model holds data and rules. The View draws and reports input. The Controller receives input, asks the Model to act, and tells the View what to show.

On Android the natural mapping is: XML layout as View, plain Kotlin classes as Model, and the Activity as Controller. The problem is in that last mapping, as you will see.

Mechanics

The feature for this whole part is Kosh's Send money screen: an amount, a payee, a Send button, a result.

class TransferModel(private val api: PaymentsApi) {

End-to-end flow: tapping Send

  1. The click listener in the activity (controller) runs.
  2. It reads the amount from the view and asks the model to validate.
  3. It mutates views to show progress and calls model.send.
  4. The network replies. The callback mutates views again with the result.

Four steps, one file, easy to follow. That simplicity is real, and it is why MVC survives for small screens.

Failure modes

  • The massive activity. The activity owns lifecycle, permissions, navigation, view wiring and the controller logic. Real screens reach thousands of lines.
  • Rotation during step 3. The activity is destroyed and recreated. The callback holds the old instance: it leaks, and it updates views nobody can see. The new instance shows an idle form while a payment is in flight. The user taps Send again.
  • Process death. All progress and result state lived in view objects and is gone.
  • Untestable logic. Testing onSendClicked needs an activity, so a device or Robolectric. Teams stop writing the tests.
  • State scattered across widgets. "Is a transfer in progress?" is answered by progress.isVisible. No single value describes the screen.

The second and fifth items are the ones the next patterns are designed to remove.

Use MVC when Move on when

You are reading a legacy app and must make a small change You need unit tests on screen logic

MVC is not wrong. The Model separation it teaches is permanent: every later pattern keeps a model layer free of Android types. What changes is who stands between the model and the screen, and how long that object lives.

Production and security

Validation in the model is a usability feature, never a control. The server must validate amount, balance and limits again. A client-side model that "enforces" a transfer limit enforces nothing against a modified app.

From MVP to MVVM to MVI

The same screen three more ways. Each step removes one failure of the step before.

Why it exists

Chapter 11 ended with two unsolved problems: logic bound to a short-lived activity, and screen state scattered across widgets. MVP solves testability. MVVM solves lifetime. MVI solves scattered state. Seeing them as a sequence is more useful than memorising three diagrams.

Mental model

MVP: the presenter commands the view. MVVM: the view observes state. MVI: the view observes one state and sends one kind of message.

Mechanics

MVP

class TransferPresenter(private val model: TransferModel) {
    private var view: TransferView? = null
    fun attach(v: TransferView) { view = v }
    fun detach() { view = null }                 // must be called in onDestroy

    fun onSendClicked(amountText: String, payeeId: String) {
        view?.showLoading(true)
        model.send(payeeId, amountText.toMinor()) { result ->
            view?.showLoading(false)
            view?.showResult(message(result))    // if the view is detached, the result is dropped
        }
    }
}

Gain: pure JVM tests. Remaining pain: manual attach and detach, an interface method per widget change, and results lost when the view is absent.

MVVM

The ViewModel exposes state and knows nothing about who is watching. Jetpack's ViewModel outlives rotation.

data class TransferUiState(
    val amount: String = "",
    val amountError: String? = null,
    val sending: Boolean = false,
    val result: TransferResult? = null,
)

@HiltViewModel
class TransferViewModel @Inject constructor(
    private val sendMoney: SendMoneyUseCase,
) : ViewModel() {

    private val _state = MutableStateFlow(TransferUiState())
    val state: StateFlow<TransferUiState> = _state.asStateFlow()

    fun onAmountChange(text: String) = _state.update { it.copy(amount = text, amountError = null) }

    fun onSend(payeeId: String) {
        if (_state.value.sending) return                       // no double submit
        viewModelScope.launch {
            _state.update { it.copy(sending = true) }
            val result = sendMoney(payeeId, _state.value.amount)
            _state.update { it.copy(sending = false, result = result) }
        }
    }
}

@Composable
fun TransferRoute(vm: TransferViewModel = hiltViewModel()) {
    val state by vm.state.collectAsStateWithLifecycle()
    TransferScreen(state, onAmountChange = vm::onAmountChange, onSend = vm::onSend)
}

Rotation now does nothing interesting: the new composition collects the same StateFlow and draws sending = true.

MVI

MVI tightens MVVM with two rules. All input is one sealed type. All state changes go through one pure function.

sealed interface TransferEvent {
    data class AmountChanged(val text: String) : TransferEvent
    data object SendClicked : TransferEvent
    data class Completed(val result: TransferResult) : TransferEvent
}

fun reduce(s: TransferUiState, e: TransferEvent): TransferUiState = when (e) {
    is TransferEvent.AmountChanged -> s.copy(amount = e.text, amountError = null)
    TransferEvent.SendClicked -> if (s.sending) s else s.copy(sending = true)
    is TransferEvent.Completed -> s.copy(sending = false, result = e.result)
}

class TransferViewModel(private val payeeId: String, private val sendMoney: SendMoneyUseCase) : ViewModel() {
    private val _state = MutableStateFlow(TransferUiState())
    val state = _state.asStateFlow()

    fun onEvent(e: TransferEvent) {
        val before = _state.value
        _state.update { reduce(it, e) }
        if (e is TransferEvent.SendClicked && !before.sending) viewModelScope.launch {
            onEvent(TransferEvent.Completed(sendMoney(payeeId, before.amount)))
        }
    }
}

reduce is a pure function: testable with a table of inputs and outputs, loggable, replayable.

End-to-end flow: tapping Send under MVVM, with a rotation

  1. TransferScreen calls onSend. The ViewModel sets sending = true and launches a coroutine in viewModelScope.
  2. The state flow emits. The composable recomposes: button disabled, progress shown.
  3. The user rotates. The activity and composition are destroyed. The ViewModel and its coroutine are not.
  4. The new composition collects state and immediately draws sending = true.
  5. The use case returns. State becomes sending = false, result = Success. The receipt appears.

Compare with the same steps in chapter 11's failure list. Both bugs are gone without any code written to handle rotation.

Failure modes

  • Many small flows. A ViewModel exposing eight separate StateFlows can show combinations that make no sense, such as loading and error together. Prefer one UiState, or a sealed type for mutually exclusive modes.
  • Events as state, state as events. "Navigate to receipt" kept as a boolean replays after rotation; sent through a channel it can be lost. Treat it as state plus an acknowledgement (chapter 9).
  • Android types in the ViewModel. Holding a Context, View or resources leaks and blocks JVM tests. Expose ids or sealed types and resolve strings in the UI.
  • Fat ViewModels. Business rules migrate into the ViewModel because it is convenient. That is the massive activity again with a different base class. Chapter 13 gives the rules a home.
  • MVI ceremony. A reducer, effect handler and middleware for a screen with one button.

Trade-offs and when not to use it

The default in this book, and in Google's guidance, is MVVM with unidirectional data flow: one immutable UiState, events in as function calls. Move to full MVI where the screen is a genuine state machine and you want to enumerate transitions: payment flows, onboarding with branching, anything where an illegal state costs money. Stay with plain MVVM for lists and detail screens. MVP has no place in new Compose code.

Production and security

A reducer gives you an audit trail for free: log event names and state transitions (never amounts, account numbers or tokens) and you can reconstruct what the user saw before a disputed payment. Double-submit protection belongs in the state machine and again on the server through idempotency keys (chapter 16).

Failure modes

  • DTOs in the UI. A renamed JSON field breaks a composable. Map at the data boundary.

Coroutines and Flow

Asynchronous code that reads top to bottom, cancels itself, and stays off the main thread.

Why it exists

The main thread must never block, and almost everything useful (disk, network, crypto) blocks. Android tried AsyncTask, callbacks, and RxJava. Each leaked work past the screen that started it or buried logic in nesting. Coroutines give sequential-looking code that suspends instead of blocking, with cancellation tied to a lifetime.

Mental model

A coroutine is a computation that can pause without holding a thread. A scope is a lifetime: when the scope ends, everything launched in it is cancelled. A Flow is a suspending sequence of values over time.

For a Java engineer: suspend functions are close to virtual-thread code in how they read, and Flow plays the role Reactor's Flux does, with far fewer operators to learn.

Mechanics

End-to-end flow: a transfer, with the user leaving

  1. viewModelScope.launch { sendMoney(...) } starts on the main thread.
  2. withContext(io) moves execution to an I/O thread. The main thread is free to draw.
  3. Retrofit suspends until the HTTP response arrives. No thread is parked.
  4. The result returns to the main thread and updates state.
  5. If the user had left the screen and the ViewModel was cleared, the scope would be cancelled at step 3, and the HTTP call aborted.

Step 5 is correct for loading a list and wrong for a payment. A transfer must not be cancelled because the user pressed back. Chapter 17 moves it to a scope that outlives the screen.

Failure modes

  • GlobalScope. Work with no owner: never cancelled, never tested, leaks.
  • Swallowing cancellation. catch (e: Exception) also catches CancellationException and turns a cancelled coroutine into a zombie. Rethrow it, or catch specific types.
  • Blocking in the wrong place. A blocking call on Dispatchers.Default starves CPU work; on Main it freezes the UI. runBlocking on the main thread is an ANR.
  • Collecting forever. lifecycleScope.launch { flow.collect { } } keeps running in the background. Use repeatOnLifecycle or collectAsStateWithLifecycle.
  • Hard-coded dispatchers. Tests cannot control time or threads. Inject them.
  • One failure cancels everything. Use supervisorScope where siblings are independent (chapter 18).

Trade-offs and when not to use it

Coroutines are the default on Android and almost every Jetpack library exposes suspend functions and flows. RxJava remains in older codebases and bridges exist both ways; do not introduce it into new code. Not everything needs a Flow: a one-shot request is a suspend fun. Reserve flows for values that change over time.

Production and security

Uncaught exceptions in a launch crash the app. Decide per boundary: repositories convert expected failures (IOException, HTTP errors) into result types, and unexpected ones crash and reach your crash reporter. Never log exception messages from payment calls without checking what they contain.

Local persistence with Room and DataStore

A database and a settings store that the rest of the app can observe.

Why it exists

Memory is temporary (chapter 5) and the network is unreliable. The device's disk is the only place state reliably survives. Android ships SQLite, which is solid and tedious: hand-written SQL strings, cursors, and no compile-time checks. SharedPreferences, the old key-value store, did disk I/O on the main thread and failed silently. Room and DataStore replace them.

Mental model

The database is the app's single source of truth. Screens observe queries. Whoever changes a row, every observer of a query that reads it is told.

Failure modes

  • Destructive migration in production. fallbackToDestructiveMigration() wipes user data when you forget a migration. Acceptable only for a pure cache you can refetch.

  • N+1 queries. Loading a list, then one query per row. Use a join or a relation.

For a higher bar, encrypt sensitive columns with a Keystore-held key (chapter 21) or use SQLCipher, accepting the performance cost. Exclude databases holding personal data from cloud backup with dataExtractionRules, or accept that they will be restored on a different device. PCI DSS scope grows the moment a primary account number touches this database, so do not store it.

Networking

HTTP from a device that changes networks mid-request, described so failures are data and not surprises.

Why it exists

A server calls another server over a stable link in the same region. A phone calls from a train entering a tunnel, behind a captive portal, switching from Wi-Fi to mobile data, with the app about to be suspended. Android's networking stack and the libraries above it exist to make that survivable: connection reuse, timeouts, and a typed description of each API.

Mental model

Every call has three outcomes, not two: success, a response that says no, and no response at all. The third is the one that matters for money.

Mechanics

OkHttp is the HTTP client: connection pooling, HTTP/2, TLS, caching, and interceptors. Retrofit turns an interface into calls. kotlinx.serialization converts JSON to Kotlin types at compile time, without reflection.

Errors as types

sealed interface ApiResult<out T> {
    data class Ok<T>(val value: T) : ApiResult<T>
    data class Rejected(val code: Int, val reason: String?) : ApiResult<Nothing>   // server said no
    data object Unreachable : ApiResult<Nothing>                                   // never got an answer
    data object Unknown : ApiResult<Nothing>                                       // sent, outcome not known
}

suspend fun <T> apiCall(block: suspend () -> T): ApiResult<T> = try {
    ApiResult.Ok(block())
} catch (e: HttpException) {
    ApiResult.Rejected(e.code(), e.response()?.errorBody()?.string())
} catch (e: SocketTimeoutException) {
    ApiResult.Unknown
} catch (e: IOException) {
    ApiResult.Unreachable
}

Idempotency

A timeout on POST /transfers does not tell you whether the money moved. The client generates a unique key per user intent, stores it before sending, and sends the same key on every retry. The server returns the original result for a repeated key. Without this, a retry is a second payment.

Worked code: interceptors and a fake server

class BearerInterceptor @Inject constructor(private val session: SessionStore) : Interceptor {
    override fun intercept(chain: Interceptor.Chain): Response {
        val request = chain.request()
        if (request.url.host != "api.kosh.example") return chain.proceed(request)   // never leak the token elsewhere
        val token = session.cachedAccessToken() ?: return chain.proceed(request)
        return chain.proceed(request.newBuilder().header("Authorization", "Bearer $token").build())
    }
}

class TelemetryInterceptor(private val appVersion: String) : Interceptor {
    override fun intercept(chain: Interceptor.Chain): Response {
        val request = chain.request().newBuilder()
            .header("X-App-Version", appVersion)
            .header("X-Request-Id", UUID.randomUUID().toString())
            .build()
        val started = System.nanoTime()
        return chain.proceed(request).also { response ->
            val ms = (System.nanoTime() - started) / 1_000_000
            // path and status only: no query string, headers or bodies
            Log.i("http", "${request.method} ${request.url.encodedPath} ${response.code} ${ms}ms")
        }
    }
}

End-to-end flow: one GET

  1. The repository calls the suspend function. Retrofit builds an OkHttp Request.
  2. Application interceptors run: add the Authorization header, a trace id, the app version.
  3. OkHttp reuses a pooled HTTP/2 connection, or does DNS, TCP and TLS for a new one.
  4. The response returns through interceptors. A 401 triggers the authenticator (chapter 18).
  5. The converter decodes JSON into DTOs on a background thread.
  6. The coroutine resumes. The repository writes to Room; the UI updates from the database.

Failure modes

  • Treating a timeout as a failure. The user is told "payment failed" and pays again. Unknown needs its own screen: "We are confirming this payment."
  • Automatic retry of a POST. Safe only with an idempotency key.
  • Strict parsing. The backend adds a field and old app versions crash. Ignore unknown keys and give new fields defaults.
  • Cleartext HTTP. Blocked by default since Android 9. If a debug backend needs it, allow it in a debug-only network security config, never in release.
  • Captive portals. The device reports "connected" and every call returns a login page. A JSON parse error on HTML is the symptom.
  • Logging interceptors in release. Request bodies, tokens and account numbers end up in logs.

Trade-offs and when not to use it

Retrofit with OkHttp is the conservative choice and has the best tooling. Ktor Client is the natural choice in Kotlin Multiplatform code and can use OkHttp underneath. GraphQL (Apollo Kotlin) suits screens that aggregate many resources and teams that can run the server side well. gRPC suits internal streaming APIs (chapter 19). Avoid HttpURLConnection in new code.

Production and security

Send a stable set of headers on every call: app version, platform, a request id, and a W3C traceparent so a mobile request can be followed through backend services. Redact logs at the interceptor. For PCI DSS, the cleanest design keeps card numbers out of your own API calls altogether, by letting the payment provider's SDK collect and tokenise them.

Offline-first and background sync

Read from the database, write through an outbox, and let the system choose when to talk to the server.

Why it exists

Mobile connectivity is intermittent, and the process can die at any time. An app that reads straight from the network shows spinners in lifts and loses writes when the user leaves. Offline-first design decouples the UI from the network: the screen reads local data instantly, and synchronisation is a separate job the OS schedules.

Mental model

Reads come from the database. Writes go into the database first, as intentions. A worker moves intentions to the server and brings truth back.

Mechanics

Read path

class OfflineFirstTransactionsRepository @Inject constructor(
    private val dao: TransactionDao, private val api: PaymentsApi,
) : TransactionsRepository {

    override fun observeRecent(accountId: AccountId): Flow<List<Transaction>> =
        dao.observeRecent(accountId.raw, limit = 50).map { rows -> rows.map { it.toDomain() } }

    override suspend fun refresh(accountId: AccountId): ApiResult<Unit> =
        when (val r = apiCall { api.transactions(accountId.raw, cursor = null) }) {
            is ApiResult.Ok -> { dao.upsert(r.value.items.map { it.toEntity() }); ApiResult.Ok(Unit) }
            is ApiResult.Rejected -> r
            ApiResult.Unreachable -> r
            ApiResult.Unknown -> r
        }
}

The UI never receives network data directly. That is what "single source of truth" means in practice.

WorkManager

@HiltWorker
class OutboxWorker @AssistedInject constructor(
    @Assisted ctx: Context, @Assisted params: WorkerParameters,
    private val outbox: OutboxDao, private val api: PaymentsApi,
) : CoroutineWorker(ctx, params) {

    override suspend fun doWork(): Result {
        for (item in outbox.queued()) {
            when (val r = apiCall { api.transfer(item.idempotencyKey, item.toRequest()) }) {
                is ApiResult.Ok -> outbox.markConfirmed(item.idempotencyKey, r.value.reference)
                is ApiResult.Rejected -> outbox.markFailed(item.idempotencyKey, r.reason)
                else -> return Result.retry()             // unreachable or unknown: same key, later
            }
        }
        return Result.success()
    }
}

fun enqueueOutbox(context: Context) {
    val request = OneTimeWorkRequestBuilder<OutboxWorker>()
        .setConstraints(Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build())
        .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 10, TimeUnit.SECONDS)
        .setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST)
        .build()
    WorkManager.getInstance(context).enqueueUniqueWork("outbox", ExistingWorkPolicy.APPEND_OR_REPLACE, request)
}

WorkManager persists the request, survives process death and reboot, honours constraints, and cooperates with Doze and App Standby. It guarantees execution eventually, not at an exact time.

class QueueTransferUseCase @Inject constructor(

    }
}

@HiltWorker
class SyncWorker @AssistedInject constructor(
    @Assisted ctx: Context, @Assisted params: WorkerParameters,
    private val accounts: AccountsRepository, private val transactions: TransactionsRepository,
    private val session: SessionStore,
) : CoroutineWorker(ctx, params) {

    override suspend fun doWork(): Result {
        val accountId = session.primaryAccountId() ?: return Result.success()     // logged out: nothing to do
        val results = listOf(accounts.refresh(accountId), transactions.refresh(accountId))
        return when {
            results.all { it is ApiResult.Ok } -> Result.success()
            results.any { it is ApiResult.Rejected } -> Result.failure()           // retrying will not help
            runAttemptCount >= 5 -> Result.failure()
            else -> Result.retry()
        }
    }
}

        .setInitialDelay(Random.nextLong(0, 60), TimeUnit.MINUTES)                 // jitter across devices

End-to-end flow: sending money in a lift

  1. The user confirms. One transaction writes the outbox row and a pending transaction.
  2. The home screen's query emits; the payment appears as "Sending".
  3. enqueueOutbox schedules the worker. There is no network, so it waits.
  4. The user closes the app. The process dies.
  5. Connectivity returns. The system starts the Kosh process and runs OutboxWorker.
  6. The API call succeeds. The worker marks the outbox row confirmed and upserts the posted transaction.
  7. A notification tells the user. If the app is open, the row changes from "Sending" to the receipt through the same database flow.

Failure modes

  • Duplicate submission. The worker runs twice, or the response is lost. The idempotency key makes the second attempt harmless.
  • Optimistic lies. Showing the balance already reduced before the server agrees. For money, show the pending item and the last confirmed balance with its time.
  • Sync storms. A periodic sync every 15 minutes on a million devices aligned to the hour. Add jitter and let push messages trigger sync (chapter 19).
  • Conflicts. Two devices edit the same payee nickname. Choose a rule per data type: server wins for money, last write wins for labels.
  • Stale forever. A cache with no age shown. Display "Updated 2 hours ago" whenever data may be old.
  • Expecting exact timing. Periodic work has a 15-minute minimum and the system defers it. Alarms and foreground services are different tools.

Trade-offs and when not to use it

Offline-first roughly doubles the data layer: schemas, mappers, sync logic, conflict rules. It is worth it for content the user revisits and writes they must not lose. It is wrong for data that must be live to be meaningful: a foreign exchange quote, an OTP, the result of a card authorisation. For those, call the network directly, fail visibly, and cache nothing. Many regulated apps also choose to require connectivity for initiating payments; the outbox then covers the gap between tap and confirmed response, not hours offline.

Production and security

Queued payment intentions are sensitive: an attacker with the device could wait for sync. Expire outbox rows after a short window, require a fresh authentication for anything queued beyond it, and make the server reject stale idempotency keys. Monitor outbox age and worker failure rates as product metrics.

Tokens: refresh once, not five times

class TokenAuthenticator @Inject constructor(private val session: SessionStore) : Authenticator {
    private val lock = Mutex()

    override fun authenticate(route: Route?, response: Response): Request? {
        if (response.request.header("X-Retry-Auth") != null) return null       // already retried: give up
        val failed = response.request.header("Authorization")?.removePrefix("Bearer ")
        val fresh = runBlocking {                                              // OkHttp thread, not main
            lock.withLock {
                val current = session.accessToken()
                if (current != null && current != failed) current              // someone else refreshed
                else session.refresh()                                         // null means logged out
            }
        } ?: return null
        return response.request.newBuilder()
            .header("Authorization", "Bearer $fresh").header("X-Retry-Auth", "1").build()
    }
}

When an access token expires, five parallel calls get 401 together. The mutex lets the first refresh and the other four reuse its result.

Worked code: retry with backoff, and a small circuit breaker

suspend fun <T> retrying(
    attempts: Int = 3, baseDelayMs: Long = 300, maxDelayMs: Long = 5_000,
    block: suspend () -> ApiResult<T>,
): ApiResult<T> {
    var last: ApiResult<T> = ApiResult.Unreachable
    repeat(attempts) { attempt ->
        last = block()
        if (last !is ApiResult.Unreachable) return last            // only "never reached the server" is safe to repeat
        val ceiling = (baseDelayMs shl attempt).coerceAtMost(maxDelayMs)
        delay(Random.nextLong(ceiling / 2, ceiling + 1))           // jitter: clients must not retry in step
    }
    return last
}

class CircuitBreaker(private val failuresToOpen: Int = 3, private val openForMs: Long = 30_000,
                     private val now: () -> Long = System::currentTimeMillis) {
    private val failures = AtomicInteger(0)
    @Volatile private var openedAt = 0L

    suspend fun <T> call(block: suspend () -> ApiResult<T>): ApiResult<T> {
        if (failures.get() >= failuresToOpen && now() - openedAt < openForMs) return ApiResult.Unreachable  // fail fast
        return block().also { result ->
            if (result is ApiResult.Unreachable || result is ApiResult.Unknown) {
                if (failures.incrementAndGet() >= failuresToOpen) openedAt = now()
            } else failures.set(0)
        }
    }
}

End-to-end flow: opening the dashboard with an expired token

  1. Four requests leave in parallel with the old access token.
  2. Banking returns 401 to two of them. The authenticator runs for the first and takes the lock.
  3. It calls the identity provider's token endpoint with the refresh token and stores the new pair.
  4. The second authenticator call acquires the lock, sees a newer token, and reuses it.
  5. Both requests are retried once with the new token and succeed.
  6. Market data times out at two seconds. The rates card shows "Rates unavailable"; the balance is already on screen.

Failure modes

  • Refresh stampede. No lock, five refresh calls, and a provider that rotates refresh tokens invalidates four of them. The user is logged out at random.
  • Credentials sent to the wrong host. One global interceptor adds the bearer token to every request, including the image CDN and the analytics vendor. Scope interceptors per client and check the host.
  • All-or-nothing screens. One optional call fails and the whole dashboard shows an error.
  • Chatty startup. Twelve sequential calls before first paint on a 3G connection.
  • Version skew. The app released eighteen months ago is still calling. Every service must keep answering it or tell it to upgrade.

Trade-offs and when not to use it

A BFF is right when screens aggregate several services and you control the backend. It adds a team dependency and a hop. GraphQL offers flexible aggregation with a heavier client and server. A circuit breaker inside a phone app sees only one user's traffic; keep it simple or leave it to the gateway. Do not rebuild a service mesh in the client.

Production and security

Never ship a third-party secret in the app. If a service needs a secret key, the call belongs behind your server. Give each downstream its own audience-restricted token so a token leaked to one service is useless at another. Propagate a trace id from the device so an incident can be followed from tap to ledger entry.

Realtime and push

Polling, streams and push notifications: which one keeps a balance current, and at what battery cost.

Why it exists

Users expect an incoming payment to appear without pulling to refresh. A phone, however, cannot hold a socket open in the background: the OS freezes idle apps and the radio is the largest battery drain after the screen. Android therefore has two regimes. While the app is on screen, you may stream. When it is not, one shared system connection (Firebase Cloud Messaging on Google devices) wakes you.

Mental model

Foreground: hold a stream. Background: wait for a push. In both cases the message is a hint to sync, and the database stays the source of truth.

Worked code: resuming a stream without gaps, and the sync a push triggers

@Serializable data class StatusEvent(val seq: Long, val transferId: String, val status: String)

class TransferStatusStream @Inject constructor(@Banking private val client: OkHttpClient,
                                               private val session: SessionStore) {
    /** Reconnects from the last sequence number seen, so no status is skipped. */
    fun events(transferId: String): Flow<StatusEvent> = flow {
        var lastSeq = 0L
        var attempt = 0
        while (currentCoroutineContext().isActive) {
            try {
                val ticket = session.streamTicket()                       // short-lived, fetched per connection
                val url = "wss://stream.kosh.example/transfers/$transferId?after=$lastSeq&ticket=$ticket"
                client.socketFlow(url).collect { text ->
                    val event = Json.decodeFromString<StatusEvent>(text)
                    if (event.seq > lastSeq) { lastSeq = event.seq; attempt = 0; emit(event) }   // drop duplicates
                }
            } catch (e: IOException) { /* fall through to backoff */ }
            delay(backoffWithJitter(attempt++))
        }
    }
}

fun backoffWithJitter(attempt: Int): Long {
    val ceiling = (500L shl attempt.coerceAtMost(6)).coerceAtMost(30_000)
    return Random.nextLong(ceiling / 2, ceiling + 1)
}

fun enqueueSync(context: Context, accountId: String?) {
    val request = OneTimeWorkRequestBuilder<PushSyncWorker>()
        .setInputData(workDataOf("accountId" to accountId))
        .setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST)
        .setConstraints(Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build())
        .build()
    // many pushes in a burst collapse into one sync
    WorkManager.getInstance(context).enqueueUniqueWork("push-sync", ExistingWorkPolicy.KEEP, request)
}

@HiltWorker
class PushSyncWorker @AssistedInject constructor(
    @Assisted private val ctx: Context, @Assisted params: WorkerParameters,
    private val transactions: TransactionsRepository, private val settings: SettingsRepository,
) : CoroutineWorker(ctx, params) {

    override suspend fun doWork(): Result {
        val accountId = AccountId(inputData.getString("accountId") ?: return Result.failure())
        val before = transactions.latestId(accountId)
        if (transactions.refresh(accountId) !is ApiResult.Ok) return Result.retry()

        transactions.newerThan(accountId, before).filter { it.amount.minor > 0 }.forEach { tx ->
            val body = if (settings.hideAmountsInNotifications()) "You received a payment"
                       else "${tx.amount.minor.asRupees()} from ${tx.counterparty}"   // from fetched data, not the push
            notifyPaymentReceived(ctx, tx.id, "Payment received", body)
        }
        return Result.success()
    }
}

End-to-end flow: Asha pays you ₹500 while Kosh is closed

  1. The ledger posts the credit and publishes an event.
  2. A notification service sends an FCM data message {type: ACCOUNT_CHANGED, accountId} to your device token.
  3. Google Play services delivers it over the device's single shared connection and starts the Kosh process.
  4. onMessageReceived enqueues an expedited sync and returns.
  5. The worker calls the banking API with the user's token, upserts the new transaction and balance into Room.
  6. The worker posts a notification built from fetched data: "₹500 received from Asha".
  7. If the app is open on another screen, the home flow emits and the balance updates.

The push carried no amount and no name. It could be forged or replayed without telling an attacker or the UI anything.

Failure modes

  • Push as truth. Rendering the amount from the push payload shows wrong data when messages arrive late, twice or out of order.
  • Gaps after reconnect. A socket drops for forty seconds and three events are missed. Resume from the last sequence number, or run a normal sync on every reconnect.
  • Sockets in the background. A foreground service kept alive only to hold a connection drains the battery and conflicts with platform policy for service types.
  • Thundering herd. The server restarts and a million clients reconnect at once. Jitter the backoff.
  • Stale tokens. Not handling onNewToken, or not removing the token on logout, sends one user's alerts to another person's phone.
  • Assuming delivery. Notifications can be disabled, the app can be force-stopped, and some manufacturers restrict background starts. Always sync on app open as well.

Trade-offs and when not to use it

Most apps need no socket. Push plus sync-on-open covers balances and transactions. Add a stream only for data that changes many times a minute while the user watches: prices, a live transfer status, chat. Prefer SSE when traffic is one-way. gRPC is excellent between your own services and heavier to carry to a phone; adopt it when you already have protobuf contracts and infrastructure that passes HTTP/2 end to end.

Production and security

Treat push content as visible to others: lock screens show it. Offer a setting to hide amounts. Authenticate streams with a short-lived token and re-authenticate on reconnect. Rate-limit what a single message can trigger so a flood of pushes cannot become a flood of API calls.

sealed interface LinkTarget {
    data class PaymentRequest(val id: String) : LinkTarget
    data class Transaction(val id: String) : LinkTarget

private val SAFE_ID = Regex("^[A-Za-z0-9_-]{4,64}$")

/** Returns null for anything unexpected. The link supplies an id and nothing else. */
fun parseLink(uri: Uri?): LinkTarget? {
    if (uri?.scheme != "https" || uri.host != "kosh.example") return null
    val segments = uri.pathSegments
    val id = segments.lastOrNull()?.takeIf { SAFE_ID.matches(it) } ?: return null
    return when {
        segments.size == 3 && segments[0] == "pay" && segments[1] == "r" -> LinkTarget.PaymentRequest(id)
        segments.size == 2 && segments[0] == "tx" -> LinkTarget.Transaction(id)
        else -> null
    }
}

Failure modes

  • Trusting the caller. An exported service or provider without caller checks is an open API to every installed app.

Identity and security

Who the user is, where secrets live on the device, and what a wallet must assume about the phone it runs on.

Why it exists

Every connection in this part carries a credential. On a server you protect secrets with network boundaries and a vault. On a phone the attacker may hold the device, the app binary is public, and the user may have installed malware. Android provides hardware-backed keys, biometric gating, verified links and attestation so that an app can still make trustworthy claims.

Mental model

The app is a public client running on a device you do not control. It can hold short-lived proof that a user authenticated. It can never hold a secret that belongs to you.

Mechanics

Threats to design for

Threat Main defences
Lost or stolen unlocked phone Biometric or PIN before sensitive actions, short sessions
Malicious app on the device Sandbox, non-exported components, verified links, no secrets in intents

Reverse engineering No secrets in the binary, server-side enforcement
Rooted or tampered device, modified app Play Integrity attestation, server-side risk decisions

Sign-in

Use OAuth 2.0 authorization code flow with PKCE, opened in a Custom Tab (the user's browser), through a library such as AppAuth. The app holds no client secret. The Play Integrity API returns a signed verdict about the app binary, the installer and the device. Your server requests a nonce, the app obtains a token bound to it, and the server verifies the verdict with Google and feeds it into a risk decision.

Worked code: a token vault, passkey sign-in, and an integrity token

/** AES-256-GCM with a key that never leaves secure hardware. Output layout: 12-byte IV, then ciphertext. */
class TokenVault @Inject constructor() {
    private fun key(): SecretKey {
        val store = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
        (store.getKey(ALIAS, null) as? SecretKey)?.let { return it }
        val spec = KeyGenParameterSpec.Builder(ALIAS, KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT)
            .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
            .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
            .setKeySize(256).build()
        return KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")
            .apply { init(spec) }.generateKey()
    }

    fun seal(plain: ByteArray): ByteArray {
        val cipher = Cipher.getInstance("AES/GCM/NoPadding").apply { init(Cipher.ENCRYPT_MODE, key()) }
        return cipher.iv + cipher.doFinal(plain)                        // the Keystore picks a fresh IV each time
    }

    fun open(sealed: ByteArray): ByteArray {
        val cipher = Cipher.getInstance("AES/GCM/NoPadding")
            .apply { init(Cipher.DECRYPT_MODE, key(), GCMParameterSpec(128, sealed, 0, 12)) }
        return cipher.doFinal(sealed, 12, sealed.size - 12)             // throws if the data was altered
    }

    private companion object { const val ALIAS = "kosh_token_key" }
}

class SessionStore @Inject constructor(private val vault: TokenVault, @ApplicationContext private val context: Context) {
    private val REFRESH = stringPreferencesKey("refresh_sealed")

    suspend fun saveRefreshToken(token: String) = context.settings.edit {
        it[REFRESH] = Base64.encodeToString(vault.seal(token.toByteArray()), Base64.NO_WRAP)
    }
    suspend fun refreshToken(): String? = context.settings.data.first()[REFRESH]
        ?.let { runCatching { String(vault.open(Base64.decode(it, Base64.NO_WRAP))) }.getOrNull() }  // null: sign in again
    suspend fun clear() = context.settings.edit { it.clear() }
}

class PasskeySignIn @Inject constructor(private val auth: AuthApi) {
    suspend fun signIn(activity: Activity): SignInResult {
        val options = auth.beginPasskeySignIn()                          // WebAuthn request JSON, with a server challenge
        val request = GetCredentialRequest(listOf(GetPublicKeyCredentialOption(requestJson = options.json)))
        return try {
            val response = CredentialManager.create(activity).getCredential(activity, request)
            when (val credential = response.credential) {
                is PublicKeyCredential ->
                    SignInResult.Ok(auth.finishPasskeySignIn(credential.authenticationResponseJson))
                else -> SignInResult.Unsupported
            }
        } catch (e: GetCredentialCancellationException) { SignInResult.Cancelled
        } catch (e: NoCredentialException) { SignInResult.NoPasskey     // offer enrolment or another method
        } catch (e: GetCredentialException) { SignInResult.Failed }
    }
}

class IntegrityTokens @Inject constructor(@ApplicationContext context: Context) {
    private val manager = IntegrityManagerFactory.createStandard(context)
    private var provider: StandardIntegrityManager.StandardIntegrityTokenProvider? = null

    suspend fun warmUp() {                                               // slow: do it before the confirm screen
        provider = manager.prepareIntegrityToken(

                .setCloudProjectNumber(BuildConfig.CLOUD_PROJECT_NUMBER).build()).await()
    }

    /** `requestHash` binds the token to this exact transfer. The server verifies the verdict, never the app. */

End-to-end flow: a transfer above the step-up limit

  1. The user confirms ₹50,000. The server replies that step-up is required and returns a challenge.
  2. The app builds the bytes to sign: challenge, payee, amount, idempotency key.
  3. BiometricPrompt appears. The user presents a fingerprint.
  4. Secure hardware releases the key for one operation and signs the bytes.
  5. The app sends the transfer with the signature and a Play Integrity token.
  6. The server verifies the signature against the enrolled public key, checks the integrity verdict, and posts the transfer.

Failure modes

  • Pinning without an exit. The certificate rotates and every installed copy stops working until users update. Always ship a backup pin, an expiry, and a tested rotation plan, or do not pin.
  • Secrets in BuildConfig. Extracted in minutes.
  • Tokens in logs, crash reports or cloud backups. Review logging, and configure backup rules to exclude credential stores.
  • Biometric as a UI gate only. See above; bind it to a key.
  • Keys lost on restore. Keystore keys do not migrate to a new phone. Design re-enrolment as a normal path.
  • Root detection as a guarantee. Client-side checks are bypassable. Treat them as signals for the server.
  • Overlay attacks. Another app draws over your confirm button. Set filterTouchesWhenObscured on sensitive controls and FLAG_SECURE on sensitive windows.

Trade-offs and when not to use it

Certificate pinning protects against a compromised certificate authority and against casual interception. It also creates an outage risk you own. Many teams pin only the most sensitive hosts. Obfuscation with R8 raises the cost of reverse engineering slightly and is not a control. Blocking rooted devices outright excludes legitimate users; a graded response (lower limits, more step-up) is usually better.

Production and security

For PCI DSS, minimise scope: let a certified provider's SDK capture card data so the number never reaches your code, memory or logs. For SOC 2, be able to show how signing keys are held, who can release, and how a vulnerable version is retired (forced upgrade, chapter 27). Run a mobile-specific review against the OWASP MASVS before each major release.

Glass UI in Compose

Translucent, blurred surfaces: how they are drawn, what they cost, and how to keep text readable on top of them.

Why it exists

Glass surfaces (frosted panels that let colour through from behind) give depth and hierarchy without heavy borders. They suit a bottom bar floating over a scrolling list, or a balance card over a gradient. They are also the easiest visual style to get wrong: blur is one of the more expensive things a GPU does per frame, and text over an unpredictable background fails contrast checks. This chapter treats glass as an engineering feature with a budget.

Mental model

Glass is four layers: something colourful behind, a blur of it, a translucent tint, and a thin bright edge. Remove the first and you have a grey box.

The important distinction is what gets blurred:

Kind Blurs API Available from
Content blur The composable's own pixels Modifier.blur() Android 12 (API 31); ignored below
Backdrop blur Whatever is drawn behind the composable Capture the background into a graphics layer and blur it, or use a library such as Haze Practical from Android 12
Window blur Other windows behind a dialog or sheet Window.setBackgroundBlurRadius(), FLAG_BLUR_BEHIND Android 12, when the device enables cross-window blur
Shader effects Anything, with custom maths RuntimeShader (AGSL) Android 13 (API 33)

Modifier.blur() on a card blurs the card's text. That is the most common first mistake. Glass needs backdrop blur.

@Composable
fun BackdropBlurScaffold(bar: @Composable () -> Unit, content: @Composable () -> Unit) {
    val source = rememberGraphicsLayer()
    val blurred = rememberGraphicsLayer()
    var barOffset by remember { mutableStateOf(Offset.Zero) }
    val canBlur = Build.VERSION.SDK_INT >= 31
    val tint = MaterialTheme.colorScheme.surface.copy(alpha = if (canBlur) 0.55f else 0.92f)   // near-solid fallback
    val shape = RoundedCornerShape(28.dp)

    Box(Modifier.fillMaxSize()) {
        Box(Modifier.fillMaxSize().drawWithContent {
            source.record { this@drawWithContent.drawContent() }       // capture what is behind the bar
            drawLayer(source)                                          // and still show it normally
        }) { content() }

        Box(Modifier.align(Alignment.BottomCenter).padding(16.dp).fillMaxWidth()
            .onGloballyPositioned { barOffset = it.positionInParent() }
            .clip(shape)
            .drawBehind {
                if (canBlur) {
                    blurred.renderEffect = BlurEffect(60f, 60f, TileMode.Clamp)
                    blurred.record { translate(-barOffset.x, -barOffset.y) { drawLayer(source) } }
                    drawLayer(blurred)
                }
                drawRect(tint)
            }
            .border(1.dp, Color.White.copy(alpha = 0.25f), shape)
        ) { bar() }
    }
}

Treat the second sample as a starting sketch to profile and adjust on a device. It re-records on every frame in which the content changes, which is exactly the cost described in the flow below.

End-to-end flow: one frame of a list scrolling under a glass bar

  1. The scroll offset changes. The list redraws into its layer.
  2. The backdrop capture for the bar's rectangle is re-recorded, because what is behind it changed.
  3. The GPU downsamples that region and applies a two-pass Gaussian blur.
  4. The tint and noise are composited over the blurred pixels, then the border, then the bar's icons and labels.
  5. All of it must finish inside the frame budget from chapter 6, at 120 Hz on many phones.

Steps 2 and 3 repeat on every frame of the scroll. Cost grows with the blurred area and with the radius.

Failure modes

  • Blurring the content instead of the backdrop. Unreadable text.
  • Unreadable text on busy backgrounds. White text passes over a dark photo and fails over a white receipt. The tint must be strong enough to guarantee contrast whatever scrolls underneath. Measure the worst case.
  • Jank on mid-range devices. A full-screen blur at a large radius, several stacked glass layers, or an animated radius. Blur small regions, keep one glass layer per screen area, animate alpha instead of radius.
  • Banding and flat grey. Blur over a plain background looks like a dull rectangle. Glass needs colour behind it, and a little noise hides gradient banding.
  • No fallback. On Android 11 and below Modifier.blur() does nothing, so a design that depends on it shows raw content under text.
  • Ignoring user settings. High contrast text, reduced transparency preferences on some devices, and battery saver should all push you to the solid fallback.

Trade-offs and when not to use it

Use glass for Avoid glass for
Navigation bars and toolbars over scrolling content Tables, statements and dense numeric screens
A hero card over a controlled gradient Forms and error messages
Sheets and dialogs, through window blur Anything on low-end devices where you cannot test
Media and imagery-rich screens Screens where the background is user content you cannot predict

In a wallet, the amount is the most important pixel on the screen. Put amounts on a surface with a strong tint (55% opacity or more), or on solid colour. Decoration yields to legibility every time.

Production and security

Add the glass level to your performance tests: run the scroll benchmark from chapter 26 with blur on and off and set a frame-time budget. Ship a remote flag that forces the tint fallback for device models that misbehave. Motion and polish

Animation that explains what changed, at a cost you have measured.

Why it exists

A screen that jumps from one state to another makes the user work out what happened. Motion carries that information: this row became that detail screen, this payment went from sending to sent. Glass surfaces depend on it, since translucent layers appearing abruptly look like rendering faults. Compose builds animation into the state model, so most of it is a few lines.

Mental model

You do not animate views. You animate a value, and the UI is a function of that value like any other state.

Mechanics

API Animates Example
animate*AsState One value toward a target Tint opacity when a bar lifts
AnimatedVisibility Appearance and disappearance An error banner
AnimatedContent A swap between two contents "Sending" turning into a receipt
updateTransition Several values in step from one state A card expanding
Animatable A value under coroutine control Drag, fling, snap
Shared element transitions One element across two screens A transaction row becoming the detail header 
@Composable
fun SendButton(state: TransferUiState, onSend: () -> Unit) {
    val scale by animateFloatAsState(if (state.sending) 0.96f else 1f,
        animationSpec = spring(dampingRatio = 0.6f, stiffness = Spring.StiffnessMedium), label = "scale")

    Button(onClick = onSend, enabled = !state.sending,
        modifier = Modifier.graphicsLayer { scaleX = scale; scaleY = scale }) {   // draw phase only
        AnimatedContent(targetState = state.sending, label = "label") { sending ->
            if (sending) CircularProgressIndicator(Modifier.size(18.dp), strokeWidth = 2.dp)
            else Text("Send")
        }
    }
}

Springs or durations. Springs take a stiffness and damping and handle interruption gracefully: reverse halfway and they continue from the current velocity. Fixed-duration tweens suit fades and colour changes. Use springs for anything that moves.

Animate in the cheapest phase. graphicsLayer { } changes scale, alpha and translation at draw time with no recomposition or layout. Animating Modifier.size() or padding() relayouts every frame.

Predictive back. During a back gesture the system shows a preview of where back will go. Navigation libraries drive the transition from gesture progress; custom back handling must cooperate through PredictiveBackHandler.

Haptics. A light tick on confirm and a distinct pattern on failure, through LocalHapticFeedback, adds more perceived quality than most visual effects.

End-to-end flow: "Sending" becomes a receipt

  1. State changes from sending = true to result = Success.
  2. AnimatedContent keeps the old content in composition and adds the new one.

  1. Gradle sees only :feature:transfer sources changed.
  2. It recompiles that module. Because its public API did not change, dependants are not recompiled.
  3. :app relinks and repackages.
  4. Other modules come from the build cache, locally or from CI.

In a single-module app the same edit recompiles everything that could see the changed file.

Failure modes

  • The common module. Everything depends on it, it depends on everything useful, and any change rebuilds the world. Split by purpose.
  • Too many modules too early. Sixty modules for six screens slows configuration and buries the code in build files.
  • Feature-to-feature shortcuts. One import to save an hour creates a cycle a year later.
  • Leaky api dependencies. A module exposes its Retrofit types transitively and the UI starts using them.
  • Duplicated models. Each feature defines its own Account. Shared domain models belong in :core:domain.

Trade-offs and when not to use it

Below roughly twenty screens and one team, packages inside one module plus discipline are cheaper. Introduce modules along the seams you already have (core layers first, then features) when build times or ownership hurt. Splitting features into api and impl modules gives the best build isolation and doubles the module count; do it for the largest features only.

Production and security

Module boundaries are also review boundaries. Put Keystore, signing and integrity code in :core:security with restricted code owners, so a change there always gets a security review. Add a build check that fails if a feature module depends on a forbidden one.

Startup, smooth frames, memory and battery: what to measure and what actually moves the numbers.

Why it exists

Users judge an app in its first second and by whether scrolling stutters. Google Play also measures: apps with poor stability or responsiveness are shown less. Performance on Android is mostly about three budgets (time to first frame, time per frame, memory) on devices far slower than the one on your desk.

Mental model

Measure release builds on a mid-range device. Everything else is a guess.

Mechanics

Startup

Start What happens Target
Cold Process fork, Application.onCreate, first activity, first frame Under about a second to first frame on mid-range hardware
Warm Process alive, activity recreated Faster
Hot Activity brought to front Near instant

Frames

A dropped frame is one that missed its vsync deadline. In Compose the usual causes are recomposing too much (chapter 7), expensive work in composition, unkeyed lazy lists, large images decoded at full size, and overdraw from stacked translucent layers, glass included.

Memory and battery

End-to-end flow: finding a slow start

  1. Android vitals shows slow cold starts concentrated on low-memory devices.
  2. A Macrobenchmark run on a comparable device reproduces it with numbers.

Release and operations

Shipping a binary you cannot roll back to devices you do not control.

Why it exists

A server deploy replaces every instance in minutes and can be reverted. A mobile release is reviewed by a store, adopted over weeks, and never reaches some users at all. Versions from two years ago are still running against your APIs. Operating an Android app means planning for that from the first release.

Mental model

You do not deploy an app. You publish a version and persuade devices to adopt it. Control lives on the server: flags, configuration and compatibility.

Mechanics

Signing. With Play App Signing, Google holds the app signing key and you sign uploads with a separate upload key that can be reset if lost. The app signing certificate is the app's permanent identity and is what App Links and attestation refer to.

Tracks and rollout. Internal testing, closed testing, open testing, production. Production releases go out in stages: 1%, 5%, 20%, 50%, 100%, watching vitals at each step. A staged rollout can be halted. It cannot be reversed: users who updated keep the new version until you ship a higher versionCode.

Runtime control.

Tool Purpose
Feature flags and remote config Ship code dark, enable by percentage, turn off without a release
Kill switch Disable a broken feature for specific versions
Minimum supported version The server tells old builds to update before continuing
In-app updates API Prompt for, or require, an update inside the app

Observability. Crash and ANR reporting with deobfuscation mapping files uploaded per build, release health by version, and business metrics (transfer success rate, sync failures, outbox age) tagged with app version.

Platform obligations. Play requires a recent target API level, a Data safety declaration that matches what the app and its SDKs collect, and justification for sensitive permissions. Budget time each year for the target API upgrade.

End-to-end flow: a bad release

  1. Version 1.9.0 reaches 5% of users. The transfer success rate for that version drops.
  2. An alert on "success rate by app version" fires within the hour.
  3. The rollout is halted at 5%. The new transfer flow's flag is turned off for 1.9.0; those users fall back to the old flow already in the binary.
  4. The fix ships as 1.9.1 through the same stages.
  5. A review asks why the regression passed tests and adds one.

Steps 2 and 3 only work if the flag, the per-version metric and the old code path were built before the incident.

Failure modes

  • Breaking API changes. Removing a field the two-year-old app needs crashes thousands of users who never update. Version APIs and track which app versions still call what.
  • No forced-upgrade path. A security flaw is found and there is no way to stop old versions.
  • Flag debt. Hundreds of stale flags and untested combinations. Give every flag an owner and an expiry.
  • Missing mapping files. Crash reports full of a.b.c().
  • Lost keys. Without Play App Signing, a lost signing key ends the app's update path.
  • SDK surprises. A third-party SDK update starts collecting data your privacy declaration does not mention.

Trade-offs and when not to use it

Server-driven UI and heavy remote configuration increase control and move complexity to the backend, with weaker type safety and harder testing. Use flags for risk control, not as a permanent configuration system. Weekly release trains give predictability; continuous delivery to production is rarely practical with store review and staged adoption.

Production and security

For SOC 2: every release traces to a reviewed commit, built by CI, signed by a controlled key, promoted with an approval. Keep a software bill of materials per release and scan dependencies. Rehearse the forced-upgrade and key-compromise runbooks before they are needed. Remove debug menus, logging and test endpoints from release variants with build-type source sets, not runtime checks.

sealed interface TransferEvent {
    data class AmountChanged(val text: String) : TransferEvent
    data object SendClicked : TransferEvent
    data class StepUpRequired(val amount: Money, val challenge: String) : TransferEvent
    data class Signed(val signature: ByteArray) : TransferEvent
    data class Queued(val idempotencyKey: String) : TransferEvent
    data class Settled(val reference: String) : TransferEvent
    data class Rejected(val reason: String) : TransferEvent
}

fun reduce(s: TransferScreenState, e: TransferEvent): TransferScreenState = when (s) {
    is TransferScreenState.Editing -> when (e) {
        is TransferEvent.AmountChanged -> s.copy(amount = e.text, error = null)
        is TransferEvent.StepUpRequired -> TransferScreenState.AwaitingStepUp(e.amount, e.challenge)
        is TransferEvent.Queued -> Money.parse(s.amount)
            ?.let { TransferScreenState.Sending(it, e.idempotencyKey) } ?: s.copy(error = "Enter an amount")
        is TransferEvent.Rejected -> s.copy(error = e.reason)
        else -> s
    }
    is TransferScreenState.AwaitingStepUp -> when (e) {
        is TransferEvent.Queued -> TransferScreenState.Sending(s.amount, e.idempotencyKey)
        is TransferEvent.Rejected -> TransferScreenState.Failed(e.reason, canRetry = true)
        else -> s
    }
    is TransferScreenState.Sending, is TransferScreenState.Pending -> when (e) {
        is TransferEvent.Settled -> TransferScreenState.Done(e.reference)
        is TransferEvent.Rejected -> TransferScreenState.Failed(e.reason, canRetry = false)
        else -> s                                   // SendClicked here is a double tap: ignored by construction
    }
    is TransferScreenState.Done, is TransferScreenState.Failed -> s
}

1. Cold start with a returning user

  1. Icon tap, Zygote fork, Application.onCreate with only Hilt and crash reporting initialised eagerly.
  2. MainActivity sets content. The root reads session state from DataStore asynchronously, showing the themed splash meanwhile.
  3. A session exists. The back stack becomes [Home]. The home ViewModel exposes cached balance and transactions from Room at once, marked "Updated 09:14".
  4. In parallel the dashboard use case refreshes through the BFF. The token is expired; one refresh happens under the authenticator's lock.
  5. Room is updated; the flow emits; the time label changes. If the price stream is enabled, it opens now and closes when the screen stops.

2. Sending ₹50,000

  1. The transfer screen's reducer handles AmountChanged and SendClicked; validation runs in the domain layer.
  2. The server replies that step-up is required. State becomes AwaitingStepUp(challenge).
  3. BiometricPrompt unlocks the hardware key, which signs challenge, payee, amount and idempotency key.
  4. One Room transaction writes the outbox row and a PENDING transaction. The UI animates to "Sending".
  5. An expedited worker posts the transfer with signature, idempotency key and integrity token.
  6. Success: the outbox row is confirmed, the transaction becomes POSTED, the receipt animates in with a haptic. Timeout: the state stays pending with honest copy, and the worker retries with the same key.
  7. The transfer screen is removed from the back stack so back returns to Home.

3. Receiving money while the app is closed

  1. The ledger posts a credit. A data push with only an account id reaches the device.
  2. The messaging service enqueues a sync. The worker fetches and writes to Room.
  3. A notification is built from fetched data, respecting the "hide amounts" setting.
  4. The user taps it. An App Link style intent opens the transaction detail with a back stack of [Home, Detail], after an authentication check.

Failure modes: a pre-launch review

Question Where the answer lives
What happens if the process dies on every screen? Chapter 5 tests, outbox
Can any action be submitted twice? Reducer guard, idempotency key, server
What does the user see when each backend is down? Section-level degradation, kill switches
What is exported from the app, and who may call it? Merged manifest review
What secrets are in the binary? None, by design
What happens to a user on a version from two years ago? API versioning, minimum-version check
Is every amount readable on glass in both themes? Contrast tests on worst-case backdrops
How do we stop a bad release? Staged rollout, flags, per-version metrics

Production and security

Before launch: an OWASP MASVS review, a penetration test including the exported-component list, a privacy review of every SDK, a performance run on the slowest supported device, and rehearsed runbooks for forced upgrade and incident response.

Practice: architecture challenges

  • Add UPI-style collect requests. Another user asks you for money. Design the push, the deep link, the confirmation and the abuse controls.
  • Add a tablet dashboard. Three panes on expanded width. What changes in navigation and state, and what does not?
  • Go multiplatform. Share the domain and data layers with an iOS app using Kotlin Multiplatform. Which modules move unchanged, and which need an expect/actual seam?
  • Lose the BFF. A reorganisation removes the BFF team. Redesign the client for direct service calls and list every new risk.
  • Expose an app function. Let an on-device assistant "pay my electricity bill". Specify authentication, confirmation and limits.
