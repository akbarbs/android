React Native from First Principles

How React Native really works, its UI framework, architecture patterns from MVC onward, complex applications, connectivity across services, and glass UI. Written in TypeScript against React Native 0.88, Expo SDK 58 and React 19.2, as of November 2026.

Who this is for

You know backend systems and perhaps some web development. You want one codebase for Android and iOS, and you want to understand what happens beneath the JavaScript rather than follow recipes. This book explains the machinery first, then builds up to a production app that talks to many services.

What React Native is, in one paragraph

Your application logic and UI description are TypeScript, run by the Hermes JavaScript engine inside an ordinary Android or iOS app. React decides what the UI should be. A C++ core lays it out and tells the platform to create real native views: an Android TextView, an iOS UILabel. It is not a web view and not a custom drawing engine. That one fact explains its strengths (native look, native accessibility, access to every platform API) and its costs (two platforms' build systems, and a JavaScript thread you must keep free).

I · Foundations · Chapter 1

How React Native works

JavaScript describes the screen, C++ lays it out, and the platform draws real native views.

Why it exists

Building the same app twice, in Kotlin and in Swift, doubles the cost and lets the two drift apart. Earlier cross-platform answers either wrapped a web page in a web view (slow, never quite native) or drew every pixel themselves (consistent, but not the platform's own controls). React Native took a third route: keep the platform's real views and drive them from one shared program.

Mental model

React is the brain and the platform is the hands. Your code never touches a view. It returns a description; the runtime turns differences between descriptions into native view operations.

Mechanics

Piece Role
Hermes The JavaScript engine. Your code is compiled to bytecode at build time, so the app does not parse JavaScript at startup
JSI A C++ interface that lets JavaScript hold references to native objects and call them directly and synchronously. It replaced the old asynchronous JSON bridge
Fabric The renderer. Builds a C++ "shadow tree" from React's output, lays it out with Yoga (Flexbox), and commits changes to native views
Turbo Native Modules Native code (Kotlin, Swift, C++) exposed to JavaScript with typed interfaces, loaded lazily
Codegen Generates the C++ glue between your typed specs and native code

Together these are the New Architecture. It has been the only architecture since React Native 0.82, and Hermes V1 has been the default engine since 0.84.

Threads

Thread Runs If you block it
JavaScript Your components, hooks, business logic Taps do nothing; lists show blank cells
UI (main) Native view creation, touch handling, drawing, native animations The whole app freezes; Android reports an ANR
Background Layout, image decoding, networking Rarely your concern

Most performance work in React Native is keeping the JavaScript thread free and moving animation to the UI thread (chapter 23).

import { Text, View, Pressable } from 'react-native';
import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);
  return (
    <View style={{ padding: 24 }}>
      <Text>Tapped {count} times</Text>
      <Pressable onPress={() => setCount(c => c + 1)} accessibilityRole="button">
        <Text>Tap</Text>
      </Pressable>
    </View>
  );
}

<View> becomes an android.view.ViewGroup on Android and a UIView on iOS. <Text> becomes native text. There is no HTML and no CSS engine.

End-to-end flow: a tap on the counter

  1. The UI thread receives the touch and identifies the pressed native view.
  2. The event is delivered to JavaScript, where React calls your onPress.
  3. setCount schedules a render. React calls Counter() again and gets a new element tree.
  4. React diffs old and new. Only the text changed.
  5. Fabric clones the affected part of the shadow tree in C++, and Yoga recomputes layout for it.
  6. On the UI thread, the native text view receives its new string. The platform draws the next frame.

Failure modes

  • A busy JavaScript thread. A 300 ms JSON parse or a large synchronous loop delays every tap and scroll callback.
  • Believing old tutorials. "The bridge", NativeModules.X and the "Legacy Architecture" describe a system that has been removed.
  • Assuming a browser. There is no DOM, window.location, localStorage or CSS cascade. Many npm packages that expect them fail at runtime.
  • Assuming Node. No fs, crypto or Buffer built in. Use native modules.
  • Forgetting it is still a native app. Signing, permissions, store review and OS behaviour changes all still apply.

Trade-offs and when not to use it

Option Choose it when Cost
React Native One team for both platforms, a UI built from standard controls, and web or React skills A JavaScript runtime in your app; native knowledge is still needed at the edges
Native (Kotlin, Swift) Deep platform integration, heavy graphics, or the newest OS features on day one Two codebases
Flutter Pixel-identical UI on both platforms matters more than native controls Its own rendering and language
Kotlin Multiplatform Share logic, keep fully native UI Two UI layers

For a wallet, React Native is a sound choice if you accept that security-critical pieces (hardware-backed signing, attestation) will be small native modules. Chapter 21 is explicit about which.

Production and security

Your JavaScript bundle ships inside the app and can be extracted and read, Hermes bytecode included. Nothing in it is secret. Every rule about server-side enforcement applies with extra force.

TypeScript and React for native

The language features and React ideas the rest of the book depends on.

Why it exists

JavaScript lets any value be anything, which is how undefined is not a function reaches production. TypeScript adds a type system that is erased at build time. React adds a way to describe UI as functions of data. You need a working command of both before the platform details matter.

Mental model

Types describe the shapes your data may take. A component is a function from props and state to a description of UI. Hooks are how that function remembers things between calls.

Mechanics

Types that prevent whole classes of bugs

/** Money as integer minor units. A branded type cannot be confused with a plain number. */
export type Minor = number & { readonly __brand: 'Minor' };
export type Money = { readonly minor: Minor; readonly currency: 'INR' | 'USD' };

export function parseMoney(text: string, currency: Money['currency'] = 'INR'): Money | null {
  const cleaned = text.trim().replace(/,/g, '');
  if (!/^\d+(\.\d{1,2})?$/.test(cleaned)) return null;
  const [whole, frac = ''] = cleaned.split('.');
  const minor = Number(whole) * 100 + Number(frac.padEnd(2, '0'));      // no floating point arithmetic
  return minor > 0 && Number.isSafeInteger(minor) ? { minor: minor as Minor, currency } : null;
}

/** A discriminated union: a closed set of outcomes the compiler can check. */
export type TransferResult =
  | { kind: 'success'; reference: string }
  | { kind: 'declined'; reason: string }
  | { kind: 'networkError' };

export function message(r: TransferResult): string {
  switch (r.kind) {
    case 'success': return `Sent. Ref ${r.reference}`;
    case 'declined': return `Declined: ${r.reason}`;
    case 'networkError': return 'Check your connection';
    default: { const never: never = r; return never; }      // adding a case makes this line a compile error
  }
}

Turn on "strict": true and "noUncheckedIndexedAccess": true. Types vanish at runtime, so data from outside (JSON, storage, deep links) must be validated, not just typed (chapter 16).

The React Compiler is enabled in new Expo projects. It memoises components and values automatically, so hand-written useMemo, useCallback and React.memo are rarely needed. It requires that you follow the rules: components are pure, state is never mutated.

End-to-end flow: typing into a text field

  1. The native text input reports a change on the UI thread.
  2. onChangeText runs in JavaScript and calls setAmount(text).
  3. React re-renders the component with the new state.
  4. The diff shows the input's value prop and perhaps an error label changed.
  5. Fabric commits those two changes to native views.

Failure modes

  • Mutating state. items.push(x); setItems(items) changes nothing on screen: same array reference. Create a new array.
  • Effects for derived data. Copying props into state with useEffect causes extra renders and stale values. Compute during render.
  • Missing dependencies. An effect that reads a value not in its dependency array sees a stale copy. Keep the ESLint rule on.
  • any. It switches the type checker off for everything it touches. Use unknown and narrow.
  • Trusting types at the boundary. as Transaction on a network response is a claim, not a check.

Trade-offs and when not to use it

TypeScript costs a build step and some verbosity and is worth it on any app with more than one screen. Class components still work and should not be written in new code. Do not reach for state libraries until useState and useReducer are uncomfortable (chapter 12).

Production and security

Never use JavaScript numbers for money arithmetic with decimals: 0.1 + 0.2 is not 0.3. Integer minor units, as above, and let the server be the authority. Be careful what goes into console.log: logs reach device logs and crash reporters.

Project anatomy and the build

What is in a React Native project, and how TypeScript becomes two signed native apps.

Why it exists

A React Native app is two native apps (an Android Gradle project and an iOS Xcode project) that both load one JavaScript bundle. Keeping two native projects configured by hand is the traditional pain point. Expo's answer is to generate them from one configuration file.

Mental model

Your repository holds TypeScript and configuration. The native projects are build artefacts, regenerated whenever configuration changes. The JavaScript bundle and the native binary are two things with two lifecycles.

Mechanics

kosh/
├── app.config.ts          name, ids, icons, permissions, plugins: the source of truth for native config
├── eas.json               build and release profiles
├── package.json
├── tsconfig.json
├── app/                   screens, by file path (Expo Router, chapter 9)
├── src/                   features, domain, data
├── modules/               your own native modules (chapter 20)
└── android/, ios/         generated by prebuild; usually not committed

End-to-end flow: from eas build to a phone

  1. Prebuild generates android/ and ios/, applying each config plugin.
  2. Autolinking finds native modules in node_modules and adds them to Gradle and CocoaPods.
  3. Metro bundles TypeScript into one JavaScript file and collects assets.
  4. The Hermes compiler turns that file into bytecode.
  5. Gradle (and Xcode) compile native code, including React Native's C++ core, and package the bytecode inside the app.
  6. The binary is signed and installed. At launch the native app starts Hermes and loads the bytecode.

Failure modes

  • Editing generated folders. Changes to android/ vanish on the next prebuild. Write a config plugin.
  • Works in Expo Go, fails in a build. A library with native code is not in Expo Go. Use development builds from the start.
  • Native and JavaScript out of step. New JavaScript that calls a native module the installed binary lacks crashes at runtime. Runtime versions (chapter 27) prevent this.
  • Dependency mismatches. A library built for a different React Native version. npx expo install picks compatible versions; npx expo-doctor reports problems.
  • Slow upgrades. Falling several versions behind makes each upgrade a project. Upgrade every release.

Trade-offs and when not to use it

Expo with prebuild suits almost every new app, including ones with custom native code. A hand-maintained bare project makes sense when React Native is embedded in a large existing native app ("brownfield"), or when a native team wants full control of the projects.

Production and security

Values in app.config.ts and extra ship inside the binary. Use build-time secrets only for the build itself (signing, upload keys), stored in the build service, never in the repository. For SOC 2, the build profile, commit and signing identity for every release should be recorded automatically.

The native host

The Android and iOS app your JavaScript lives in: entry points, permissions and links.

Why it exists

React Native does not replace the operating system's rules. Android still starts your app through an Activity declared in a manifest; iOS still launches a UIApplication with an Info.plist. Permissions, notifications, links from other apps and background limits are all platform concepts. A React Native engineer who does not know them is stuck the first time something works on one platform and not the other.

Mental model

There is one native activity (Android) or one root view controller (iOS) hosting a React root view. Everything the OS knows about your app comes from native configuration, which you write through app.config.ts.

Mechanics

Concept Android iOS
App declaration AndroidManifest.xml Info.plist, entitlements
Screen entry point MainActivity hosting the React root Root view controller hosting the React root
Ask another app to do something Intents URL schemes, share sheet, universal links
Runtime permissions Per permission, can be re-requested with rationale Per capability, asked once; after denial the user must go to Settings
Background work WorkManager, foreground services Background tasks at the system's discretion, tightly limited
Process lifetime Killed when memory is needed Suspended quickly in the background, then killed

Permissions

import * as Notifications from 'expo-notifications';
import { Linking } from 'react-native';

export async function ensureNotificationPermission(): Promise<'granted' | 'denied' | 'blocked'> {
  const current = await Notifications.getPermissionsAsync();
  if (current.granted) return 'granted';
  if (!current.canAskAgain) return 'blocked';                 // only Settings can change it now
  const asked = await Notifications.requestPermissionsAsync();
  return asked.granted ? 'granted' : 'denied';
}

End-to-end flow: tapping the Kosh icon on Android

  1. The launcher sends an intent. Android forks a process and creates MainActivity (chapter 1 of any Android text).
  2. The activity creates a React host, which starts Hermes on the JavaScript thread.
  3. Hermes loads the bytecode and runs your entry file. Expo Router registers the root component.
  4. React renders the first screen. Fabric creates native views.
  5. The splash screen stays until you hide it, usually when fonts and session state are ready.

Steps 2 to 4 are the part of startup React Native adds over a native app. Chapter 26 measures them.

Failure modes

  • Testing on one platform. Permissions, back behaviour, keyboard handling and fonts all differ. Test both, every feature.
  • Assuming background execution. JavaScript timers stop when the app is suspended. Background work needs platform-scheduled tasks (chapter 17).
  • The Android back button. It must do something sensible on every screen. Navigation libraries handle the common case; custom modals need care.
  • Missing native configuration. A library needs a manifest entry or an Info.plist usage string and the app crashes or is rejected in review. Read each library's configuration section.
  • Permission asked at launch. Users deny what they do not understand, and on iOS you rarely get a second chance.

Trade-offs and when not to use it

Expo's packages cover most platform features with one TypeScript API. When they do not, you write a native module (chapter 20). If a large fraction of your app would be custom native code on both platforms, the sharing benefit shrinks and native development deserves a second look.

Production and security

Review the generated manifest and plist before each release: every permission, every exported Android component, every URL scheme. Libraries add entries you did not ask for.

Lifecycle, process death and state

What survives rotation, backgrounding and being killed, and what you must save yourself.

Why it exists

Phones kill background apps to reclaim memory. Native Android gives developers saved-state machinery for this. React Native does not: when the process dies, the JavaScript world is gone, and on the next launch your program starts from its first line. Nobody saves component state for you. Knowing this early shapes how you hold state.

Mental model

Three lifetimes. Component state lives until the component unmounts. A store or query cache lives until the process dies. Only what you wrote to disk survives the process.

Mechanics

Event What happens to JavaScript Your job
Rotation, resize, dark mode Nothing restarts. Components re-render with new dimensions or colour scheme Lay out responsively (chapter 10)
App goes to background JavaScript keeps its memory, but timers and network may be paused within seconds Stop streams, save drafts
App returns to foreground Execution resumes Refresh stale data
Process killed in background Everything in memory is lost Restore from disk on next launch
Navigating away from a screen By default the screen stays mounted under the stack; it unmounts when popped Do not rely on unmount to save

React Native on Android handles configuration changes without recreating the activity, which is why rotation is uneventful compared with native Android.

Where state lives Survives navigation Survives process death Use for
useState in a screen While mounted No UI details
A store (Zustand, Redux) or query cache Yes No, unless persisted Session, server data
Navigation state and URL Yes Only if you persist or deep link Where the user is
Disk: SQLite, MMKV, SecureStore Yes Yes Anything the user would be upset to lose 
import { useEffect, useState } from 'react';
import { AppState } from 'react-native';
import { createMMKV } from 'react-native-mmkv';

const drafts = createMMKV({ id: 'drafts' });        // synchronous key-value storage on disk

/** State that is written through to disk, so a half-typed transfer survives the process. */
export function usePersistedDraft(key: string, initial = '') {
  const [value, setValue] = useState(() => drafts.getString(key) ?? initial);

  useEffect(() => { drafts.set(key, value); }, [key, value]);

  const clear = () => { drafts.remove(key); setValue(initial); };
  return [value, setValue, clear] as const;
}

/** Run something whenever the app returns to the foreground. */
export function useOnForeground(callback: () => void) {
  useEffect(() => {
    let previous = AppState.currentState;
    const sub = AppState.addEventListener('change', next => {
      if (previous !== 'active' && next === 'active') callback();
      previous = next;
    });
    return () => sub.remove();
  }, [callback]);
}

End-to-end flow: the user leaves mid-transfer

  1. The user types ₹2,500. usePersistedDraft writes each change to disk.
  2. They switch to their banking app. AppState becomes background.
  3. Memory runs low. The OS kills Kosh. No JavaScript runs.
  4. The user returns. The native app starts, Hermes loads, your code runs from the top.
  5. The app restores the session from secure storage and, if you persisted it, the navigation location.
  6. The transfer screen mounts. useState's initialiser reads the draft. The field shows ₹2,500.

Failure modes

  • Never tested. Development phones have spare memory. Force it: background the app, run adb shell am kill com.kosh.app, return.
  • Saving on unmount or on background only. Neither is guaranteed to run before a kill. Write through as the user types.
  • Restoring too much. A one-time password or a stale payment confirmation restored after an hour is worse than a clean start. Give drafts an expiry.
  • Global variables as state. Module-level variables reset on process death and persist across hot reloads in development, hiding bugs.
  • Work that should outlive the screen. A payment request started in a component is abandoned if the app is killed. Chapter 17 puts it in an outbox.

Trade-offs and when not to use it

Restoring the exact screen after process death is optional polish for most apps; restoring user input is not. Decide per screen. Persisting an entire global store to disk is easy to switch on and hard to migrate later; persist small, named pieces with versions.

Production and security

MMKV and AsyncStorage are plain files in the app sandbox. Tokens and anything sensitive belong in secure storage backed by Keystore and Keychain (chapter 21). Never persist card numbers. Hide sensitive screens from the app switcher (chapter 21).

The handful of native building blocks, and the three phases that turn a component into pixels.

Why it exists

Every UI toolkit needs primitives. React Native has few, and each maps to a real platform view. Knowing them, and what happens between "state changed" and "the screen updated", is what lets you reason about performance later.

Mental model

The three phases

  1. Render (JavaScript thread). React calls components and produces an element tree, then a tree of shadow nodes.
  2. Commit (often a background thread). Yoga computes sizes and positions; the new tree becomes "next to mount".
  3. Mount (UI thread). The differences are applied as create, update, insert and delete operations on native views.

Because the shadow tree lives in C++ and is immutable, React 19 features such as transitions and Suspense work, and layout can be read synchronously when needed (useLayoutEffect, ref.measure).

Accessibility is not optional

Native views bring native accessibility, but only if you label them: accessibilityRole, accessibilityLabel, accessibilityState. Screen readers read exactly what you provide. Touch targets should be at least 44 to 48 points.

End-to-end flow: showing a list of three rows

  1. The screen component renders and returns three TransactionRow elements.
  2. React creates shadow nodes: three pressables, each with a view and three texts.
  3. Yoga measures text (asking the platform for text metrics) and positions everything.
  4. The mount phase creates native views and sets their frames.
  5. The platform draws. Later re-renders repeat the steps only for what changed.

Failure modes

  • Text outside Text. A string directly inside a View throws at runtime.
  • Expecting CSS inheritance. Setting color on a View does not colour the text inside. Text styles inherit only from parent Text.
  • ScrollView for long lists. Hundreds of rows all mounted at once: slow start and high memory.
  • Inline heavy work in render. Sorting and formatting on every render. Compute once in the state holder.
  • Unlabelled controls. An icon-only button with no accessibility label is invisible to a screen reader.

Trade-offs and when not to use it

The core set is deliberately small. For platform-specific controls (date pickers, menus, native tab bars) use libraries that wrap the real native components, such as Expo UI, rather than imitations drawn in JavaScript. Imitations look right on one OS version and wrong on the next.

Production and security

Mark sensitive inputs: secureTextEntry for secrets, correct textContentType and autoComplete so password managers and one-time-code autofill work, and importantForAutofill="no" where autofill would leak.

II · UI framework · Chapter 7

The React mental model

UI as a function of state, and the rules that make re-running that function safe and cheap.

Why it exists

Imperative UI code keeps a tree of views in step with data by hand, and every "screen disagrees with data" bug comes from that. React inverts it: describe the UI for a given state, and let the runtime work out the changes.

Mental model

UI = f(state). You never update the screen. You replace state, and the function runs again.

Mechanics

Rendering is calling your function. It may happen often, be paused, or be thrown away. So components must be pure: same props and state in, same elements out, no side effects during render.

State is a snapshot. Within one render, state values are constants. setCount(count + 1) twice in one handler adds one, not two; use the updater form setCount(c => c + 1) when the next value depends on the previous.

Identity comes from position and key. React matches elements between renders by their place in the tree. In lists, a stable key tells it which item is which.

// Lifting state: the parent owns it, children receive values and callbacks
export function TransferForm({ balance }: { balance: Money }) {
  const [amountText, setAmountText] = useState('');

  // Derived data: computed during render, never stored
  const amount = parseMoney(amountText);
  const error = amountText === '' ? null
    : amount === null ? 'Enter a valid amount'
    : amount.minor > balance.minor ? 'Not enough balance' : null;

  return (
    <View style={{ gap: 12 }}>
      <AmountField value={amountText} onChangeText={setAmountText} error={error} />
      <SendButton disabled={amount === null || error !== null} />
    </View>
  );
}

function AmountField(props: { value: string; onChangeText: (t: string) => void; error: string | null }) {
  return (
    <View>
      <TextInput value={props.value} onChangeText={props.onChangeText}
                 keyboardType="decimal-pad" inputMode="decimal" placeholder="Amount"
                 accessibilityLabel="Amount" />
      {props.error && <Text accessibilityRole="alert">{props.error}</Text>}
    </View>
  );
}

Effects are for the outside world

// Good: synchronising with something external, with cleanup
useEffect(() => {
  const socket = openPriceSocket(symbol, setPrice);
  return () => socket.close();
}, [symbol]);

// Bad: copying props to state. Compute `fullName` during render.
useEffect(() => { setFullName(first + ' ' + last); }, [first, last]);

Ask of every effect: what external system is this keeping in step? If the answer is "none", it should be a calculation or an event handler.

Context

Context passes a value to any depth without threading props: theme, session, dependency container. Every consumer re-renders when the value changes, so keep context values stable and narrow.

Concurrency features

useTransition marks an update as non-urgent so typing stays responsive while a heavy list re-renders. Suspense shows a fallback while a child waits for data or code. Both work in React Native on the New Architecture.

End-to-end flow: one keystroke in the amount field

  1. The native field reports "2" then "25". onChangeText('25') runs.
  2. setAmountText('25') schedules a render of TransferForm.
  3. TransferForm runs: amount and error are recomputed from the new text.
  4. React compares elements. AmountField's value changed; SendButton's disabled changed.
  5. With the compiler, components whose props did not change are skipped without any manual memoisation.
  6. Fabric commits two prop updates.

Failure modes

  • Side effects in render. A network call in the component body runs on every render.
  • State that duplicates props or other state. Two sources of truth drift apart.
  • Unstable keys. Using the array index as key makes rows swap state when the list reorders.
  • Stale closures. A timer callback captures an old state value. Use the updater form or a ref.
  • Giant context. One context holding the whole app state re-renders everything on every change.

Trade-offs and when not to use it

React's model costs a mental shift for engineers from imperative UI backgrounds, and hides when work happens. It repays that with far fewer consistency bugs. Do not fight it with refs and imperative calls except at the edges: focus management, scrolling to an item, animations (chapter 23).

Production and security

Enable strict mode in development: it runs renders and effects twice to expose impurity and missing cleanup. Bugs it reveals are real and will appear in production under concurrency.

Navigation

Screens as files, a native stack underneath, and URLs as the address of everything.

Why it exists

An app is many screens with a history. Users expect the platform's own transitions and gestures: the iOS swipe back, the Android back button and predictive back. Writing that by hand is hopeless, so navigation libraries drive real native navigation containers. Expo Router adds a convention: the file tree under app/ is the route tree, and every screen has a URL.

Mental model

Every screen has an address. Navigating is going to an address. The back stack is managed natively; you describe structure with layout files.

Mechanics

Stacks, tabs, modals. The stack is a native stack on each platform. Tabs can be the platform's own tab bar. Modals and sheets are presentation options on a screen.

Passing results back. Write to shared state (a store, the query cache, or search params) and go back. Do not pass callbacks through navigation params; params must be serialisable.

End-to-end flow: a link to a transaction, signed out

  1. The user taps https://kosh.example/tx/123. The OS opens Kosh with that URL.
  2. Expo Router resolves the path to app/tx/[id].tsx.
  3. The root layout's guard is false, so that route does not exist yet. The router shows sign-in.
  4. The user signs in. status changes; the protected group appears.
  5. The app navigates to the originally requested URL, with Home beneath it in the stack so back makes sense.
  6. The detail screen validates id and loads the transaction.

Failure modes

  • Objects in params. They are stale, are lost on reload, and break deep links. Pass ids.
  • Navigating during render. Calling router.push in a component body pushes on every render. Use event handlers, effects, or <Redirect>.
  • Double pushes. A fast double tap opens the same screen twice. Disable the control while navigating.
  • Auth checks per screen. Easy to forget one. Guard at the layout.
  • Assuming screens unmount. A screen under another in the stack stays mounted and keeps its effects running. Pause work on blur with useFocusEffect.
  • Android back ignored in custom overlays. Handle it or use a navigation-based modal.

Trade-offs and when not to use it

File-based routing gives deep links and typed routes with little effort. React Navigation, with routes configured in code, is the long-established alternative and suits dynamic navigation structures and brownfield apps. Both render the same kind of native containers.

Production and security

Every route is reachable by URL, so every screen must cope with missing or malicious parameters. Never put secrets or personal data in a path or query string; URLs are logged by analytics, crash reporters and the OS.

Adaptive UI

One codebase across phones, foldables, tablets, desktop windows and two operating systems.

Why it exists

React Native already spans two platforms. Each also spans form factors: folding phones, tablets, split screen, desktop windowing. For apps targeting Android 17 (API 37), the platform ignores orientation and resizability restrictions on large screens, so a portrait lock in your app config no longer holds there. Layouts must respond to whatever window they get.

Mental model

Window size is state. Read it with a hook, pick a layout from it, and never ask what kind of device this is.

Mechanics

Navigation chrome. Tabs at the bottom on compact widths; a side rail or sidebar when wider. Expo Router's native tabs and split view adapt on tablets; check their current status before depending on them.

Platform conventions. Adaptive also means respecting each OS: back gesture and placement of primary actions differ, system fonts differ, haptics differ. Share structure and behaviour; let controls be native.

Input. Large screens come with keyboards, mice and trackpads. Pressable reports hover; make focus order sensible and visible.

End-to-end flow: unfolding a phone on the transactions screen

  1. The window width changes from about 380 to about 700 points.
  2. Nothing restarts. useWindowDimensions returns the new size and the screen re-renders.
  3. useWidthClass now returns medium. The component returns the two-pane tree.
  4. Yoga lays out both panes. The list keeps its scroll position because it is the same component instance.
  5. selectedId is component state, so it survives. A detail screen that was pushed on the stack in compact mode needs a decision: pop it and select the same id.

Failure modes

  • Reading dimensions once. Dimensions.get('window') at module load never updates. Use the hook.
  • Branching on device type. A tablet in split screen has a compact window.
  • Orientation locks. Ignored on large Android screens under API 37 targeting. Layouts that never considered landscape show stretched content.
  • Two navigation models out of step. Detail as a pushed screen in compact mode and as a pane in wide mode, with the selection lost when resizing between them.
  • One platform's idiom on the other. An iOS-style bottom sheet and swipe actions on Android without the Android back behaviour.

Trade-offs and when not to use it

Two-pane layouts cost design and test effort on two platforms. A centred single column with a maximum width is an acceptable first release on large screens; a stretched or letterboxed phone layout is not.

Production and security

Wider layouts keep sensitive data visible longer and to more onlookers. Consider masking balances by default on expanded widths. Test resizing continuously in a resizable emulator and iPad multitasking.

III · Architecture patterns · Chapter 11

MVC in React Native

The first pattern everyone reaches for, what it looks like in a component world, and where it gives way.

Why it exists

Model-View-Controller comes from Smalltalk in the 1970s. Its purpose is one idea: the code that knows the business rules should not know how it is displayed. Every later pattern refines that. React blurs the picture because a component can be view and controller at once, which is exactly why the pattern is worth studying here.

Mental model

The Model holds data and rules. The View draws and reports input. The Controller receives input, asks the Model to act, and decides what the View shows.

In React Native the natural mapping is: plain TypeScript as Model, JSX as View, and the component's handlers and state as Controller. When all three sit in one function you have the "fat component", the React equivalent of Android's massive activity.

Mechanics

The feature for this whole part is Kosh's Send money screen: an amount, a payee, a Send button, a result.

Model: no React imports

// transferModel.ts
export function validateTransfer(amountText: string, balance: Money): string | null {
  const amount = parseMoney(amountText);
  if (!amount) return 'Enter an amount';
  if (amount.minor > balance.minor) return 'Not enough balance';
  return null;
}

export async function sendTransfer(api: PaymentsApi, payeeId: string, amount: Money): Promise<TransferResult> {
  try {
    const dto = await api.transfer(payeeId, amount.minor);
    return { kind: 'success', reference: dto.reference };
  } catch {
    return { kind: 'networkError' };
  }
}

View and controller in one component

export default function TransferScreen() {
  const [amountText, setAmountText] = useState('');
  const [error, setError] = useState<string | null>(null);
  const [sending, setSending] = useState(false);
  const [result, setResult] = useState<TransferResult | null>(null);

  // Controller logic
  async function onSendPressed() {
    const problem = validateTransfer(amountText, balance);
    if (problem) { setError(problem); return; }
    setSending(true);
    const r = await sendTransfer(api, payeeId, parseMoney(amountText)!);
    setSending(false);                    // is this component still mounted?
    setResult(r);
  }

  return (
    <View style={{ gap: 12, padding: 24 }}>
      <TextInput value={amountText} onChangeText={t => { setAmountText(t); setError(null); }} keyboardType="decimal-pad" />

      <Pressable onPress={onSendPressed} disabled={sending}><Text>{sending ? 'Sending…' : 'Send'}</Text></Pressable>

    </View>

}

MVC done properly

Separate the controller into a class that knows nothing about React, and let the component be a passive view:

export interface TransferView {
  showAmountError(message: string): void;
  showLoading(loading: boolean): void;
  showResult(text: string): void;
}

export class TransferController {
  constructor(private api: PaymentsApi, private view: TransferView) {}

  async onSendPressed(amountText: string, payeeId: string, balance: Money) {
    const problem = validateTransfer(amountText, balance);
    if (problem) return this.view.showAmountError(problem);
    this.view.showLoading(true);
    const result = await sendTransfer(this.api, payeeId, parseMoney(amountText)!);
    this.view.showLoading(false);
    this.view.showResult(message(result));
  }
}

This works and is testable. It also feels foreign in React, because the controller commands the view while React wants the view to be a function of state. That friction is what the next chapter resolves.

End-to-end flow: tapping Send

  1. onSendPressed runs in the component.
  2. It asks the model to validate.
  3. It sets several pieces of state and awaits the model's call.
  4. The promise resolves. It sets state again and the component re-renders.

Four steps, one file. For a small screen this is fine, and most React Native apps start here.

Failure modes

  • The fat component. State, validation, networking, navigation and layout in one 600-line function.
  • Flags that contradict each other. Four separate useState calls allow sending and error and result all at once. Nothing forbids impossible combinations.
  • The user leaves during step 3. The component unmounts; the promise resolves and sets state on nothing. The result is lost, and the user does not know whether the money moved.
  • Double submit. Two fast taps before sending re-renders the button as disabled.
  • Logic you can only test by rendering. Slow tests, so fewer tests.

Unlike native Android, rotation does not destroy the component, so MVC lasts longer here before it hurts. Process death and navigation still expose the same weaknesses.

Trade-offs and when not to use it

Use a simple component with a model when Move on when
A settings screen, a static page, a prototype The screen has several interdependent states
Logic is two or three lines You want to unit test screen logic without rendering
State is local and disposable Work must outlive the screen

The Model separation is permanent: plain TypeScript functions with no React in them, at every scale. What changes next is where the controller logic and state live.

Production and security

Validation in the model is a usability feature, never a control. The server validates amount, balance and limits again; a modified JavaScript bundle can skip any client check.

From MVP to MVVM to Flux and MVI

The same screen three more ways. Each step removes one failure of the step before.

Why it exists

Chapter 11 left two problems: logic entangled with a component, and state scattered across flags. MVP gives testability. MVVM, which in React means a custom hook, gives logic a home that fits the framework. Flux and MVI replace scattered flags with one state and one way to change it.

Mental model

MVP: a presenter commands the view. MVVM: the view renders state from a hook. Flux and MVI: the view renders one state and dispatches one kind of message.

Mechanics

MVP

The TransferController from chapter 11 is a presenter in all but name. It is testable, and it fights React: the component must implement showLoading by calling setState, duplicating what React does natively. It is rare in React Native code for that reason.

}

// transferReducer.ts: no React
export type TransferState =
  | { phase: 'editing'; amountText: string; error: string | null }
  | { phase: 'sending'; amount: Money; idempotencyKey: string }
  | { phase: 'pending'; amount: Money; idempotencyKey: string }         // sent, outcome unknown
  | { phase: 'done'; reference: string }
  | { phase: 'failed'; reason: string; canRetry: boolean };

export type TransferEvent =
  | { type: 'amountChanged'; text: string }
  | { type: 'rejectedLocally'; reason: string }
  | { type: 'submitted'; amount: Money; idempotencyKey: string }
  | { type: 'settled'; reference: string }
  | { type: 'timedOut' }
  | { type: 'rejected'; reason: string };

export const initialTransferState: TransferState = { phase: 'editing', amountText: '', error: null };

export function transferReducer(s: TransferState, e: TransferEvent): TransferState {
  switch (s.phase) {
    case 'editing':
      if (e.type === 'amountChanged') return { ...s, amountText: e.text, error: null };
      if (e.type === 'rejectedLocally') return { ...s, error: e.reason };
      if (e.type === 'submitted') return { phase: 'sending', amount: e.amount, idempotencyKey: e.idempotencyKey };
      return s;
    case 'sending':
    case 'pending':
      if (e.type === 'settled') return { phase: 'done', reference: e.reference };
      if (e.type === 'timedOut') return { phase: 'pending', amount: s.amount, idempotencyKey: s.idempotencyKey };
      if (e.type === 'rejected') return { phase: 'failed', reason: e.reason, canRetry: false };
      return s;                                   // a second "submitted" here is a double tap: ignored by construction
    case 'done':
    case 'failed':
      return s;
  }
}

End-to-end flow: tapping Send with the reducer

  1. The view calls onSend. The view model validates and dispatches submitted with a fresh idempotency key.
  2. The reducer returns sending. The view shows progress; the button is gone because sending has no button.
  3. A second tap dispatches submitted again. The reducer returns the same state.
  4. The request times out. timedOut moves the state to pending: "We are confirming this payment."
  5. A later sync dispatches settled. The receipt appears.

Failure modes

  • Boolean soup in the hook. A view model with six flags has the same impossible states as the fat component. Use a discriminated union.
  • Side effects in the reducer. Reducers must be pure. Network calls go in the hook, a thunk or middleware.
  • Everything global. Form text in a global store makes every keystroke a global event. Keep state as local as it can be.
  • Server data copied into client state. It goes stale and you write synchronisation code by hand.
  • Unselective store subscriptions. A component that reads the whole store re-renders on every change. Select the slice it needs.

Trade-offs and when not to use it

The default in this book: a custom hook per screen as its view model, a reducer inside it when the screen is a state machine, a query cache for server data, and a small store for the little client state that is truly shared. Redux remains a sound choice for large teams who value its conventions. Avoid introducing a store before you have state that two distant screens share.

Production and security

A reducer gives an audit trail: log event types and phases, never amounts, account numbers or tokens. Double-submit protection belongs in the state machine and again on the server through idempotency keys (chapter 16).

Layers and dependency injection

Where business rules live once they leave the hook, and how code finds its collaborators.

Why it exists

A view-model hook organises one screen. An app has fifty screens sharing the same accounts, session and rules. Without structure each hook grows its own copy of "fetch, cache, map, validate", and components import fetch directly. Layering gives each concern one home. Dependency injection lets tests and environments swap the edges.

Mental model

Three layers, one direction. UI depends on domain, domain depends on data interfaces. The domain is plain TypeScript: no React, no React Native, no network library.

Async, the event loop and server state

One JavaScript thread, promises that cannot be forgotten, and a cache that does most of the work.

Why it exists

All your application code shares one JavaScript thread. Nothing can block it, so everything slow is asynchronous: network, storage, native modules. JavaScript makes that readable with async and await, but it has no structured concurrency: a promise, once started, runs to completion whether or not anyone still wants the answer. Managing that by hand in every screen is where most React Native bugs live, and it is why a server-state library earns its place.

Mental model

One thread, one queue. await gives the thread back until the result is ready. A started promise cannot be stopped; you can only ignore its result or abort the underlying work with a signal.

Mechanics

Cancellation is opt-in

export async function fetchJson<T>(url: string, init: RequestInit & { timeoutMs?: number } = {}): Promise<T> {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), init.timeoutMs ?? 20_000);
  init.signal?.addEventListener('abort', () => controller.abort());      // honour the caller's signal too
  try {
    const response = await fetch(url, { ...init, signal: controller.signal });
    if (!response.ok) throw new HttpError(response.status, await response.text());
    return (await response.json()) as T;                                  // validated properly in chapter 16
  } finally {
    clearTimeout(timer);
  }
}

End-to-end flow: opening Home

  1. useRecentTransactions mounts. The cache has data from a minute ago, so it is returned immediately and marked stale.
  2. The query function runs in the background with an abort signal.
  3. The user leaves the screen before the response. The query has no observers; the signal aborts and the native request is cancelled.
  4. They return. The query runs again; the response updates the cache; the component re-renders with fresh data.
  5. A transfer succeeds elsewhere. invalidateQueries marks transactions stale and the visible list refetches.

Compare with doing this by hand: an effect, three pieces of state, a mounted flag, a race between two responses.

Failure modes

  • Fetching in useEffect by hand. Races (an older response overwrites a newer one), no cancellation, duplicated loading state.
  • Unhandled rejections. An async function called without await or .catch fails silently, or crashes in strict environments.
  • await in a loop. Ten sequential requests where Promise.all would do. Or the reverse: a thousand parallel requests flooding the network.
  • A mutation tied to the component. The user navigates away; the request finishes but nobody handles the result. Payments go through the outbox (chapter 17).
  • Timers in the background. setTimeout does not fire reliably when the app is suspended.
  • Blocking the thread. A synchronous loop over 50,000 items freezes every tap.

Trade-offs and when not to use it

TanStack Query is the default here; RTK Query is the natural choice if you already use Redux; SWR is a lighter alternative. For two requests on one screen, a hand-written hook is fine. Do not put server data in a global client store and synchronise it yourself.

Production and security

Decide per boundary which failures are data and which are bugs: repositories convert expected failures into result types; unexpected ones reach the crash reporter. Clear the query cache on sign-out. Never log response bodies from payment calls.

Local persistence

Three kinds of storage on the device, and which data belongs in each.

Why it exists

Memory is temporary (chapter 5) and the network is unreliable. The disk is the only place state reliably survives. React Native has no built-in storage at all, so you choose native modules: a key-value store for settings, a relational database for records, and secure storage for secrets.

Mental model

Three drawers. Small settings in key-value storage, records in SQLite, secrets in the platform's hardware-backed store. Putting something in the wrong drawer is either slow or unsafe.

const MIGRATIONS: string[] = [
  /* 1 */ `CREATE TABLE transactions (
             id TEXT PRIMARY KEY NOT NULL, account_id TEXT NOT NULL, counterparty TEXT NOT NULL,
             amount_minor INTEGER NOT NULL, currency TEXT NOT NULL, posted_at INTEGER NOT NULL);
           CREATE INDEX idx_tx_account_time ON transactions(account_id, posted_at DESC);`,

             idempotency_key TEXT PRIMARY KEY NOT NULL, payee_id TEXT NOT NULL, amount_minor INTEGER NOT NULL,

export async function openDatabase(): Promise<SQLite.SQLiteDatabase> {
  const db = await SQLite.openDatabaseAsync('kosh.db');
  await db.execAsync('PRAGMA journal_mode = WAL; PRAGMA foreign_keys = ON;');

  const row = await db.getFirstAsync<{ user_version: number }>('PRAGMA user_version');
  let version = row?.user_version ?? 0;
  while (version < MIGRATIONS.length) {
    await db.withTransactionAsync(async () => {
      await db.execAsync(MIGRATIONS[version]!);
      await db.execAsync(`PRAGMA user_version = ${version + 1}`);
    });
    version++;
  }
  return db;
}

Failure modes

  • String-built SQL. Injection, and broken queries on the first apostrophe. Always bind parameters.
  • Migrations that cannot run twice or skip versions. Users jump from version 1 to 5. Number them, run them in order, in transactions.
  • Everything in AsyncStorage. One giant JSON blob parsed on the JavaScript thread at startup.
  • Secrets in plain storage. MMKV and AsyncStorage are readable files on a rooted device and in backups.
  • Unbounded caches. Nobody prunes, and the app is using a gigabyte in two years.
  • Stale UI. A write with no invalidation and no live query.

Trade-offs and when not to use it

Raw expo-sqlite is transparent and has no magic. Drizzle adds typed schemas, generated migrations and live queries for modest overhead. Store nothing for data you must not keep, such as a full card number.

The app sandbox and OS file encryption protect data at rest on an unrooted, locked device. For a higher bar use SQLCipher (supported by expo-sqlite as a build option) with a key held in secure storage. Exclude sensitive files from cloud backup. Networking

HTTP from a device that changes networks mid-request, with responses you have actually checked.

Why it exists

A phone calls from a train entering a tunnel, behind a captive portal, switching from Wi-Fi to mobile data. React Native's fetch runs on each platform's native HTTP stack, so connection reuse and TLS are handled for you. What it does not give you is timeouts, typed responses, or a sane error model. You build a thin client once.

Mental model

Every call has three outcomes, not two: success, a response that says no, and no response at all. And TypeScript types say nothing about what the server really sent.

Mechanics

Errors as data

export type ApiResult<T> =
  | { ok: true; value: T }
  | { ok: false; kind: 'rejected'; status: number; reason?: string }     // the server said no
  | { ok: false; kind: 'unreachable' }                                   // never got an answer
  | { ok: false; kind: 'unknown' }                                       // sent, outcome not known
  | { ok: false; kind: 'malformed' };                                    // answered with something unexpected

type Options<T> = { method?: 'GET' | 'POST'; body?: unknown; schema: z.ZodType<T>;
                    headers?: Record<string, string>; signal?: AbortSignal; timeoutMs?: number };

export function createHttpClient(baseUrl: string, getToken: () => string | null, appVersion: string) {
  return async function request<T>(path: string, o: Options<T>): Promise<ApiResult<T>> {
    const controller = new AbortController();
    const timer = setTimeout(() => controller.abort(), o.timeoutMs ?? 20_000);
    o.signal?.addEventListener('abort', () => controller.abort());
    let sent = false;
    try {
      const token = getToken();
      sent = true;
      const res = await fetch(baseUrl + path, {
        method: o.method ?? 'GET',
        signal: controller.signal,
        headers: {
          Accept: 'application/json',
          'X-App-Version': appVersion,
          'X-Request-Id': Crypto.randomUUID(),
          ...(o.body ? { 'Content-Type': 'application/json' } : {}),
          ...(token ? { Authorization: `Bearer ${token}` } : {}),
          ...o.headers,
        },
        body: o.body ? JSON.stringify(o.body) : undefined,
      });
      if (!res.ok) return { ok: false, kind: 'rejected', status: res.status, reason: await safeReason(res) };
      const parsed = o.schema.safeParse(await res.json().catch(() => null));
      return parsed.success ? { ok: true, value: parsed.data } : { ok: false, kind: 'malformed' };
    } catch (e) {
      const timedOut = controller.signal.aborted && !o.signal?.aborted;
      // a write that timed out may have reached the server
      return timedOut && sent && o.method === 'POST' ? { ok: false, kind: 'unknown' } : { ok: false, kind: 'unreachable' };
    } finally {
      clearTimeout(timer);
    }
  };
}

      method: 'POST', schema: TransferDto,
      headers: { 'Idempotency-Key': input.idempotencyKey },
      body: { payee_id: input.payeeId, amount_minor: input.amountMinor, currency: 'INR' },
    }),
});

Idempotency

A timeout on POST /transfers does not tell you whether the money moved. The client generates a unique key per user intent, stores it before sending, and sends the same key on every retry. The server returns the original result for a repeated key. Without this, a retry is a second payment.

End-to-end flow: one GET

  1. A query function calls the repository, which calls request.
  2. fetch crosses into native code: OkHttp on Android, URLSession on iOS.
  3. The native stack reuses a pooled connection or performs DNS, TCP and TLS.
  4. The response body returns to JavaScript as text and is parsed.
  5. The schema validates the shape. A mismatch becomes malformed, not a crash three screens later.
  6. The repository maps the DTO to a domain model and writes to SQLite.

Failure modes

  • Treating a timeout as a failure. The user is told "payment failed" and pays again. unknown needs its own screen: "We are confirming this payment."
  • as instead of validation. The server sends null for a field typed as string, and the app crashes far from the cause.
  • No timeout. fetch has none by default.
  • Automatic retry of a POST. Safe only with an idempotency key.
  • Captive portals. Every call returns an HTML login page; res.json() throws. The client above reports malformed.
  • Logging requests. Tokens and account numbers in logs and crash breadcrumbs.
  • Huge JSON. Parsing megabytes blocks the JavaScript thread. Paginate.

Trade-offs and when not to use it

A hand-written client like the one above is about sixty lines and has no surprises. Axios adds interceptors and is widely known; ky is a small fetch wrapper. Generated clients from an OpenAPI schema remove a class of mistakes if your backend publishes one. GraphQL clients suit screens that aggregate many resources. Certificate pinning is not available through fetch configuration; it is native configuration (chapter 21).

Production and security

Send app version, platform, a request id and a W3C traceparent on every call. Android blocks cleartext HTTP by default and iOS App Transport Security does the same; never loosen either in release. For PCI DSS, let the payment provider's SDK collect and tokenise card numbers so they never pass through your JavaScript.

Offline-first and background sync

Read locally, write through an outbox, and accept how little background time a phone will give you.

Why it exists

Mobile connectivity is intermittent and the process can die at any moment. An app that reads straight from the network shows spinners in lifts and loses writes when the user leaves. Offline-first design decouples the UI from the network. In React Native there is an extra constraint: JavaScript only runs while the app process is alive and the OS allows it, and iOS in particular allows very little in the background.

Mental model

Reads come from local storage. Writes go into local storage first, as intentions. Sync runs whenever it gets the chance: app open, foreground, reconnect, a push, and occasionally a background task. Never depend on only one of those.

Mechanics

Read path

export class OfflineFirstTransactionsRepository {
  constructor(private api: PaymentsApi, private dao: TransactionsDao) {}

  /** What the UI reads. Fast, always available. */
  recent = (accountId: string) => this.dao.recent(accountId).then(rows => rows.map(toDomain));

  /** Brings truth from the server into the database. */
  async refresh(accountId: string): Promise<ApiResult<void>> {
    const result = await this.api.transactions(accountId);
    if (!result.ok) return result;
    await this.dao.upsertMany(result.value.items.map(toRow));
    return { ok: true, value: undefined };
  }
}

Write path: the outbox

/** Called when the user confirms. Returns as soon as the intention is safely on disk. */
export async function queueTransfer(db: SQLiteDatabase, payee: Payee, amount: Money): Promise<string> {
  const key = Crypto.randomUUID();                 // one key per user intent, reused on every retry
  const now = Date.now();
  await db.withTransactionAsync(async () => {      // both rows, or neither
    await db.runAsync(
      `INSERT INTO outbox (idempotency_key, payee_id, amount_minor, state, created_at) VALUES (?, ?, ?, 'queued', ?)`,
      [key, payee.id, amount.minor, now]);
    await db.runAsync(
      `INSERT INTO transactions (id, account_id, counterparty, amount_minor, currency, posted_at, status)
       VALUES (?, ?, ?, ?, ?, ?, 'pending')`,
      [`pending-${key}`, payee.fromAccountId, payee.name, -amount.minor, amount.currency, now]);
  });
  void drainOutbox();                              // try now; other triggers will try again
  return key;
}

let draining: Promise<void> | null = null;

/** Safe to call from anywhere, any number of times. */
export function drainOutbox(): Promise<void> {
  draining ??= (async () => {
    try {
      for (const item of await outbox.queued()) {
        const r = await api.transfer({ payeeId: item.payee_id, amountMinor: item.amount_minor, idempotencyKey: item.idempotency_key });
        if (r.ok) await outbox.markConfirmed(item.idempotency_key, r.value.reference);
        else if (r.kind === 'rejected') await outbox.markFailed(item.idempotency_key, r.reason);
        else break;                                // unreachable or unknown: same key, later
      }
      queryClient.invalidateQueries({ queryKey: ['transactions'] });
    } finally { draining = null; }
  })();
  return draining;
}

End-to-end flow: sending money in a lift

  1. The user confirms. One transaction writes the outbox row and a pending transaction.
  2. The list refetches from SQLite; the payment appears as "Sending".
  3. drainOutbox tries the API and gets unreachable. It stops.
  4. The user leaves the lift. NetInfo reports connectivity; drainOutbox runs again with the same key.
  5. The server accepts. The outbox row is confirmed; the transaction becomes posted.
  6. If the app had been killed at step 3 instead, the next app open or background task would do step 4.

Failure modes

  • Relying on background tasks. On iOS they may not run for hours or at all for rarely used apps. They are a bonus, never the plan.
  • Duplicate submission. Two triggers at once, or a lost response. The single-flight guard and the idempotency key make it harmless.
  • Optimistic lies. Showing the balance reduced before the server agrees. Show the pending item and the last confirmed balance with its time.
  • A mutation that lives in a component. Unmounted, killed, lost. The outbox is on disk.
  • Sync storms. A million devices syncing on the hour. Add jitter.
  • Stale forever. Show "Updated 2 hours ago" whenever data may be old.

Trade-offs and when not to use it

Offline-first roughly doubles the data layer. It is worth it for content the user revisits and writes they must not lose. A lighter option is TanStack Query with a persisted cache and paused mutations, which suits apps where brief offline periods matter and conflicts do not. For data that must be live to mean anything (an FX quote, an OTP, a card authorisation), call the network directly and cache nothing.

Production and security

Queued payment intentions are sensitive. Expire outbox rows after a short window, require fresh authentication for anything queued beyond it, and make the server reject stale keys. Monitor outbox age as a product metric, split by platform, because the two platforms will behave differently.

Talking to many backends

Identity, banking, payments, market data and flags are different services. The app must make them feel like one.

Why it exists

Kosh calls an identity provider, a core banking API, a payments API, a market data feed, push providers, feature flags and analytics. Each has its own base URL, credentials, latency and failure behaviour. Treating them as one "the backend" produces a client where a slow analytics call delays sign-in.

Mental model

Each remote service gets its own typed client and its own failure budget. Repositories compose them. A screen should degrade by section, never as a whole.

Mechanics

One client factory, several clients

const banking = createHttpClient(config.bankingUrl, session.accessToken, version);       // bearer token

// The identity provider gets a client that never attaches the access token.

The token getter is passed per client, so a credential for one service cannot be sent to another host by accident.

Tokens: refresh once, not five times

export class Session {
  private access: string | null = null;
  private refreshing: Promise<string | null> | null = null;

  accessToken = () => this.access;

  /** Single-flight: concurrent callers share one refresh. */
  refresh(): Promise<string | null> {
    this.refreshing ??= (async () => {
      try {
        const refreshToken = await SecureStore.getItemAsync('refresh');
        if (!refreshToken) return null;
        const r = await identity.token({ grant_type: 'refresh_token', refresh_token: refreshToken });
        if (!r.ok) { if (r.kind === 'rejected') await this.signOut(); return null; }   // revoked: sign out
        await SecureStore.setItemAsync('refresh', r.value.refresh_token);              // providers rotate these
        this.access = r.value.access_token;
        return this.access;
      } finally { this.refreshing = null; }
    })();
    return this.refreshing;
  }
}

/** Wrap a client: on 401, refresh once and retry once. */
export const withAuthRetry = (request: Request, session: Session): Request =>
  async (path, options) => {
    const first = await request(path, options);
    if (first.ok || first.kind !== 'rejected' || first.status !== 401) return first;
    return (await session.refresh()) ? request(path, options) : first;
  };

When an access token expires, five parallel calls get 401 together. The shared promise lets the first refresh and the other four wait for its result.

Resilience, borrowed from the server side

export async function retrying<T>(fn: () => Promise<ApiResult<T>>, attempts = 3, baseMs = 300): Promise<ApiResult<T>> {
  let last: ApiResult<T> = { ok: false, kind: 'unreachable' };
  for (let i = 0; i < attempts; i++) {
    last = await fn();
    if (last.ok || last.kind !== 'unreachable') return last;        // only "never reached the server" is safe to repeat
    const ceiling = Math.min(baseMs * 2 ** i, 5_000);
    await sleep(ceiling / 2 + Math.random() * (ceiling / 2));       // jitter
  }
  return last;
}

Give each downstream an audience-restricted token. Propagate a trace id from the device so an incident can be followed from tap to ledger entry. Keep access tokens in memory only; persist only the refresh token, in secure storage.

Realtime and push

Polling, streams and push notifications across two operating systems with different rules.

Why it exists

Users expect an incoming payment to appear without pulling to refresh. A phone cannot hold a socket open in the background, and in React Native your JavaScript is not even running then. While the app is on screen you may stream. When it is not, the platform's push service (FCM on Android, APNs on iOS) is the only way in.

Mental model

Foreground: hold a stream. Background: wait for a push. Either way the message is a hint to sync, and local storage stays the source of truth.

Mechanics

A WebSocket hook that follows the app

export function usePriceStream(symbol: string): PriceTick | null {
  const [tick, setTick] = useState<PriceTick | null>(null);
  const active = useAppIsActive();                       // chapter 2
  const focused = useIsFocused();                        // only while this screen is on top

  useEffect(() => {
    if (!active || !focused) return;                     // closed in the background and under other screens
    let socket: WebSocket | null = null, attempt = 0, stopped = false;
    let timer: ReturnType<typeof setTimeout>;

    const connect = async () => {
      const ticket = await session.streamTicket();       // short-lived, fetched per connection
      if (stopped) return;
      socket = new WebSocket(`wss://stream.kosh.example/prices/${symbol}?ticket=${ticket}`);
      socket.onopen = () => { attempt = 0; };
      socket.onmessage = e => {
        const parsed = PriceTick.safeParse(JSON.parse(e.data));
        if (parsed.success) setTick(parsed.data);
      };
      socket.onclose = () => {
        if (stopped) return;
        const ceiling = Math.min(500 * 2 ** attempt++, 30_000);
        timer = setTimeout(connect, ceiling / 2 + Math.random() * (ceiling / 2));    // backoff with jitter
      };
    };
    void connect();

    return () => { stopped = true; clearTimeout(timer); socket?.close(1000); };
  }, [symbol, active, focused]);

  return tick;
}

Native modules and connectivity inside the device

Calling Kotlin and Swift from TypeScript, and how links, files and other apps reach yours.

Why it exists

Some services Kosh connects to are on the device itself: the Keystore, a payment SDK shipped as native libraries, another app handing over a payment request, the OS opening a link. React Native reaches all of these through native modules. Most already exist as packages. Sooner or later you need one that does not.

Mental model

A native module is a small typed API implemented twice, once in Kotlin and once in Swift, and called from TypeScript as if it were local. JSI makes the call direct; your job is to keep the interface narrow.

Mechanics

End-to-end flow: signing.signTransfer(...) on Android

  1. TypeScript calls the function. Through JSI this reaches the Kotlin module without serialising to JSON.
  2. The module finds the current activity and shows BiometricPrompt on the UI thread.
  3. The user presents a fingerprint. The Keystore releases the key for one operation and signs.
  4. The module resolves the promise with the signature.
  5. TypeScript resumes after await and sends the signature to the server.

The private key never existed in JavaScript, and no JavaScript code can approve the signature without the hardware step.

Failure modes

  • Wide native interfaces. Twenty methods mirrored on two platforms drift apart. Keep modules small and do the logic in TypeScript.
  • Different behaviour per platform. One side rejects, the other resolves null. Write the TypeScript wrapper to normalise, and test both.
  • Blocking the UI thread in a module. Heavy work in a synchronous function freezes the app.
  • Forgetting it needs a new binary. Native code cannot be delivered over the air (chapter 27).
  • Unverified links. A wrong association file sends links to the browser, and phishing apps can register the same custom scheme.
  • Trusting link parameters. Amounts or payees taken from a URL.

Trade-offs and when not to use it

Look for a maintained package first. Write a module when the capability is specific to you (your signing scheme, a vendor SDK) or when a package's quality is a risk for something security-critical. If most of your features need custom native code on both platforms, reconsider how much React Native is saving.

Production and security

Every native entry point (links, share targets, exported Android components that libraries add) belongs in the threat model: who may call it, how the caller is verified, what is validated. Audit third-party native modules as you would any dependency with full device access, because that is what they are.

Identity and security

Who the user is, where secrets live, and what a wallet must assume about a readable bundle on an uncontrolled phone.

Why it exists

Every connection in this part carries a credential. On a phone the attacker may hold the device, and the app binary is public. In React Native there is one more fact: your logic ships as a JavaScript bundle that can be extracted, read and modified more easily than compiled native code. That does not make React Native unsuitable for finance. It decides where controls must live.

Mental model

JavaScript decides what to ask for. Hardware and the server decide whether it is allowed. Any check that exists only in JavaScript is a convenience, not a control.

Mechanics

Threat Main defences
Lost or stolen unlocked phone Biometric or PIN before sensitive actions, short sessions
Malicious app on the device Sandbox, verified links, no secrets in URLs
Network attacker TLS everywhere, optional certificate pinning
Reverse engineering, modified bundle No secrets in the bundle, server-side enforcement
Rooted device, repackaged app Play Integrity and App Attest verdicts, checked on the server

Sign-in

OAuth 2.0 authorization code flow with PKCE in the system browser. No client secret in the app. Never an embedded web view.

import * as AuthSession from 'expo-auth-session';
import * as WebBrowser from 'expo-web-browser';

export function useSignIn() {
  const discovery = AuthSession.useAutoDiscovery('https://id.kosh.example');
  const redirectUri = AuthSession.makeRedirectUri({ scheme: 'kosh', path: 'auth' });
  const [request, , promptAsync] = AuthSession.useAuthRequest(

    const tokens = await AuthSession.exchangeCodeAsync(
      { clientId: 'kosh-mobile', code: result.params.code, redirectUri, extraParams: { code_verifier: request.codeVerifier } },

    return true;
  };
}

End-to-end flow: a transfer above the step-up limit

  1. The user confirms ₹50,000. The server replies that step-up is required, with a challenge.
  2. TypeScript builds the bytes to sign: challenge, payee, amount, idempotency key.
  3. The native module shows the biometric prompt. The user presents a fingerprint or face.
  4. Secure hardware releases the key for one operation and signs.
  5. The app sends the transfer with the signature and an integrity token.
  6. The server verifies the signature against the enrolled key, checks the verdict, and posts the transfer.

Failure modes

  • Secrets in the bundle or in extra. API keys, "encryption keys", feature unlock codes. All readable.
  • A boolean biometric check guarding money. See above.
  • Tokens in AsyncStorage or MMKV. Plain files.
  • Client-side limits and role checks treated as enforcement. A patched bundle ignores them.
  • Pinning without an exit. A certificate rotates and every installed copy stops working. With over-the-air updates you can change JavaScript, but not native pins.
  • Keys lost on restore. Hardware keys do not migrate to a new phone. Design re-enrolment as a normal path.
  • Untrusted over-the-air updates. Enable code signing for updates so only bundles you signed will run (chapter 27).

Trade-offs and when not to use it

Obfuscating JavaScript raises the cost of reading it slightly and is not a control. Root and jailbreak detection in JavaScript is trivially bypassed; use attestation verified by the server and respond in grades (lower limits, more step-up) rather than blocking outright. Pin only the most sensitive hosts, or accept the operational risk knowingly.

Production and security

For PCI DSS, use a certified provider's native SDK or hosted fields so card numbers never enter your JavaScript, memory or logs. For SOC 2, show who can publish an over-the-air update, how it is signed, and how a vulnerable version is retired. Review against the OWASP MASVS, and include the JavaScript bundle and the update channel in every penetration test scope.

Glass UI in React Native

Translucent, blurred surfaces on two platforms that implement them very differently.

Why it exists

Glass surfaces (frosted panels that let colour through from behind) give depth without heavy borders: a tab bar floating over a list, a balance card over a gradient. iOS has a native, highly optimised material for this and, since iOS 26, the Liquid Glass style. Android has no direct equivalent, and its blur support depends on OS version. A cross-platform glass design therefore has to be planned as two implementations and one fallback.

Mental model

Glass is four layers: something colourful behind, a blur of it, a translucent tint, and a thin bright edge. The tint and edge are free everywhere. The blur is where the platforms differ and where the cost is.

Choosing a level at runtime

export type GlassLevel = 'tint' | 'blur';

export function useGlassLevel(): GlassLevel {
  const reduceTransparency = useReduceTransparency();        // AccessibilityInfo, iOS setting
  const lowPower = useLowPowerMode();                        // expo-battery
  const flags = useFlags();
  const supported = Platform.OS === 'ios' || Number(Platform.Version) >= 31;
  return supported && !reduceTransparency && !lowPower && flags.glassBlur ? 'blur' : 'tint';
}

function useReduceTransparency() {
  const [on, setOn] = useState(false);
  useEffect(() => {
    AccessibilityInfo.isReduceTransparencyEnabled().then(setOn);
    const sub = AccessibilityInfo.addEventListener('reduceTransparencyChanged', setOn);
    return () => sub.remove();
  }, []);
  return on;
}

End-to-end flow: one frame of a list scrolling under a glass bar

  1. The native scroll view moves on the UI thread. No JavaScript runs.
  2. The blur view needs the pixels now behind it. On iOS the compositor does this as part of drawing the material. On Android the content behind is captured and blurred.
  3. The GPU downsamples and blurs that region.
  4. The tint, border and the bar's own content are composited on top.
  5. All of it must fit the frame budget: 8.3 ms at 120 Hz.

Because scrolling and blur both happen natively, JavaScript load does not make a glass bar stutter. GPU load does.

Failure modes

  • Designing on an iPhone only. It looks perfect, and then Android shows either no blur or dropped frames.
  • Unreadable text. White text is fine over a dark photo and unreadable over a white receipt. The scrim must guarantee contrast whatever scrolls underneath.
  • Jank on mid-range Android. Large blurred areas, several stacked blur views, or blur inside every list row. One blurred region per screen area.
  • Flat grey. Blur over a plain background looks like a dull rectangle. Glass needs colour behind it.
  • Ignoring accessibility settings. Reduce Transparency and increased contrast should give the solid fallback.
  • Animating blur intensity. Expensive. Cross-fade opacity between a blurred and a plain layer instead.

Trade-offs and when not to use it

Use glass for Avoid glass for
Tab bars and headers over scrolling content Tables, statements and dense numeric screens
A hero card over a controlled gradient Forms and error messages
Sheets and modals Low-end Android devices you cannot test

Often the best glass is the one you do not build: native tab bars and headers adopt the system material by themselves on iOS and stay correct across OS releases. In a wallet, the amount is the most important pixel. Put amounts on a strong tint or solid colour.

Production and security

Measure scroll frame times with blur on and off on a mid-range Android device and set a budget. Ship a remote flag (glassBlur) that forces the tint fallback per device model. Check text contrast against WCAG ratios with the lightest and darkest content that can appear underneath, in both themes, on both platforms.

Motion and polish

Animation that runs on the UI thread and explains what changed.

Why it exists

A screen that jumps from one state to another makes the user work out what happened. Motion carries that information. In React Native there is a specific trap: an animation driven from JavaScript competes with everything else on the JavaScript thread, so it stutters exactly when the app is busiest. The solution is to run animation logic on the UI thread.

Mental model

A shared value lives on the UI thread. A worklet is a small function that runs there. React renders once to set things up, and then frames are produced without React or the JavaScript thread being involved.

Mechanics

Tool Runs on Use for
Reanimated shared values and animated styles UI thread Almost all custom animation
Reanimated layout animations (entering, exiting, layout) UI thread Items appearing, leaving and moving
Gesture Handler UI thread Drags, swipes, pinches that drive shared values
Navigator transitions Native Screen changes, shared elements, zoom transitions
React Native's Animated with the native driver UI thread for supported props Simple cases with no extra dependency 
import Animated, { useSharedValue, useAnimatedStyle, withSpring, withTiming, useReducedMotion,
                   FadeIn, FadeOut, LinearTransition } from 'react-native-reanimated';

export function SendButton({ sending, onPress }: { sending: boolean; onPress: () => void }) {
  const scale = useSharedValue(1);
  const style = useAnimatedStyle(() => ({ transform: [{ scale: scale.value }] }));   // a worklet: runs on the UI thread

  return (
    <Pressable onPress={onPress} disabled={sending}
               onPressIn={() => { scale.value = withSpring(0.96, { damping: 15, stiffness: 300 }); }}
               onPressOut={() => { scale.value = withSpring(1); }}>
      <Animated.View style={[styles.button, style]}>
        {sending ? <ActivityIndicator /> : <Text style={styles.label}>Send</Text>}
      </Animated.View>
    </Pressable>
  );
}

      <Animated.Text style={[styles.amount, StyleSheet.absoluteFill, dots]}>₹ ••••••</Animated.Text>

    </View>
  );
}

Springs or durations. Springs handle interruption: reverse one midway and it continues from the current velocity. Use them for anything that moves; use timed fades for opacity and colour.

Animate transforms and opacity. These are composited without layout. Recent React Native and Reanimated versions can animate layout properties natively too, but transforms remain cheapest.

End-to-end flow: pressing the Send button

  1. onPressIn runs in JavaScript once and assigns a spring to the shared value.
  2. From here the spring is evaluated on the UI thread, every frame.
  3. The animated style worklet computes the transform and applies it directly to the native view.
  4. React does not re-render. If JavaScript is busy validating the amount, the animation still runs at full rate.
  5. onPressOut assigns a new spring; it starts from the current value and velocity.

Failure modes

  • Animating with state. setState sixty times a second re-renders the component on the JavaScript thread. Use shared values.
  • Reading shared values during render. scale.value in the component body is not reactive and breaks under the compiler's rules. Read them in animated styles or worklets.
  • Calling ordinary functions from a worklet. Code running on the UI thread cannot call arbitrary JavaScript. Schedule back to the JavaScript runtime explicitly.
  • Infinite animations off screen. Shimmer placeholders that keep running drain the battery.
  • Ignoring reduced motion. useReducedMotion exists; use it for anything decorative.
  • Gestures fighting the scroll view. Configure activation offsets so vertical scrolling is not stolen.
  • Motion that delays. Keep feedback under about 200 ms and transitions under about 400 ms.

Trade-offs and when not to use it

Reanimated and Gesture Handler are native dependencies and near-standard in production apps. For a fade on one element, the built-in Animated API with useNativeDriver: true avoids a dependency. Lottie and Rive suit illustrations and are poor for anything that must respond to state. Shared element transitions between screens depend on your navigator's support; check its current status before designing around them.

Production and security

Never let an animation represent success before the server has confirmed it. Animate the move to pending honestly and reserve the success motion and haptic for the confirmed state.

Structure and boundaries

Organising a large TypeScript codebase so that teams and layers do not dissolve into each other.

Why it exists

JavaScript will let any file import any other. In a small app that is convenient. In a large one it means the UI imports the HTTP client, features import each other's internals, and a change anywhere can break anything. Native projects get walls from the compiler and build system. Here you build the walls yourself, with folder conventions, lint rules and, at scale, packages.

Mental model

The folder tree is the architecture diagram. An import that crosses a boundary the wrong way should fail in CI, not in code review.

Mechanics

End-to-end flow: a pull request that breaks a rule

  1. A developer imports src/data/api/client from a component in features/home.
  2. The editor underlines it immediately through the ESLint plugin.
  3. If ignored, CI's lint step fails with "feature may not import data".
  4. The fix is to add a method to a repository interface in domain and use it through the container.

Failure modes

  • utils/ and common/. Everything depends on them and they depend on everything.
  • Barrel files everywhere. An index.ts that re-exports hundreds of modules slows Metro and defeats tree shaking. Use one per feature, for its public API only.
  • Import cycles. A imports B imports A: values are undefined at load time, with confusing crashes. Enable the import/no-cycle rule.
  • Routes with logic. Business code in app/ files cannot be reused or tested without the router.
  • A monorepo too early. Tooling overhead for one app and one team.

Trade-offs and when not to use it

Folders and lint rules are enough for most apps of up to a few dozen screens. Move to packages when you share code with another app, or when independent teams need independent ownership and CI. Feature-first structure scales better than layer-first (components/, hooks/, screens/), where one feature's code is scattered across the tree.

Production and security

Put security-critical code (platform/signing, platform/integrity, the config plugins) under restricted code owners so changes there always get a security review. Dependency sprawl is a supply-chain risk: every npm package with native code runs with full app privileges. Review additions, pin versions with a lockfile, and audit regularly.

Why it exists

Mental model

Measure release builds on a mid-range Android phone. Then ask whether the JavaScript thread or the UI thread missed the frame; the fixes are completely different.

Release and operations

Two stores, two kinds of update, and devices you do not control.

Why it exists

A mobile release is reviewed by a store, adopted over weeks, and never reaches some users. React Native adds a capability native apps lack and a hazard to match: the JavaScript bundle can be replaced over the air without a store release, but only if it remains compatible with the native binary already installed.

Mental model

There are two artefacts. The binary (native code plus a bundled JavaScript) ships through the stores. An update (JavaScript and assets only) ships over the air to binaries with the same runtime version. Anything native needs a new binary.

Mechanics

Runtime version. Each binary declares a runtime version, and an update is only delivered to binaries with the same one. With the fingerprint policy the version is a hash of everything native, so adding a native module automatically makes new updates incompatible with old binaries instead of crashing them.

Update signing. Configure code signing for updates so the app refuses any bundle not signed with your key.

Observability. Crash reporting with source maps uploaded for every binary and every update, release health by version and update id, and business metrics (transfer success rate, outbox age) tagged with both.

Platform obligations. A recent Android target API level, current Xcode and iOS SDK requirements, privacy declarations that match what the app and its SDKs collect on each store. Budget time each year; upgrading React Native and Expo regularly is how you stay within them.

End-to-end flow: a bad release

  1. A JavaScript update reaches 10% of production users. Transfer success for that update id drops.
  2. An alert on "success rate by update id" fires within the hour.
  3. The update is rolled back: the previous update is republished to the channel. Users get it on their next launch.
  4. If the fault had been in native code, the response is the binary playbook: halt the staged store rollout, turn off the feature flag, ship a fixed binary.
  5. A review adds the missing test.

Failure modes

  • An update that needs native code the binary lacks. A crash on launch for everyone who receives it. Fingerprint runtime versions prevent it.
  • Missing source maps for updates. Unreadable stack traces.
  • Breaking API changes. A two-year-old binary still calls your backend.
  • No forced-upgrade path when a native security flaw is found. Updates cannot fix native code.
  • Using over-the-air updates to ship unreviewed features. A store policy violation that can remove the app.
  • Unsigned updates and loose publishing rights. Whoever can publish an update can change what every user's app does.
  • Flag debt. Give every flag an owner and an expiry.

Trade-offs and when not to use it

Over-the-air updates are excellent for fixes and small improvements, and a temptation to skip process. Treat an update like a release: reviewed, tested, staged. Self-hosting the update server is possible if you cannot use a hosted service. Without Expo, plain store releases work exactly as for native apps.

Production and security

For SOC 2: every binary and every update traces to a reviewed commit, built by CI, signed by a controlled key, promoted with an approval; publishing rights for the production channel are restricted and logged. Keep a software bill of materials per release, covering npm and native dependencies. Rehearse the forced-upgrade and update-rollback runbooks.

// src/features/transfer/useTransferViewModel.ts: the reducer from chapter 12, with step-up and the outbox
export function useTransferViewModel(payee: Payee) {
  const { limits, outbox, signing, api } = useDomain();
  const [state, dispatch] = useReducer(transferReducer, initialTransferState);

  const send = async () => {
    if (state.phase !== 'editing') return;
    const amount = parseMoney(state.amountText);
    const refusal = amount ? limits.check(amount) : 'Enter an amount';
    if (!amount || refusal) return dispatch({ type: 'rejectedLocally', reason: refusal ?? 'Enter an amount' });

    const pre = await api.preflight({ payeeId: payee.id, amountMinor: amount.minor });
    if (!pre.ok) return dispatch({ type: 'rejectedLocally', reason: 'Check your connection' });

    let signature: string | undefined;
    if (pre.value.stepUpChallenge) {
      try { signature = await signing.signTransfer(encodeForSigning(pre.value.stepUpChallenge, payee, amount), `Confirm ${formatMoney(amount)}`); }
      catch { return dispatch({ type: 'rejectedLocally', reason: 'Confirmation cancelled' }); }
    }

    const key = await outbox.queue(payee, amount, signature);        // on disk before anything else
    dispatch({ type: 'submitted', amount, idempotencyKey: key });
  };

  // The outbox reports the outcome whenever it happens, even after a restart
  useOutboxResult(state.phase === 'sending' || state.phase === 'pending' ? state.idempotencyKey : null, dispatch);

  return { state, setAmount: (text: string) => dispatch({ type: 'amountChanged', text }), send };
}
